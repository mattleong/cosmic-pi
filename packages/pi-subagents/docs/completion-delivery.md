# Completion, projection, and delivery

Part of the [pi-subagents](../README.md) architecture documentation. See [ARCHITECTURE.md](../ARCHITECTURE.md) for the ownership map and cross-cutting invariants.

## Assignment epochs, questions, and phases

Assignment epochs are prepared monotonically before task issue, advance only after at least one current live authenticated peer acknowledges them, and become unready on disconnect until a new peer handshakes. Supervisor tool calls capture the observed epoch, so delayed prior-assignment events retain their old epoch. Progress and warning/question calls normalize to existing `supervisor_contact` events; warnings update parent-visible projection/session history without injecting a standalone model message, while the latest child warning and latest system warning are preserved separately and folded together into the terminal outcome. Questions remain immediate generation-aware parent actions, and child instructions escalate risks that could invalidate current parent work into questions. The channel assigns report sequence and current captured epoch before emitting existing `BackendReport` data. Report `deliveryId` retries with identical text return the original sequence without a second event, while conflicting reuse fails. Only one question may be used per assignment and only one may block per run at a time; parent reply, MCP cancellation, socket loss, adapter cancellation, and scope close settle the exact owned correlation. Every definite question-death path emits a bounded epoch/request-correlated cancellation event so orchestration clears `waiting_for_parent` instead of retaining a dead question. The channel reserves queue capacity for that cancellation; ownership is not cleared unless the cancellation is queued. A parent reply timeout after transmission returns `reply_outcome_uncertain`, closes the exact question without retry, and retains a bounded system warning.

The standalone helper exposes only `supervisor_progress`, `supervisor_warning`, `supervisor_question`, and `supervisor_submit_report`. It dispatches up to 16 calls concurrently, so a blocked question does not block ping, progress, reports, cancellation, or unrelated responses. Tool execution returns response data and never writes stdout. Only the supervisor RPC operation is interruptible; its `Exit` selects success, failure, or cancellation, then one narrow uninterruptible writer commit publishes and acknowledges exactly one JSON-RPC frame. Cancellation after an RPC reply therefore cannot add a second frame while stdout is backpressured. Writer shutdown still precedes active-call and socket interruption. It never silently retries an uncertain send. Parent death closes TCP and fails pending calls.

Every assignment has a monotonic never-reused epoch and a `preparing`/`issuing`/`running`/`reported` phase. Assignment-scoped events from older epochs, plus activity/tool/progress/warning/question events while idle `reported`, are ignored; handle-scoped lifecycle warnings remain visible in projection and session history but never trigger a parent model turn. A report received while `controls.start` is in flight is held in one bounded slot and committed only after start confirmation (or correlated `run_started` evidence following an outcome-uncertain result). Definite resume-start failure restores the prior view, report/warning fields, active tools, and assignment state under the matching attempt token while preserving bounded warning notices observed during the failed attempt. Outcome uncertainty keeps the new assignment and warning. Confirmation, rollback, and uncertainty reconciliation share one predicate under the run lock: the attempt token still matches, the assignment is still issuing, and the run is not inactive. They do not require a starting view because `run_started` can precede prompt confirmation. Late prompt replies cannot revive a stopped or failed run, change its cleanup facts, or create another report generation. Report acceptance rechecks inactivity under the lock, including post-lock replay. Start confirmation never overwrites an already committed fast report.

Every `issuing` to `running` activation drains `pendingReport` and `pendingRunSettled` while holding the run lock. The same locked transition sets the phase, commits a report or installs the caller's running view, and publishes once. After lock release, `settlement.ts` replays one arm. A report takes precedence over settlement, including close-on-report resumes whose prompt result was uncertain. Buffered reports already passed the public normalization and bounds checks, so replay enters the validated report path rather than crossing that boundary again. `settlement.ts` owns this drain, report acceptance, report commit, and post-lock replay; assignment callers retain only their attempt guards, uncertainty policy, and running-view construction.

Local Claude guidance delivery has a separate optional `steeringDelivery` fact: `pending`, `confirmed`, `not-sent`, `report-unconfirmed`, or `unresolved`. Backend events bind it to the current handle, assignment epoch, and monotonic delivery sequence. A ten-second caller wait does not abandon the backend's correlation or fail the assignment. A matching accepted report can complete with a warning that guidance remained unconfirmed; it is never treated as replay evidence. Terminal pending guidance becomes unresolved and blocks route retry and retry hints, even after process cleanup. The backend's typed primary failure survives native exit, while every public settlement sanitizes and bounds its message.

Runs retain Deferreds only for initialization, cleanup, and a pending pause; each active cwd writer pool owns one shared lease-preparation Deferred. Assignment settlement has no unused Deferred.

## Close-on-report lifetime and root shutdown

All supported candidates close after reporting. Omitted or true `closeOnReport` is accepted; false is rejected before admission. Completion payloads and exclusive await claims survive process cleanup. `subagent_send` steers active assignments, never starts an idle retained session. Local Pi advertises paused in-place resume and completed-session respawn; native Claude/Codex do not advertise resume. Each supported resume is a new monotonic assignment epoch, with session-owned admission so cancellation cannot abandon a published assignment.

Natural completion or failure closes only that run's backend scope and leaves its Pi descendants attached to their original run nodes. Explicit stop marks the selected subtree against new admission and closes it leaf-first. Root shutdown, replacement, tree navigation, and reload close all local children leaf-first, detaches confirmed writer-pool members, then releases each safely releasable final pool lease. Local Pi private run directories remain while a completed run is resumable; failed, stopped, evicted, and session-ended records reclaim them after process cleanup. A graceful shutdown is not crash recovery: parent death after `spawn-started` intentionally leaves a manual-recovery lock even after a surviving backend later exits. Leasing is owned above the three-driver registry, so every writer shares the same protocol without adapter-specific locking.

## Projection and delivery

UI and tool renderers consume immutable projections. The root TUI installs one read-only activity widget above the editor from the same frozen fleet projection. It renders every starting, running, stopping, waiting, or paused run plus any ancestor needed to preserve the tree, marks active await targets with `◎`, and emits no lines for terminal-only state. Its one-line rows use profile plus a provider-free `model:effort` label below 100 columns and the full profile plus host/runtime/provider/model route at wide widths; activity and elapsed time are optional. Adaptive shared host tickers repaint only animation, elapsed time, and relative ages that can change at the current projection cadence; projection and presentation subscriptions invalidate cached panel and render state. Session replacement and shutdown clear the exact widget, subscribers, ticker, and short-lived start/await presentation leases. The ordinary footer is suppressed only while this widget has content and resumes when it is empty. All public tool calls use bounded user-facing action summaries; start calls keep tasks expanded-only and final start results render immutable launch receipts rather than live run snapshots. Collapsed receipts retain the batch outcome plus exceptional failures or route warnings; expanded rows retain profile plus actual selected/attempted route and model, or an explicit resolving/no-eligible-route state. Outcome icons distinguish complete, mixed, and failed batches, and a single `/subagents` hint hands successful starts to the live widget. Non-start/await results persist bounded semantic profile routes, run cards, and per-target failures instead of reparsing prose. Live cards expose run identity, profile/host/runtime/model route (using compact `model:effort ⚡` notation for fast models), write intent, optional exact claims, bounded write-audit state, bounded timing/activity, humanized aggregate usage, state-aware recovery, and expanded provenance/capabilities. Usage cost is optional/unknown: only a backend-reported known cost renders (Pi RPC totals and Claude's `total_cost_usd` estimate are known; Codex remains unknown), unknown or zero-information usage renders nothing — in cards and in the detailed status output, which omits its `Usage` field rather than printing `unknown` — sub-cent prices trim trailing zeros, and a fleet cost subtotal over runs with unknown costs is explicitly marked as a lower bound (`≥`). Compact card fallback preserves capability evidence, and renderers treat absent capabilities as unknown-neutral while an explicit lack of `resume` keeps cannot-resume guidance. `subagent_models` renders effective source, defaults, candidate eligibility, and the explicit launch-check boundary from flat structured candidate cards. Discovery persists the eight candidate policy fields plus `status` and `reason`, never the old prose candidate/order/effective-context representation. Its renderer reads those fields directly. Full, compact, and minimal projections retain all seven routes and all 32 candidates per route; minimal uses short bounded ASCII model/reason fallbacks and marks `contentOmitted`. Persisted details use strict version 2 from one Effect Schema model. Optional bounded `writeClaims`, total claim count, explicit claim-omission evidence, `writeAudit`, and paused-admission fields are additive version-2 card fields; compact/minimal fitting may retain only a claim prefix with its original count, and older version-2 cards remain valid without these fields. Start details require the full request-ordered entry list and optional matching failures, and never contain run cards. Await details require cards and `awaitUntil`; each non-start action has its own discriminant. The public details door applies explicit privacy projections, strips unknown fields, rejects malformed known children without salvage, and selects among semantic full, report-free, compact, and minimal candidates. Both makers and decoders return deeply frozen values whose canonical JSON is at most 48,000 characters. Version-1 or unsupported history uses the existing bounded terminal-sanitized text fallback; no compatibility parser reconstructs cards. Await cards include only the latest report generation and preserve explicit truncation/omission evidence when reports cannot fit. Collapsed tool calls use one accent disclosure affordance with `ctrl+o` hints for hidden start tasks, report sections, launch details, truncated action-failure text, and recoverable fallback lines. A root TUI start or await execution acquires a presentation lease before work begins and releases it on success, failure, or cancellation. While the widget is available, partial start and await result components emit no duplicate hierarchy; non-TUI, nested, and widget-installation failure paths retain the bounded live-card renderer. Settled await cards keep a compact durable outcome. Expanded await cards render each preserved report or error under a compact numbered heading before the static settled hierarchy, suppress routine per-run diagnostics and stale finished progress, and preserve exceptional fallback, warning, writer, and failure evidence. Expanded list and status cards retain their full diagnostics, while no-report completion and recovered omitted output stay explicit. Progressive batch starts remain input-ordered and keep pending/started/failed receipt slots in their persisted details. The fallback partial card renders those slots and animates only the launch header. The widget-backed path shows live fleet rows instead. Settled start rows are immutable and appear only when the final receipt is expanded; collapsed receipts show the outcome, exceptional evidence, disclosure, and live-status handoff. Management banners count the true run total (`runCount`), and a result whose bounded card list omits runs adds an explicit cue to query specific run IDs with `subagent_status`. Send acknowledgements describe active guidance delivery, not a new retained assignment. Interrupt-capable backends that do not advertise resume remain stoppable and present stop/replacement recovery instead of suggesting an unsupported resume. The fleet keeps message/resume/rename input and action errors inside its full-screen overlay, consumes stop confirmation modally, and uses capability-aware actions. List tool cards use parent-before-child rows. Await details retain the requested IDs as the only completion/report-claim targets and add as many report-free descendants as the 12-card bound permits. The persistent widget uses those leased IDs only for `◎` presentation over the complete root projection; descendant-only state changes repaint it without changing completion semantics. The fallback partial card uses the bounded details and explicit omission markers.

The service stores every committed run mutation as one complete immutable `{ revision, runs }` snapshot in a `SubscriptionRef` while still holding the shared run lock, then invokes the best-effort host publisher. List and projection read that immutable snapshot without taking the run lock. Await still captures its revision in the same locked state check, then subscribes for a snapshot with a strictly newer revision; replay closes the check-to-subscribe race, every wake rechecks authoritative run state, and interruption releases the stream subscription with the caller scope.

Each accepted report or terminal failure creates one internal unresolved outcome-generation record. Successful reports retain their final text; failures retain their bounded error; both snapshot a bounded fold of the latest child warning and latest system warning without adding warning ownership to completion claims. The per-record `completionGenerations` map is the sole payload and outbox. There is no pending-completion queue or second receipt index. `completionClaims` remains a separate map from generation to one exclusive opaque owner token, never a refcount. Await atomically claims the current generation when the assignment is finished or the next generation while working, so a claim may exist before its payload. A second await fails with typed `completion_claim_conflict`. Stopped records with an unresolved generation still return a receipt to its matching claim. Competing status observes bounded metadata with report text/assistant transcript redacted and receives no receipt. A receipt carries the owner token, and consumption removes only that exact payload and matching claim.

Report and terminal transitions build the payload, call the lock-required synchronous insertion, open the completion latch, resolve any pending pause, and publish projection before releasing the service lock. Post-lock work is limited to peer notice and returning the committed view. Claim release removes only its matching token and opens the same latch in that locked transition. The completion worker takes the completion gate before the run lock, closes the latch, scans run IDs and generations deterministically for unclaimed payloads, and selects at most 12. It releases the run lock but keeps the gate through synchronous host notification, then deletes only selected payload objects whose exact `(runId, generation)` key was acknowledged. Partial acknowledgement retries only the remainder. If any eligible payload remains, the worker reopens the latch before releasing the run lock; a quiescent eligible payload cannot be left behind a closed latch. Retry delay starts at 100 ms, resets after progress, and caps at 30 seconds.

Delivery first walks immutable ancestry to the nearest connected Pi process and sends a bounded private notification. If no Pi ancestor accepts it, the stateless root host notifier bounds, sanitizes, redacts, and chunks messages. Both paths return exact successful completion keys; an accept-then-throw root result remains uncertain and is retried by the service. Questions use a separate run-ID-keyed map and latch worker. The event handler stamps and queues each question inside the same locked transition that publishes `waiting_for_parent`. The question worker holds the completion gate from selection through host acknowledgement. An await takes that gate before the run lock and claims its selected run IDs, including questions not yet published. The worker skips claimed questions. A successful await tool result confirms only exact `(runId, notificationGeneration, requestId)` receipts for fully rendered runs; output omitted by bounding leaves its question queued. Cancellation, failure, or defect releases the claim and wakes pending delivery. A replacement question cannot be removed by an older acknowledgement. Normal synchronous return accepts a question; an accept-then-throw root notifier has no confirmed acknowledgement and retries. Outcome-uncertain ancestor question sends also remain unacknowledged for retry, without falling through to another recipient. A definite failed outcome whose frozen route still has candidates includes one bounded `subagent_lifecycle` retry hint; outcome-uncertain or exhausted runs do not. The retry action itself waits for confirmed cleanup, creates a linked successor, and never changes completion ownership for the predecessor. A failure after resumed report generation N allocates N+1, preventing key collisions; public `reportGeneration` still counts accepted reports only.

Resolved generation records are removed, while the immutable public projection retains only the latest bounded report, error, and warning for human UI. Close-on-report resume paths retain admission below the hard 64-unresolved-generation bound. After 50 terminal records, start admission may reclaim the oldest terminal leaf with no descendants, unresolved/claimed outcome, process, cleanup ownership, or writer-admission pause recovery identity. Active descendants, immutable ancestry, or unresolved delivery may require the tree to retain more than 50 records. Retention never rejects an otherwise valid start or acts as a tree-wide budget. Eviction is a two-phase reclaim-before-admit transaction: one eligible candidate is exclusively claimed under the lock without deletion by a single `evictionClaim` that simultaneously reserves the prospective process admission (and writer cwd digest plus exact claims, when present) before any destructive reclamation, its private run state is reclaimed outside the lock while it stays registered (resume rejects a claimed candidate), and a final locked phase revalidates eligibility and performs the delete+insert atomically while excluding its own reservation, creating the new record's scopes only after successful reclamation. Definite reclaim success is required before phase C, and a second reclamation phase is impossible by construction. A mutable writer-pool safety transition may still reject phase C; that path keeps and quarantines the already-reclaimed record so it cannot resume without private state. Reclaim failure, timeout, or post-reclaim admission rejection clears only the claim (and with it the reserved admission), keeps the candidate registered, quarantines it against unsafe resume, and admits nothing. Each record still has the hard 64-generation bound, with no duplicate completion queue, plus bounded event queues. Questions use one independent retryable object per run; ordinary warnings stay in projection/session history and are folded into an eventual terminal outcome instead of being sent through `pi.sendMessage`.

## Script results and report read-back

Root start, await, status, and lifecycle registrations declare version-1 machine-readable results from Effect Schema. Their JSON output schemas are generated locally, separate from privacy-bounded persisted details. The result constructor encodes the contract inside the claim scope before consumption; only completely returned owned reports are consumed. Structured results preserve ordered launch/action outcomes and admitted cleanup/retry facts. The strict nested-Pi result decoder preserves this additional channel, although proxy definitions remain model-only for now.

Native execution-start and admission `parentToolCallId` provenance identifies scripted execution. Start preserves empty parent IDs that pinned Pi may omit at admission. Script evidence cannot be downgraded, and model origin requires both observations; missing or capacity-lost start evidence stays fail-closed. Scripted starts enforce read-only intent after route resolution and before admission; lifecycle permits only stop. Scripted awaits and status reject parent attention before consumption; awaits also leave questions unacknowledged, allowing scoped release to wake the existing outbox. Other coordinator tools are model-only. These gates do not confine arbitrary native tools or child capability.

`includeDeliveredReports` is an explicit status-observation option. It reveals the latest retained final text only after the current outcome has already been delivered and when no competing completion claim owns any generation. No receipt is returned, no outbox entry is added, and assistant events stay redacted. Default status/await redaction is unchanged. The accepted-report generation remains available to distinguish later assignments; this is bounded in-memory read-back, not historical or restart-persistent storage.

## Tool result certainty

Root and local Pi registrations retain bounded activation-owned receipts for final returned results. A matching `tool_result` hook sets Pi's error flag for actual target-operation failures, including mixed batches, without replacing content/details or changing the proxy wire. Successful status/list/await calls are not tool failures merely because they describe failed workers. Uncertain actions retain their codes and no-resend guidance; send counts describe confirmed operations rather than claiming unacknowledged input was never sent. Optional version-2 steering-delivery fields survive bounded card projection and remain absent/unknown in older history.

Pending guidance delivery is distinct from both error and success. `actionFailureDisposition(action, failure)` in `tools/outcome.ts` is the single classifier. A failure is `pending` only when the action is `send`, the additive version-2 `pendingDelivery: true` field is present, and the code is exactly `steer_outcome_uncertain`; only the local Claude caller-wait timeout produces that typed flag. Other `_outcome_uncertain` and `_cleanup_unconfirmed` codes are `unconfirmed`; everything else is `failed`. Not every uncertain steering code means pending: an unflagged `steer_outcome_uncertain`, including historical records without the field, stays unconfirmed. The details decoder accepts the flag structurally on any action failure, so a flag on the wrong action or code keeps its code-based error semantics instead of disappearing from receipts. The send producer and details projection persist the flag only on that exact send code. Other malformed values reject the details as usual.

`hasSubagentToolFailure` still reports any returned failure evidence for summaries and expansion. `marksSubagentToolError` is the receipt policy: pending-only and pending-plus-confirmed sends are not Pi tool errors, while any unconfirmed or definite failure in the same result marks the call. Model text never claims pending guidance was delivered. It lists `Guidance awaiting confirmation`, `Unconfirmed targets`, and `Failed targets` separately. The pending paragraph says delivery was still tracked when the call returned and forbids resending, retrying, interrupting, or replacing a worker merely because confirmation is pending; the caller may continue or await, and stop remains available. Compact send counters distinguish confirmed, awaiting-confirmation, unconfirmed, and failed targets. A pending issue is a warning that makes the compact outcome uncertain; its short message omits IDs and codes, which stay in the expanded detail with the no-resend recovery. The default preview renders pending rows amber without error chrome. Expanded results keep labelled raw output whenever failure evidence is returned, even without Pi's error flag. Recovery hints for any uncertain or cleanup-unconfirmed code never advise retrying or resending. Later status and await report delivery through the card's existing `steeringDelivery` evidence. Action failures carry no worker name, because the failing operation returns no caller-visible run view; unnamed pending targets therefore share the generic message, and their IDs remain in expanded details.

The root and nested `/subagents` fleets reuse this classification. A root send resolves only the typed pending error as pending, rather than delivered or failed. The nested fleet accepts a proxied action only from decoded details for the expected action and target. It treats missing, malformed, or mismatched details as unconfirmed, never as success.

## Cancelled waits and report availability

`subagent_await` keeps a call-local snapshot of requested IDs, latest observed target states, descendant context, and pending parent actions. Its Promise boundary returns a persisted `cancelled: true` result only after an interruption-only Effect exit and owned finalizers settle. An aborted signal alone never converts a failure or defect into cancellation. If delivery was attempted before a late abort, the script result marks those reports unknown rather than deferred; opt-in status can recover any already-delivered latest report. A root-local wait returns only after its completion claims are released, without stopping children, consuming missing reports, or launching retries. Await and status wait interruptibly for the shared notification gate, then the run lock. Once both permits are held, only claim insertion and registration of its private scoped finalizer are masked. Both permits are released before the caller uses the observations. The private scope owns claims only, so resources acquired by the caller's use callback retain the caller's scope. Cancellation before ownership does not wait for ancestor-notification I/O holding the completion gate. Local Pi proxy boundaries preserve interruption evidence before Promise error squashing; when their transport supplied no progress, the receipt retains requested IDs and explicitly says states were unobserved. Proxy cancellation has no root-cleanup acknowledgement in the current wire protocol. Its saved result carries `cancellationCleanup: "unconfirmed"` and warns that root claims may still be held; an immediate replacement await may fail with `completion_claim_conflict`. Local bridge finalization is not proof of root cleanup. No timeout, automatic retry, or remote acknowledgement protocol is added.

Finished observations classify `reportStatus` before redacting text: `available`, `claimed`, `delivered`, or `missing`. This metadata does not acquire, release, or consume a completion claim. Version-2 cards retain it through bounded projections. Historical cards without the field have unknown availability, not proof of a missing report.

## Run cancellation and cleanup

- `session-owned.ts` owns the one claim-then-owner-scoped-commit mask shared by session-owned launch, retry, reply, interrupt, stop, and resume, so cancelling a waiter never abandons ownership while owner-scope closure still interrupts the commit.
- Subtree stops join descendant cleanup, including already-stopping and terminal descendants, before closing ancestors.
  Terminal outcomes remain unchanged.
- `writer-preparation.ts` owns lease preparation and masks its shared ownership claim through settlement-finalizer installation.
  Pre-ownership lease checks and joiners remain interruptible, while the lease's synchronous core-lock commits are not.
- Process lifecycle installs its settlement handler before backend-spawn admission, keeping registry permit waiting and driver work interruptible.
  A same-callback ownership flag makes unclaimed cancellation a no-op; claimed cleanup identity-clears the attempt and settles its latch, including cancellation before the driver runs.
- `record-cleanup.ts` masks owned scope closure through backend and writer-lease release and cleanup-outcome publication, because closing a scope cannot be retried after interruption.
  Joiners and pre-close spawn waits remain interruptible.
  An interrupted pre-close owner relinquishes its claim without settling cleanup disposition; awakened joiners or late launch compensation reclaim it.
  A stalled owned release keeps shutdown waiting rather than falsely confirming cleanup.
- Shutdown disables projection publication without blocking late cleanup state commits or private run-state reclamation.

## Tool registration and compact presentation

### Activation

- `src/extension.ts` checks the child marker before importing the root application.
  Root factories await that import and registration; private child entrypoints remain separate.
- Runtime startup runs preview settings as an interruptible best-effort bootstrap, then returns the initial projection, tool runtime, and preview scheduler as prepared activation data.
  The shared session-runtime slot owns latest-start replacement and cancellation, and only its current token may register tools or publish activation state.
- Pi drops its pending tool-restore list whenever a tool is deactivated, so subagent tools stay active through `/tree` and the outgoing instance's `/reload` shutdown.
  They are deactivated only when an activation is lost or on another shutdown, and a later registration deactivates only tools it activated that the session had not kept active.
- `makeRuntime` captures the tree and reload profile handoffs after the slot has disposed the prior runtime.
- Each registering runtime composes `CodePreviewSchedulerService.layer` and passes its startup scheduler through a current-token callback, so isolated extension loaders need no shared scheduler singleton.
  Replacement and shutdown dispose animation fibers and revoke stale scheduling.
  Registration also stops the original progress ticker when compact rendering takes over or execution settles; hidden renderers need not run just to release animation.

### Tool modules

- `subagent.ts` is the registration door; it derives each self-contained Pi output declaration with pi-cosmic-core's shared `toPiToolOutputSchema`.
  `schema.ts` holds the one tool catalog, `SUBAGENT_TOOL_SCHEMAS`: each tool name's parameter schema plus any cross-field validator.
  Registration walks the catalog in `SUBAGENT_TOOL_NAMES` order.
- Root execution, the fleet proxy, and the nested-Pi wire all carry the same tool-keyed `{ tool, args }` input, whose args are exactly the wire JSON; `proxy-protocol.ts` decodes only own catalog names with TypeBox `Check` plus the entry's validator.
- `model.ts` contains plain tool outcome and profile DTOs.
  `execute-models.ts` owns the whole `models` action (static profile-route discovery, its formatted text, and compact details).
  `execute-start.ts` owns the whole public start-batch orchestration: request validation, the one profile snapshot per batch, the `generalist` default for omitted profiles, route resolution, partial outcome publication with hostile update containment, and request-ordered receipts.
  `execute-await.ts` owns call-local progress and cancellation evidence, and `execute.ts` keeps action dispatch, authorization, and post-finalizer Promise cancellation translation.
- `execute-result.ts` separates text, persisted display details, and version-1 script results.
  `contract-schema.ts` defines the authoritative Effect output schemas, and `contract.ts` projects domain facts.
- `execute-workspace.ts` dispatches strict workspace operations through the coordinator, pages complete immutable diffs, and keeps patches out of persisted detail metadata.
- `workflow.ts` registers root-only, model-only `subagent_workflow`, with its schema, text, and compact presentation in `workflow-schema.ts`, `workflow-format.ts`, and `workflow-presentation.ts`; `result-presentation.ts` renders the child-only `subagent_result`.
- Root scripts may launch read-only assignments, await, inspect status, and stop; ultracode gates only `subagent_workflow`.
  All other coordinator tools and every nested-Pi coordinator definition remain model-only.
- `boundary/host-tool-result.ts` owns bounded activation, call, and detail-identity receipts that set Pi's tool error flag without discarding returned evidence, including decoded child-proxy results.
  It also tracks native host-derived call identity from execution-start and admission events, never argument fields or ID spelling.
  Model origin requires matching top-level evidence from both events; empty-parent script evidence is sticky, and missing or capacity-lost start evidence fails closed.
  Unknown call provenance fails closed, and native execution-end events release blocked or aborted call tracking.
- Cancelled awaits conservatively mark any attempted delivery unknown, preserving late-abort read-back rather than asserting an unconsumed report.
  Actual target-operation failures, including mixed batches, mark the call; successful observations of failed workers do not.

### Shell coverage

- All 11 root coordinator registrations and their local-child proxies, root-only `subagent_workflow`, and child-only `subagent_result` use the shared presentation shell, and `tools/compact-summary.ts` opts all 11 coordinator tools into the shared compact setting using decoded domain details.
  Root and local-child proxy registration share this provider.
- The shell owns semantic headings and attention in both compact states.
  Content callbacks retain tasks, reports, hierarchy, usage, routes, and audits without adding a competing status banner.
  A live panel may hide partial hierarchy, but never owns the tool heading, omissions, questions, writer admission, or cleanup recovery.
- `contact_parent` uses content-only callbacks and preview bodies (`tools/render-parent.ts`); arbitrary replies remain verbatim, and child transport returns them with the one `PARENT_REPLY_PREFIX`.
  `tools/compact-parent-summary.ts` supplies pure bounded input summaries for child-only `contact_parent` and supervisor tools through the same token-checked scheduler.
  Live child subjects use bounded sanitized message or report excerpts, and warning calls retain their full warning as the issue detail.
  Exact owned acknowledgements supply semantic summaries; settled questions, arbitrary replies, and errors use the generic compact row and retain their original rendering on expansion.
- The four native supervisor tools are served over private MCP, not registered as Pi tool rows; that transport carries results only and has no Pi TUI renderer.
- Workspace producers record optional UTF-16 display spans while composing output, so expansion can show list records and immutable diff pages without parsing text for deduplication.
  Original content bytes remain unchanged; historical or invalid spans retain labeled raw output.

### Compact issues

- Compact attention policy stays in the typed tool projections, which emit one `CompactIssue` per problem or recovery step in producer order.
  Codes carry run, launch-slot, profile, or workspace identity.
- Issue producers author their human-facing messages where each issue is built.
  Messages are one sentence that starts with a subagent, launch, or profile name, never a run or workspace ID.
  `tools/compact-action-failures.ts` maps failed-target codes and rejected calls to such messages and keeps the service text as detail.
- Headings (`tools/compact-heading.ts`) name runs by display name and use words, not raw operation tokens.
  Running await headers show only the observed finished/target counter; other running headers use current arguments, except start's observed started/total counter.
  Ordinary headers show one combined domain count without routine IDs, route, writer, or report-history metadata, and requested IDs resolve names only from exact matching cards.
- Worker and system warnings, questions, and errors are quoted by their first line (common service failures by name) unless the text opens with agent guidance.
  Run IDs, full text, and agent procedures stay in the expanded-only `detail`.
  Retry guidance travels in the failure's own detail, and a failed launch's cleanup and retry state share one line.
- Routine facts are `info` issues: a stop the status already shows, a pause or stop the call itself requested, a retry moving past its failed option, a list's omitted report text, and an isolated writer's report awaiting review (also a `changes ready for review` heading label).
  Recovery steps with no human-facing fact are `info` issues, shown only on expansion.
- Any error issue makes the outcome an error, and a warning issue turns success into warning; uncertain and cancelled classifications stay.
- Static discovery counts eligible options and disabled or unavailable profiles without claiming launch readiness.
  Valid-source empty routes mean disabled; invalid sources and configured routes without eligible candidates warn.
- Clean settled completed cards keep routine static skip history as one expanded-only info issue.
  Await, status, and list retain child, system, and selection warnings; matching prose never hides an independent warning.
  The latest warning stays unchanged for other tools and expansion, and a separate system warning survives later child warnings until the next assignment.
- Decoded run, claims, await, and workspace outcomes use compact summaries with explicit outcomes and ordered issues; original reports, paths, audits, and diff pages remain on expansion.
  Unknown details use the shared generic compact row while collapsed and the original fallback on expansion.
- `compact-run-issues.ts` never derives grant paths or cleanup or retry authority from bounded cards.
  `compact-start-summary.ts` owns launch-slot issues and the start outcome.
  `compact-workspace-summary.ts` retains pagination and exact review, test, and integration gates using receipt-only display metadata.
  Workspace rows show operation receipts or bounded counts; pagination, orphan recovery, and review, test, and integration gates are info issues, and only an explicit empty list drops generic orphan-recovery guidance.
- Report-only omissions use the strict optional `reportsOnlyOmitted: true` producer flag; generic, error, and uncertain omissions retain warnings and full-status guidance.
  Await summaries count requested targets, not descendant context, and omitted projections point to full status.
- Compact expansion uses content-only callbacks.
  In preview style the shell draws the same issue lines from the summary, so the original renderers draw bodies only: routine counters as muted text, run rows that show IDs only when expanded or when names collide, and agent recovery steps and failed-target evidence only when expanded, under a label.
  Safety issues remain live.
- Parent warnings use the owned warning issue with the full warning as its detail; settled questions and arbitrary replies still decline compaction.
  Expansion retains the original evidence.
- List cards render parent-before-child; hierarchy run rows use one stable width-bounded line per run, with tree identity and state glyph first, route metadata next, and lower-priority details truncated at narrow widths.

### Notification rows

- `application/messages.ts` registers root and child message renderers.
  Pure `ui/notification.ts` shows one human row in both collapsed styles (typed counts and the lone run's display name, or a neutral mark for untyped forwarded and peer notices) and the full content only once expanded.
- `host-notifier.ts` attaches display-only counts and a lone run's name without altering message content, delivery keys, or acknowledgement behavior.
- Workflow results use the same notifier with their own `pi-subagents-workflow` message: completed and failed runs join or start a turn, while a user's stop and an interrupted-run notice wait for the next one.

## Activity provider and fleet

- `boundary/host-activity.ts` registers the root session's Cosmic UI Activity provider through Cosmic UI's `registerRevisionedActivityProvider`, prompts for action input and dispatches actions.
  Pure `ui/run-activity.ts` projects frozen fleet projections into items, details and the action policy: the complete authorized root tree, including terminal history and completed ancestors, and workflows from `ui/workflow-activity.ts` (see [Workflow internals](workflow-internals.md#activity-projection)).
  A row's summary never repeats the state Activity draws beside it: it is why a member's call or a run failed, or what the run is doing.
- Launch leases are published as provider count metadata and await leases as exact-target row metadata, without synthetic selectable rows or moving run ownership.
  Launch counts describe requested work in unsettled start calls, including the interval before run rows exist.
- `ui/run-activity-detail.ts` writes a run's detail pane beneath the state, profile, elapsed time and breadcrumb Activity already shows, technical facts last, and `ui/activity-revision.ts` stamps item revisions.
  Each item's revision hashes its published fields, plus assignment and question identity for runs, so unrelated progress never makes an action stale.
- Credentials are redacted before summaries or selected details leave the producer, and selected-item details use the same checked capability and stay bounded.
- Actions recheck cancellation, the session token, item revision, and current capabilities before entering the authoritative service runner with the host's abort signal.
  Destructive actions declare their confirmation scope, including descendant shutdown for stop.
  Replacement and shutdown revoke registration and callbacks.
- Parent-contact questions explicitly target the parent, never the user.
  Claim admission pauses override questions: peers wait for file access, active offenders show containment, and paused or terminal offenders require parent file-access review.
  The producer uses the authoritative parent-action predicate without treating an older question as claim recovery.
  Ordinary pauses and missing-question waits require parent review.
  These remain blocked rows, preserving unresolved recovery visibility and existing action safeguards.
- Message, reply, rename, and resume declare handoff and use the owned abort-aware Pi input boundary after the shared manager closes; stop, interrupt, and workflow actions run in place.
  Post-input checks compare the captured assignment and question identity and current capabilities, claim, and steering policy, not the item revision, which the run's own progress changes while the user types.
  Pending native guidance remains a warning, never claimed delivery.
- `host-ui.ts` removes the legacy widget only after Cosmic UI acknowledges installed provider UI, restores it when that acknowledgement is lost, and keeps presentation leases and footer fallback intact.
  `boundary/host-activity-widget.ts` owns that widget's installation, projection and render caching, presentation leases, footer suppression, stale-context guards, and disposal.
- `/subagents` uses the unified manager; only absent or pre-admission-unavailable UI falls back to the standalone fleet.
  Rejection, cancellation, and a replaced activation never open another overlay.
- `ui/run-presentation.ts` shares bounded age, short ID, and sanitized route and model projection without choosing panel or tool width policy.
- `ui/run-tree-rows.ts` owns the single parent-before-child walker and box-drawing branch renderer behind both the tool card hierarchy and the fleet and activity hierarchy.
  Tool cards dedupe IDs, promote missing, self, and unknown-parent orphans, and surface cycles as roots.
  The fleet scopes to the visibility root, never renders it, supports collapse, and drops out-of-scope orphans.
- `boundary/host-refresh-ticker.ts` owns adaptive stop-before-start host ticker replacement shared by the persistent widget and full-screen fleet.
- The full-screen fleet projects the authenticated subtree into one parent-before-child hierarchy, expands all branches initially, uses Left/Right to collapse or expand a selected subtree, and uses Enter to inspect the selected run.
  A nested caller cannot render or select nodes above or beside its visibility root.
  Pane-focus borders and headings come from `pi-cosmic-ui`; `session-output.ts` renders the fleet detail pane's heading and subtitle, taking only the detail-pane focus flag from the fleet.
- `src/settings/proxy-controller.ts` registers the packaged nested-Pi subtree manager without owning remote state.

## Module responsibilities

- `src/run/` owns immutable ancestry, per-parent direct-child admission, depth checks, subtree authorization, immutable launch-time routing, cooperative exact-file claims, root writer pools, process and control transitions, native-agent summaries, supported resume and respawn assignments, completion claims and ancestor-first delivery, bounded terminal-history reclamation, and the synchronous tree projection.
- Run modules receive service-owned primitives as one `RunContext` from `internal.ts`, name cross-module operations by their producer's type, and only launch mutates the run registry.
  The service wires producer operations by explicit name, so consumers receive the questionnaire-draining `closeRecordScope`, never the raw cleanup result.
- `src/run/model.ts` holds the one pure predicate for runs that need parent action, `isParentActionRequiredRun`, covering real questions, pauses, and paused writer admission, so service awaits and tool results agree.
- `src/run/attention.ts` resolves the one attention state a run is in (containment, a paused writer peer, paused, a question, or a missing question) by a single precedence, which recovery steps, compact issue lines, the preview renderer, and workflow status all use.
- `src/run/tree.ts` owns pure ancestry, visibility, count, and leaf-first ordering rules.
- `src/run/assignment.ts`, `settlement.ts`, and `resume.ts` own assignment epochs, prompt confirmation, report commit, terminal settlement, and supported resume/respawn generation rollover.
- `src/run/coordination.ts` formats ownership notices and sends bounded best-effort updates. Each send snapshots eligible recipients, then renders recipient text from the live run registry without holding the service lock during process I/O.
- `src/run/process-lifecycle.ts` owns locked backend-control admission, outside-lock joins, process acquisition, event acknowledgment, scoped event and exit fibers, and cleanup handoff.
- `src/run/service.ts` owns the run registry, locks, subtree stop, write-violation containment, runtime cleanup, and direct factory composition. It acquires the proxy FiberMap before registering leaf-first shutdown and provides authenticated service dispatch and questionnaire lifetime callbacks to `proxy-execution.ts`.
- `src/run/proxy-execution.ts` owns authenticated proxy admission, the per-run concurrency bound, keyed execution and cancellation, strict questionnaire decoding, and bounded response encoding. It uses the service-owned FiberMap without a separate registry or runtime.
- `src/run/completion.ts`, `completion-observations.ts`, and `notification-delivery.ts` own outcome records, exclusive claims, receipt consumption, and the retrying delivery outbox.
- `src/run/write-claim-control.ts`, `writer-pool.ts`, `claims-observation.ts`, and `admission.ts` own exact claim changes, shared lease membership, bounded tool observation, and overlap policy. `projection.ts`, `state.ts`, `session-events.ts`, and `warnings.ts` own bounded immutable views and diagnostic/session-history projection.
- `src/run/tool-policy.ts` owns the root Pi active-tool snapshot, the competing-orchestrator denylist, and canonical authenticated proxy names.
- `src/tools/execute-await.ts` owns call-local await progress/cancellation snapshots and interruption evidence; `execute.ts` translates that evidence at the Promise boundary after finalization.
- `src/tools/details.ts` is the sole public details door. Its private `details-schema.ts` room owns the strict version-2 Effect Schema model, focused decoders, canonical bound, and freezing; `format.ts` and `render*.ts` own bounded model-visible output.
- `src/ui/` and pure `src/settings/ui/` modules consume immutable projections and never own Effect resources.

Backend-specific completion evidence is documented in [Local backends](local-backends.md).
