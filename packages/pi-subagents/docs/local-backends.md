# Local backends: Pi, Claude, Codex, writer pools and leases, and the supervisor channel

Part of the [pi-subagents](../README.md) architecture documentation. See [ARCHITECTURE.md](../ARCHITECTURE.md) for the package ownership map, [Completion and delivery](completion-delivery.md) for assignment/report ownership.

## Local Pi ownership and safety

Local Pi children launch the published `dist/bundle/cli.js` entry, still Pi's `bin` in the pinned 1.2, in RPC mode over stdin/stdout with bounded/schema-decoded frames. The unbundled `dist/cli.js` imported server dependencies that were not shipped separately in the CLI installation when this was checked against Pi 0.85. The initial `get_state` handshake has a 30-second deadline because process spawn precedes model/resource loading and extension startup. Ordinary RPC commands and IPC acknowledgements retain their 10-second deadlines. Natural local Pi transport closure waits interruptibly for its exit receipt before rejecting pending RPCs, preserving bounded, sanitized stderr plus exit code/signal through failed-start cleanup. The same diagnostic reaches run exit handling; scope teardown retains immediate generic cancellation and never waits for an exit receipt. Initial usage reconciliation propagates startup failures, while later usage refresh remains best effort. Startup expiry never replays the request or sends the task; the failed launch still joins owned cleanup before returning. A separate bounded Node IPC channel goes directly to the root process and carries parent contact, peer notices, ancestor outcomes, and authenticated coordinator proxy calls. `boundary/local-pi-ipc.ts` is the only owner of raw `child.send`/`process.send`, message and disconnect listeners, bounded callback settlement, and schema decoding for both directions. It passes typed contact events to `child-process.ts`; `backend/local-pi-rpc.ts` owns command-checked native RPC and IPC-acknowledgement correlation, and `backend/local-pi-events.ts` maps those typed contacts without seeing raw IPC values. The backend emits normalized events through a bounded, backpressured queue, and raw event ownership is acknowledged only after run orchestration consumes each normalized event. Run orchestration supplies every assignment-start control with a monotonic assignment epoch, and the adapter tags assignment-scoped normalized events with the active epoch. Definite start failure restores the adapter's prior epoch; outcome-uncertain failure retains the attempted epoch. Run orchestration does not construct or decode Pi RPC commands. Backend continuation state is an opaque token to orchestration; only the local Pi adapter translates its token into a Pi session-file launch argument, while `view.sessionFile` remains status metadata. Fresh children use a dedicated session directory; forked children receive a private copy of the stable parent branch. Runtime API keys cross through an ephemeral environment bootstrap rather than argv. Each child receives the root's protocol fingerprint, a hash of the Pi version and the modules that define the root-child wire (`boundary/protocol-fingerprint.ts`); a child whose own copy differs, because `pi update` or a package update changed Pi or pi-subagents on disk mid-session, writes a "restart Pi" line to stderr and exits 78 before taking work, and the root reports it as the failed start. Pi, Claude, and Codex children all exit within about a second of stdin closing, which happens when the root process dies, so no separate parent-death watchdog runs. A Pi child whose `get_state` reports a different model than the route requires (ignoring registry `@` context variants) fails its start with `pi_model_mismatch`. Pi children and the supervisor MCP helper that Claude and Codex start run on `process.execPath`, which Homebrew resolves to a versioned Cellar path that `brew upgrade` deletes, so every local launch preflight first fails with `node_executable_missing` and a restart-Pi message when that binary is no longer executable. Children load extensions from Pi settings and installed packages only, never the root's temporary `-e` extensions, so a model that a `-e` provider registers in the root makes the child exit 1 with `Model "…" not found`. That startup failure gets code `pi_model_not_found` and a second line with the `pi install` remedy, which stays out of the one-line summary. After startup, the run's model follows the `provider/model` that each assistant `message_end` reports, so status names the model a user extension switched to mid-run, while relaunch and resume still use the route's model. Route planning skips a forked Pi candidate with `fork_context_too_large` when the parent's context exceeds 80% of that model's window. Pi children inherit the parent environment except Node loader settings, Pi session identity, and Git's repository-local variables (`git rev-parse --local-env-vars` and `GIT_CONFIG_KEY_*`/`GIT_CONFIG_VALUE_*`), so a parent started from a Git hook cannot redirect a child's Git. Claude and Codex children receive only an allowlist: identity, locale, paths, certificate settings including `NODE_EXTRA_CA_CERTS`, and proxy variables in either case. `boundary/host-child-pi.ts` owns one-shot credential consumption/scrubbing and the eligible `before_provider_request` priority-tier hook shared by local Pi. Local Pi consumes credentials during child extension registration. The priority hook reads `pi-subagents-fast-mode` for each provider request, not during factory initialization: Pi applies CLI flag values after loading extensions. Only the boolean `true` enables the hook, and each request still checks the active provider/model and payload.

Child stdout lines are limited to 4 MiB, but Pi repeats whole messages and tool results, including base64 images of up to 4.5 MiB, in `agent_end`, `turn_end`, `entry_appended`, tool-result `message_start`/`message_end`, and `tool_execution_update`/`tool_execution_end`. The shared parser never buffers an oversized line: it keeps a 2 KiB prefix and a 256-byte suffix, discards the rest through the newline, and keeps parsing. The Pi backend reads the event's leading fields from the prefix. It skips those aggregate, session, and tool-result events: settlement comes from `agent_settled`, and the backend does not read `agent_end.willRetry`, which Pi writes after the messages. A skipped `turn_end` or `entry_appended` still refreshes usage. An oversized `tool_execution_end` closes its tool from the leading `toolCallId` and `toolName` and the trailing `isError`, with a size note as its output preview. Any other oversized event, such as an assistant `message_end`, fails the run as a protocol error. Claude Code repeats tool-result images and documents in its `user` line, so an oversized line whose first content part is a `tool_result` closes that `tool_use_id` (always as a success, because `is_error` follows the content), and an oversized `stream_event` counts as activity. Any other oversized Claude line, and every oversized Codex line, is a protocol error.

Fork creation copies the stable parent branch. Pi 0.86 through the pinned 1.2 persist prompt and tool state as `role: "system"` messages and compaction `systemMessage` fields; how the copy treats them depends on whether the fork can share the parent's prompt cache. In both cases labels become inert `pi-subagents-fork-anchor` custom entries, every entry keeps its ID, parent link, and timestamp so compaction anchors still select the retained conversation, resuming the child's own session does not sanitize its transcript, and the launch allowlist and competing-orchestrator denylist remain authoritative over executable tools, including tool membership restored through branch navigation.

A fork shares the parent's prompt cache when its model is the parent's current model and the transport can carry the child's own prompt and tool changes after the inherited history without changing the request prefix: Anthropic Messages models with mid-conversation system messages and tool changes, and OpenAI Responses or Azure models with mid-conversation system messages and additional tools or tool search. Route resolution records this as `sharesParentPromptCache`, and the root then passes the parent session's ID to the child as `PI_SUBAGENT_PROMPT_CACHE_KEY`. The copy keeps the parent's system messages, compaction `systemMessage` fields, and assistant thinking verbatim, so the child's first request starts with the prefix the parent's last request cached. Authority still comes from the child. Its first prompt patch replaces every inherited section that differs and removes the ones it lacks, so the replayed prompt is the child's. Pi executes only the child's registered tools, so a call to a tool only the parent declared fails as unknown and runs nothing. Anthropic requests withdraw the parent's other tools in place. OpenAI Responses requests keep the parent's tool declarations: the child's removals and redefinitions of inherited tools are dropped from the request, its new tools are added in place, and the payload carries the parent's `prompt_cache_key`. The session file keeps Pi's own tool record, and a request that no longer starts with the inherited prompt, such as one after the child compacts, is sent unchanged. A branch whose system messages carry prompt text, which section patches cannot withdraw, or that holds an encrypted checkpoint is isolated instead. Codex is excluded because Pi 1.2 derives its `session-id` header from the child's own session after extension headers apply, and the parent's cached prefix was unreachable without it.

Every other fork is isolated. Parent `role: "system"` messages, including opaque content, section patches, and tool declarations, become inert anchors. Ordinary inherited compactions lose only `systemMessage`; summaries, details, usage, and retained messages survive. Better OpenAI encrypted checkpoints become inert anchors because the child does not load their decoder. Pi then reconstructs the plaintext branch behind them, respecting the latest ordinary compaction. Encrypted parent payloads are not copied. Assistant thinking blocks are excluded for cross-model portability.

Pi 0.86 through the pinned 1.2 route RPC `steer` and `follow_up` through extension input hooks with source `rpc`. Hooks may transform or handle guidance before queue admission; a successful RPC response means accepted or handled, not necessarily queued unchanged. A bare RPC `steer` to a child that has already settled is queued with no run to consume it, so local Pi guidance is an RPC `prompt` with `streamingBehavior: "steer"`: it queues into a working child and starts a turn in a settled one. The adapter reads the returned `disposition`: `queued` and `started` deliver the guidance, `handled` fails with `guidance_not_delivered`, and `started` discards the settlement the child reported before it. Natural settlement first waits for admitted guidance, parent replies, and descendant notifications to drain, then drops a settlement that guidance made stale. The offline bundled-CLI regressions check both input paths and queue clearing without a provider call, and a faux-provider child shows that a steering prompt after `agent_settled` starts a turn while a bare steer does not.

A credential-free integration test runs real bundled Pi children through `ChildProcess` and `SubagentService` with a private home and agent directory. A scripted faux-provider extension in that agent directory records each request's prompt, system prompt, and active tools; the test covers parent contact, the final report, resume from the session file, subtree stop, and the observable effect of `--approve`, `--name`, `--append-system-prompt`, and `--tools`. Pi rejects unknown options at startup, so a removed flag fails the launch.

`boundary/host-child.ts` creates one session-runtime slot for the child bridge, which owns one managed runtime for the current started child session. A package-local scoped Layer attaches the IPC listener and detaches it when replacement or shutdown closes the runtime. Preview settings load through the runtime's cancellation signal before activation. Only the current session identity and slot token may register or execute fresh proxy tools, `contact_parent`, and the subtree manager; a reload first removes their active names. A partial registration removes those names and closes the runtime. Each question and proxy call owns one exact Deferred map entry through `acquireUseRelease`. Response callbacks complete that Deferred synchronously, while release deletes only the same waiter identity and sends cancellation only under the established delivery rules. Listener release and shutdown reject all remaining correlations unconditionally. A disconnect callback does so only while its listener still belongs to the current session, so a detached old listener cannot reject the replacement session's waits. Controls from a detached or superseded listener receive no acknowledgement.

Pi 0.84.4 continued queued steering after `abort`, and Pi 1.2's `abort` still leaves the steering and follow-up queues in place, so resumable interruption first closes run-level turn-input admission and waits for admitted guidance, parent replies, and descendant notifications to drain. Parent replies receive a correlated child acknowledgment after the waiting tool is resumed (or a typed ownership rejection if the question is gone). Notifications receive a correlated acknowledgment after the child synchronously admits `pi.sendMessage`. The child (`boundary/host-child-settle.ts`) starts a turn for a notification only while idle; while it works the notification is sent with `triggerTurn: false`, so Pi holds it outside the steering queue, appends it at turn end or at abort, and the child continues its settling run to react. `clear_queue` therefore removes only queued guidance, never an acknowledged descendant notification. An acknowledgment-uncertain notification remains owned by that first ancestor instead of falling through and risking duplicate delivery. Replies and notifications share the adapter's session-local turn-control semaphore with interruption. Once it owns that semaphore, interruption sends and confirms an IPC barrier. Node IPC ordering proves the child processed every earlier turn input before the adapter issues correlated `clear_queue`, discards the returned steering and follow-up text, and sends `abort`. New guidance, parent replies, and ancestor notification delivery are rejected after `pauseRequested`; paused ancestors are skipped. Barrier, clear, or transport failure and uncertainty suppress later interruption commands and release the pause claim. Clear uncertainty uses `clear_queue_outcome_uncertain`, distinct from post-abort `interrupt_outcome_uncertain`; only the latter keeps a pending pause that late child settlement may confirm.

At every local Pi launch, the root coordinator snapshots the root Pi's current active tool names and project-trust decision. `writeIntent` does not filter those names. Only competing coordinator/orchestrator implementations are denied; the public extension returns when `PI_SUBAGENT_CHILD === "1"` before importing the root application, and a packaged private extension registers authenticated `subagent_*` proxies plus the subtree manager. Proxy requests cannot carry ancestry: the root binds them to the channel's run ID and authorizes run targets against that subtree. Workspace mutations use the stricter direct-parent ownership check.

An active name is not an implementation transfer. The child can use it only when its trust mode discovers the providing built-in, extension, or package, or when the package explicitly installs the private integration. The snapshot is immutable for that launch. A nested start returns to the root for a fresh root snapshot, so child-local active-tool toggles do not control grandchildren. Before ownership, the snapshot validates count, exact comma-free names, control characters, per-name length, and aggregate UTF-8 size; Pi's CLI parser must not normalize or inject another activation.

Pi read-only is a no-mutation prompt and writer-lease policy, not capability confinement, a filesystem sandbox, or a confidentiality boundary. It receives the same trusted-tool snapshot as a Pi writer and does not acquire a writer lease. In a trusted local Pi child, active/discoverable Code Mode is consequently available for either intent. The model applies `writeIntent` and exact-file claims when it writes the program. Native codemode dispatches nested tools through Pi hooks, approvals, and registered definitions; its emitted tool-execution events participate in per-file claim observation. This remains cooperative, asynchronous observation, not filesystem confinement. Nested Pi coordinator tools are always model-only. Native Claude/Codex launches retain their fixed adapter-specific tools and sandboxes and do not consume the Pi snapshot.

## Isolated workspace lifecycle

The root coordinator selects one persisted `writerWorkspaceMode` for the session, defaulting to `shared-checkout`. With opt-in `worktree` mode, a writer launches in a detached worktree in package-private state; its cwd lease protects that isolated directory rather than reserving the parent checkout. Only root launches worktree writers in this release; nested writer launches fail explicitly instead of borrowing a parent workspace lease. Read-only nesting and shared-checkout nesting remain supported. Nested read-only runs inherit their authenticated parent's effective cwd, including an isolated worktree, rather than the root checkout. Read-only runs do not acquire workspaces. `shared-checkout` retains the cooperative pools described below. Mode changes are refused while writers, reservations, quarantined cleanup, or unresolved artifacts remain.

`workspace/service.ts` owns private artifacts and Git operations. Its standalone bare repository contains only a bounded snapshot of current source files: every tracked file with its staged/unstaged contents, plus eligible untracked source. It never borrows the source object database or imports source HEAD history. Dependency, build, and Pi state directories (`node_modules`, `vendor`, `dist`, `build`, `coverage`, `.pi`) stay out even when tracked; the workspace handle lists any tracked paths they omit, and the writer's task names them. An untracked file is copied only with a source-like extension and a name that isn't credential-shaped (`.env*`, `.npmrc`, `secrets*`, `credentials*`, `*.pem`, SSH keys and similar). Ignored files never are, including those ignored by the user's global excludes file (`core.excludesFile`, else `$XDG_CONFIG_HOME/git/ignore` or `~/.config/git/ignore`), which the isolated Git is given explicitly. Captures of the source checkout (create, prepare, and integrate) refuse a file whose bytes differ from its stage-0 index blob when it contains a private key block, AWS access key ID, GitHub token, or `sk-` key; content the index already holds is already stored in the user's repository, so committed and staged fixtures pass. Worker and prepared-tree captures are not scanned, because their content was written by the worker and already exists on disk. This is a guard against making durable copies of uncommitted credentials, not a universal credential detector. Unsupported repository/file states fail explicitly, and every refusal's detail names the path, the rule that fired, and a remedy: bare source repositories, sparse checkouts, skip-worktree or assume-unchanged index entries, unmerged indexes, submodules inside the repository, hardlinks, special files/modes, and oversized files. Linked worktrees and submodule checkouts work as sources because Git resolves their index and HEAD paths; SHA-256 source repositories compare SHA-256 blob ids, while the private repository is always SHA-1. Tracked symlinks with canonical relative targets are preserved only when they point directly to a separately captured regular file inside the repository, such as `CLAUDE.md -> AGENTS.md`. Absolute, escaping, excluded, dangling, chained, directory-target, untracked and ancestor symlinks are rejected, as are noncanonical targets such as `missing/../AGENTS.md`. Workers may change the target regular file, but adding, removing, retargeting or replacing a symlink is rejected before integration. It caps snapshots at 4,000 files, 4 MiB per file, and 32 MiB total. Invalid UTF-8 text without a NUL in the first 8,000 bytes fails explicitly rather than being decoded with replacement characters. `.gitattributes` files are copied like any tracked file, but the private repository's `info/attributes` unsets `text`, `eol`, `crlf`, `filter`, `ident`, `working-tree-encoding`, `diff`, and `merge` for every path, so checkout, apply, and diff stay byte-exact and never run a filter or driver. Each capture reads and hashes its files in-process and writes every blob and one parentless commit through a single `git fast-import` stream. Snapshot size and content checks fail closed. Native Pi tools still have local-user authority, so isolation is not a confidentiality boundary or filesystem sandbox. Excluded dependencies and local settings are absent unless the project declares a setup command.

A trusted project's `.pi/pi-subagents.json` may declare `workspaceSetup: { "command": [argv...], "timeoutSeconds"?: 1-3600 }` (default 600 seconds); global documents reject it because setup is repository-specific. The command runs without a shell at the root of each new isolated writer tree before the worker starts, and again in the combined tree after `prepare`, with the user's environment minus Git's repository-local variables, in its own process group with bounded output. Afterwards the engine requires the tree to match its baseline (or the captured prepared tree): setup may add only ignored or excluded files such as `node_modules`. Changed project files, a non-zero exit, or a timeout fail the launch or preparation with `workspace_setup_failed`; a failed launch discards its new workspace. Setup does not run for `revise`, which reuses the worker tree. For pnpm, `["pnpm", "install", "--offline", "--frozen-lockfile"]` installs from the local store, and workspace links resolve to the isolated tree's own packages rather than the source checkout. The setting applies after `/reload`.

The run coordinator's workspace modules bind each artifact to its authenticated direct parent and own process-cleanup evidence, revision requests, and mode admission. Artifacts outlive backend scopes and terminal-history eviction. A final report changes no parent files and grants no approval. `subagent_workspace review` freezes a cleaned-up proposal and pages its immutable patch. The parent must inspect every page, prepare the exact revision against current parent work, and run relevant tests in the returned combined cwd. Only then does `integrate` accept the exact revision/preparation pair and apply uncommitted edits without changing the parent index. Conflicts, drift, modified preparation, or uncertain cleanup block integration. `revise` creates a backend-neutral successor assignment, whose admission makes the old review/preparation stale; `discard` explicitly deletes an unwanted proposal after cleanup. `run/workspace-control.ts` keeps mode admission and listing and composes the rest: `workspace-binding.ts` holds the shared bindings, `workspace-launch.ts` the launch, resume, and revise paths, `workspace-review.ts` review, prepare, and discard, and `workspace-integration.ts` integration.

Launch, resume, and revise check what they can before touching a workspace. A worktree writer checks direct-child capacity before its workspace is created, then holds one of its parent's direct-child slots until admission, an eviction claim while history is reclaimed, or failure; every other start and resume counts that slot. If running children alone fill the limit, the launch fails with `direct_child_capacity` at once. If only launches still creating workspaces fill it, the launch waits, interruptibly and holding nothing, until one of them resolves, then checks again. The binding is recorded as soon as the engine acquires the workspace, so an interrupted create can still be found. A start that is never admitted frees its slot, then discards the workspace it created; if that discard fails, the binding stays so the parent can discard it. Admitted starts that fail keep their workspace, because route retry forks from it.

Resume and revise never change the workspace before the resumed or successor writer is admitted. Resume checks everything, the writer's binding included, in one locked claim. It refuses a writer whose binding a root operation holds (`workspace_operation_in_progress`) or a revision successor is using (`workspace_owner_unavailable`), and a workspace this session integrated, discarded, or left mid-integration (`workspace_finished`); a kept worker can still be discarded. A writer whose process is still alive resumes in place and leaves the workspace as it is; otherwise the claim marks the reviewed revision stale as it commits. Revise checks the binding, session, quarantine, nesting, and direct-child capacity under the run lock, then holds the binding while its successor launches. The successor's launch takes over that hold as its first step, so an abandoned revise call doesn't release it, and until the successor is admitted or refused, review, prepare, integrate, discard, and another revise refuse with `workspace_process_unsettled`. Admission commits the revision under the same lock: the binding takes the successor's request, and the reviewed revision is stale. A refused successor leaves the reviewed revision, the tested preparation, and the earlier revision request unchanged. While a revision is stale, `list` shows the workspace as active with no revision or preparation, reviewing the old revision fails with `workspace_revision_stale`, integrating the old pair fails with `workspace_preparation_stale`, and the next review reopens the engine record and freezes a new revision. Revision successors are ordinary root runs. A fork keeps its original source's baseline exclusions.

Review, prepare, and discard queue one at a time on the coordinator's workspace operation lock, mark the binding busy, and call the engine outside the run lock, so settlement, stops, and admissions never wait behind engine work. A second root operation on the same workspace waits its turn; a resume, retry fork, or other caller that finds the binding busy fails with `workspace_operation_in_progress`, and a writer-mode switch reports the workspace as unresolved meanwhile. Integration queues on the same lock but holds the run lock throughout, so no writer is admitted to its source mid-integration.

After a committed integration the engine removes the proposal's `prepare-*` test trees and its worker tree. Trees that a live run still uses, such as a reader the writer started, are kept. The worker tree is also kept when the worker holds any file the integrated revision left out, such as an unsupported file type or a file at an excluded path like a writer's `.env` or vendored code, even where the source has its own excluded file of that name: the worker started from the baseline snapshot, which holds none of them, so a writer made each one. Only gitignored files don't count. The integrate result then names those files and the worker root, and `discard` deletes the kept tree. A failed removal is a warning, never an integration failure, and nothing is removed when integration fails. Integration refuses up front with `workspace_integration_quarantined` while quarantined. If a source lease release fails after the integration committed, the workspace still reports integrated, the result warns, and writer admission and further integration stay quarantined until Pi restarts; the lease may then need manual recovery.

Ordinary new nested directories are supported. Integration leases every existing ancestor of each touched file, rechecks source and preparation evidence, and records planned directories and file changes in a durable journal before publication. A fixed one-shot Node helper checks its cwd device/inode and uses only relative names inside that directory. It writes each new file to a temporary `.pi-workspace-new-<id>` sibling, moves a file it replaces or deletes to a `.pi-workspace-old-<id>` backup beside it and checks the backup against the reviewed preimage, then installs with an exclusive link so a competing destination is never clobbered. Journal updates are fsync-backed. Publication is not an atomic multi-file transaction, so backups stay until the whole integration commits: once the record says integrated, the helper deletes them, and a backup it can't delete is an integration warning naming its path, never a failure. A conflict or failure stops publication without rollback and leaves the workspace mid-integration. The journal and every backup stay for manual recovery, as does the temporary copy of a file whose outcome is uncertain; a conflicting file's temporary copy was never installed, so the helper discards it.

A crash leaves the same evidence. Before the integrated record is saved, the workspace is mid-integration and its journal names every temporary and backup path; a crash between capture and install can leave a file's original only in its backup. After that save, only backups the cleanup had not yet deleted remain, and the journal still names them.

The tool/proxy boundary never accepts caller ancestry, owner IDs, or a caller-supplied cleanup boolean. Nested proxies bind identity on their authenticated channels; subtree visibility does not grant workspace mutation authority. Review patches appear only as bounded text pages; persisted details keep IDs and paging metadata rather than whole patches.

Workspace engine details:

- `boundary/git-installation.ts` resolves Git once per process: `/usr/bin/git` when present, else the first absolute `git` on the user's PATH. Workspace creation requires Git 2.31 or later. The user's excludes file is resolved the way Git resolves it and passed to every isolated Git call, which otherwise runs without global or system configuration.
- `boundary/git-worktree-store.ts` owns records and the store lock. Every mutating engine operation holds a pi-cosmic-core `CrossProcessLock` keyed by its source checkout root under `<agent-dir>/git-workspaces/locks`, so sessions in different Pi processes serialize per checkout while other checkouts proceed; listing takes no lock. A waiting operation polls interruptibly for up to two minutes, then fails naming the lock and its owner's process ID. A lock whose owner process has exited is reclaimed on the next attempt. The agent directory is resolved through `realpath` once, so a symlinked `~/.pi` works; symlinks below it are still refused.
- `boundary/git-worktree-recovery.ts` owns record listing and editable-tree removal.
  Listing separates valid records from fixed-size unavailable-artifact diagnostics and revalidates registry security and identity after scanning.
  Registry failures, defects, and interruption still reject the listing; individual unreadable records do not hide healthy neighbors.
- Root listings retain unknown artifacts without inferred owner or source metadata; nested listings expose only valid exact-owner records.
  Unavailable artifacts block mode changes regardless of source, remain visible as warnings across pagination, and grant no mutation or recovery authority.
- Fork records persist predecessor identity before acquiring a seed, and creation removes the seed before the fork becomes owned.
  A failed fork keeps its seed and `creating` record for manual recovery; no session owns or discards it.
  Discarding a fork checks predecessor owner and source identity and that no seed remains, and discard is recorded only after all editable trees are removed.
- Acquired integration leases enter cleanup tracking under the ownership mask, and lease release preserves the caller's finalizer mask.
  Required ancestor roots are revalidated before journal publication.
  Publication discovery refuses existing ancestors absent from the prepared lease set, including directories created after that revalidation; missing directories must still be created exclusively.
  Encoded recovery records must fit the reader's 64 MiB limit before temporary-file creation.
- `boundary/git-worktree-symlink.ts` reads tracked internal link text without following it; capture requires its target in the same snapshot as a regular file.
  Freeze and publication reject link changes, so the publication helper remains regular-file-only.
- `workspace-launch.ts` owns launch checks, the direct-child slots worktree launches hold while acquiring workspaces, resume admission, and backend-neutral revision successors.
  `config/store.ts` persists the writer mode, and settings change it only through coordinator admission.

Crash or reload artifacts without current ownership are never adopted. Each record names the owner lease its creating engine holds from its first workspace until its runtime closes; a free lease proves that session ended, whether it reloaded, quit, or crashed. The root of another session in the same checkout may then `discard` the orphan: the coordinator first takes the writer lease on its worker tree, so a writer still running there blocks the discard, and the engine then removes its editable trees and records it as discarded. A workspace left mid-integration still requires manual journal recovery, and records without owner evidence or that cannot be read are never discarded this way. Nothing else is deleted automatically: at startup each runtime collects discarded and integrated records a week after their last change, under their checkout's lock, unless an editable tree remains (such as a worker kept for files integration left out) or a remaining fork names the record as its predecessor. For any other artifact, inspect `subagent_workspace list` and the private artifact metadata before recovery. Independently confirm every writer process and descendant is dead, preserve the proposal and integration journal, and compare any partially published paths against the journal and parent local work before manual repair. Do not remove a private Git directory or lease solely because the parent PID has exited. Unresolved evidence remains fail closed; list visibility is not mutation authority.

## Local Pi usage

- `backend/local-pi-usage.ts` validates cumulative `get_session_stats` snapshots.
  The initial snapshot excludes copied parent history; one process-lifetime high-water mark emits deltas across paused and resumed assignments and never rebases on lower or malformed totals.
- Assistant messages carry text and terminal evidence but no accounting charges.
  Dedicated usage events are process-scoped, because run totals survive assignment changes and include idle warming.
- `process-lifecycle.ts` supplies the source handle; settlement rechecks exact handle ownership under the mutation lock before merging.
  Missing or stale handles cannot charge a replacement, and usage never changes activity, report text, or terminal evidence.
- The driver keeps stats requests out of the raw RPC dispatcher.
  A scoped coalesced lane shares a semaphore with startup and refreshes after `turn_end`, `compaction_end`, and `entry_appended`, and before settlement.
- Delayed usage remains valid across paused and resumed assignments; pending settlement still carries its original assignment epoch.
  Transport closure releases pending RPC waits and drains held settlement before ending output; scope cancellation can interrupt that drain.
- A valid baseline is required before sending any prompt, so malformed or unavailable startup stats fail initialization without charging parent history or discarding early work.
  Later failed accounting is best effort and never fails an active run.

## Structured child questionnaires

- `host-ask-user.ts` consumes the versioned `pi-ask-user/protocol` root capability and publishes checked child relays over existing authenticated transports.
  Only explicit blocking `ask_user` requests from local Pi enter this path.
  `pi-ask-user` remains the sole tool registrar and must be discoverable in the child; a missing relay or capability fails closed.
  Native Claude and Codex, asynchronous child questionnaires, ordinary `contact_parent` questions, and raw `extension_ui_request` forwarding are not supported.
- The root derives owner run, assignment epoch, and request ID from coordinator state, never tool arguments.
  A separate strict 128 KiB decoder keeps questionnaires out of `SubagentToolInput`.
- `run/questionnaire-lifetime.ts` owns assignment validity, revocation signals, cleanup joins, and at most 256 request-ID tombstones per assignment.
  Replayed answered or cancelled identities cannot reopen a dialog.
- Publication revokes queued, visible, or hidden waits on pause, stop, settlement, and assignment replacement; process cleanup joins their finalizers outside the service lock.
  Shutdown revokes before leaf-first release.
- The root boundary installs exact capability and owner cleanup before the interruptible answer wait.
  Its narrow masked finalizer joins `cancel(owner)` on success, failure, and interruption; aborting a Promise alone does not acknowledge root dialog or editor cleanup.
  A stalled owned cleanup keeps stop and shutdown waiting.
- Local child reload cancels tracked questionnaire correlations before detaching the old IPC listener.
  Capability generation and assignment validity are rechecked before returning answers.
  Deliberate cancellation remains a cancelled outcome, not an invitation to retry through another UI.

## Writer pools, cooperative claims, and cross-process safety

Fixed local CLI readiness probes require confirmed leader exit, sweep the detached process group, and confirm its absence.

The root `SubagentService` owns the complete run tree, backend scopes, and one writer pool per canonical cwd. Nested Pi writer requests enter the same admission path, so writer leases and disjoint claims remain tree-wide even though active-run limits are per parent. It resolves `realpath` for launch and diagnostics, while both the fast in-memory guard and disk slot are keyed by a bounded SHA-256 digest of the directory's stable local filesystem identity (`stat` device plus inode/file ID). Relative and symlink aliases collide, and renaming the directory does not change writer ownership. The first pool member acquires and durably marks the package-owned cross-process lease before any member may spawn; concurrent members wait for that same preparation. The lease remains held until the last member confirms backend cleanup. Read-only runs never canonicalize for or join a pool, and every supported writer closes after reporting.

A writer without `writes` owns the whole cwd exclusively. A writer with `writes` owns normalized exact workspace-relative paths in the session registry, and admission rejects case-insensitive overlap with active members and start reservations. Dynamic grants and revocations use the parent-only `subagent_claims` tool while the worker is blocked on a parent claim question with no other active tool. A confirmed paused violation offender is also eligible while its pool admission is paused, its run ID remains in the pool's offender set, and it has no active tool. Ordinary paused writers and non-offending peers are not eligible. The run view and persisted tool card mark only current offenders; the write audit remains historical. Peers may announce contracts, but only the parent changes claims. Absolute paths and the case-insensitive outside-workspace audit marker remain ungrantable.

An observed out-of-claim native file-tool call pauses new writer admission and starts owner-scoped containment in one uninterruptible orchestration step. A running backend is interrupted only when it supports both interruption and resume. Starting or non-resumable active backends stop instead. Any interrupt failure or uncertainty falls back to normal stop, and orchestration logs only when that stop also fails. Admission remains closed until the parent reviews the audit and containment state. For a resumable paused offender, the parent may grant intended safe claims, reopen admission, resume with the authoritative claims, and await again. An outside-workspace write or non-resumable offender requires confirmed stop cleanup, explicit admission reopening, and a corrected replacement. A likely mutating Bash command increments a bounded heuristic-notice count in the write audit but does not create a sticky run warning or trigger interruption.

Per-file claims are cooperative, not filesystem isolation. Claim comparison is lexical after NFC normalization and conservative case-folding; it does not prove that two in-workspace symlink or hard-link paths reference different files. Native edit, write, and Bash remain unchanged and can physically modify the whole assigned cwd. Observation is asynchronous and post-hoc, so a violating mutation may land before interruption; the extension never rolls it back automatically. A violation pause survives final-member cleanup as a resource-free session tombstone, so releasing the lease does not silently reopen admission; the parent can resume it by referencing the historical offending run. Unconfirmed process or lease cleanup quarantines the entire cwd pool because the surviving process cannot be confined to its declared claims.

Writer leases use pi-cosmic-core's `CrossProcessLock` (see its ARCHITECTURE.md) under the caller-owned private root `<agent-dir>/subagents/writer-leases-v3`, with the filesystem-identity digest as the namespace. Core owns the owner evidence, durable commits, dead-owner retirement, and no-follow validation; neither the slot name nor its evidence exposes the cwd path or unhashed filesystem identity. `acquire` makes one non-waiting `tryAcquire`: a live owner is a `live` conflict, and core `recovery-required` (a dead native-pending owner, corrupt evidence, or an unsafe root mode, which is rejected rather than repaired) is a `recovery-required` conflict. `markSpawnStarted` commits core `mutationStarted` before any driver call, so parent death afterward requires manual recovery instead of reclaim: detached local process groups may survive their parent. The refusal names the slot's lock directory; recover it only after independently verifying that the external backend and descendants are dead (its `owner.json` names the owner's process id), then remove that directory. Release from `spawn-started` first commits `mutationSettled`. Leases are opaque: a module-private table keyed by the lease object holds the core handle and a shared phase, and every mark, settle, or release sets that phase to `uncertain` until the core commit returns. Any failure therefore keeps the slot held and quarantines the pool until restart, and an unknown or already released lease fails closed. Coordination assumes same-host parent Pi processes share one agent directory on a local filesystem with stable device/inode identity; distinct agent homes and remote filesystems are outside it.

Backend scopes are service-owned and explicitly closed before pool membership is detached. Stop and shutdown also wait for every admitted backend spawn attempt to settle before closing its scope, so a spawn cannot acquire into a closed scope after writer ownership is released. Non-final members detach only after confirmed cleanup; the final member alone authorizes lease release. If any backend cleanup fails, that member remains attached and release is never authorized. If lease release cannot be confirmed, the whole pool remains quarantined and retains process capacity and writer ownership. An explicit pool `pending`/`preparing`/`held`/`failed`/`releasing`/`quarantined` state plus one shared Deferred lets shutdown distinguish interruptible pre-ownership acquisition, attached waiters, and a narrow ownership commit already in progress. `acquireRelease` preserves an uninterruptible acquired-value/finalizer handoff while the lease boundary restores interruption only for its asynchronous pre-ownership checks; the core acquire, mark, settle, and release commits are short synchronous steps that remain indivisible and fail closed. Session shutdown applies spawn-settlement → backend cleanup → lease ordering to every owned run.

## Private state housekeeping

Local Pi run directories (`<agent-dir>/subagents/<session>/<run>-<runtime suffix>`), local CLI harnesses (`local-cli-v1`, `native-model-catalog-v1`; a Codex harness holds a copied `auth.json`), and supervisor channel state (`supervisor-channels-v3`) each carry an `owner.json` naming the root Pi process and its start identity. Normal cleanup removes them; a crashed or killed root leaves them behind. Each root session start therefore sweeps them in the background (`src/boundary/private-state.ts`): an entry goes as soon as its owner is provably dead (absent PID, or a reused PID with a different start time), and an entry without a provably live owner goes once nothing in it changed for seven days. Removal renames the entry to a `.swept-` tombstone first, so a concurrent Pi never reads a half-deleted directory and the next sweep finishes an interrupted deletion; any entry failure is skipped. Because a Codex writer may write the private temp directory in its harness, harness cleanup and the sweep restore owner access to any directory the child left unwritable or unsearchable when a first removal attempt fails. The runtime suffix keeps a resumed session's run ids, which restart in every process, from reusing an earlier process's directory. The sweep never touches reports (pruned separately), writer leases, debug ledgers, writer workspaces, or directories it does not recognize; nested Pi children never sweep.

## Supervisor channel and completion ownership

The local native supervisor channel is composed once with the shared backend registry. Local Claude/Codex acquire one authenticated channel inside each backend scope. Local Pi uses its separate RPC/IPC parent-contact transport.

Local Pi retains bounded, sanitized text, stop reason, and error evidence for only the latest assistant attempt in the current assignment. Assignment start, low-level retry start, and assistant message start invalidate older evidence. Only `agent_settled`, after retries and queued continuations finish, decides the outcome. A successful `stop` with nonempty final text completes; provider errors, unrequested aborts, output limits, tool-use-only endings, and missing or empty reports fail without incrementing accepted report generation. Before that, the child bridge gives a final message without text one hidden reminder per prompt to write its report; a second empty ending still fails, and earlier assistant messages are never promoted to the report. Buffered settlement carries the same evidence through prompt admission. Parent stop, correlated pause, and an accepted explicit report take precedence. These failures can leave completed writes behind; continuation remains an explicit frozen-route retry after confirmed cleanup, never automatic replay. Local Claude/Codex completion is owned exclusively by a supervisor MCP report; raw final CLI text and normal native turn/result completion do not settle the assignment. SupervisorChannel records exact accepted-report epoch evidence before acknowledging the MCP call. Claude successful assignment results and Codex normal `turn/completed` both query that exact epoch evidence directly, independent of adapter queue scheduling, so an accepted report wins behind progress/backpressure and a missing or wrong-epoch report is decided by protocol causality rather than by hanging or a scheduling sleep. The first assignment turn that ends without an accepted report gets one automatic follow-up input, a fixed reminder to call the report tool; Claude and Codex are idle once a turn ends, so it starts another turn in the same assignment, without a new `run_started`, whose own end is checked the same way. A second miss, or a reminder that cannot be sent, fails the assignment with the latest turn's final assistant text (Claude's result text, Codex's latest agent message), bounded to 2,000 characters in the same shape as the local Pi partial-output failure; earlier messages are never substituted. If native transport closes before the supervisor-event forwarding fiber drains, the adapter reprojects that exact accepted evidence into its backend queue before ending it. Claude's epoch-zero native initialization result remains non-assignment evidence. Claude and Codex interruption retain their separate correlated native lifecycles and emit no completion-shaped run event. Every local candidate has `closeOnReport: true`, so accepted report completion closes process and channel scope immediately while retaining bounded projection data. No report or harness artifact is written into the project.

The backend-neutral report event is bounded and correlated by run plus assignment epoch. An adapter supplies a positive monotonic per-run sequence, a bounded retry identity (`deliveryId`), and optional opaque ownership evidence. Phase, epoch, sequence, and delivery identity are validated in one serialized commit; the watermark advances only with a committed report. Exact `(sequence, deliveryId)` retries are idempotent. Higher reports while idle are rejected without advancing the watermark, so a valid later assignment can reuse that unpoisoned delivery. Future adapters decode their foreign protocol before emitting this event.

The Effect platform split is deliberate. Ordinary supervisor networking, framing, request correlation, interruption, and scope ownership use unstable Effect Socket and RPC APIs pinned by the workspace. Security-sensitive configuration reads and state cleanup retain the Node boundary because Effect FileSystem has no `lstat` or `O_NOFOLLOW` equivalent. Foreign MCP/Codex JSON-RPC stdio uses the shared byte-bounded parser because `Stream.splitLines` does not impose a maximum incomplete-line or aggregate queued-byte bound. The standalone supervisor helper uses that parser too, preserves CRLF and final unterminated frames, and writes a bounded invalid-request response before closing overflowed stdin; validated frames then feed Effect queues or RPC clients. A tool call's interruptible RPC operation returns response data without touching stdout. Its `Exit` selects success, failure, or cancellation, then one uninterruptible serialized-writer commit publishes and acknowledges exactly one frame. Writer close still runs before active-call and socket interruption. The import-free `supervisor/mcp-contract.ts` is the sole owner of MCP registration, tool names, snake_case argument keys, nonblank/delivery patterns, and the 16,384/32,768/256 character bounds. The patterns are enforced when decoding calls and are not advertised in the MCP input schemas, which some providers reject. The helper serverInfo name `pi-subagents-supervisor`, backend report limits, parent reply bound, transport framing/call limits, and concurrency caps are separate identities.

`supervisor-channel.ts` owns resource acquisition and cleanup; `supervisor-channel-session.ts` owns one session's controls and shutdown over private per-session state in `supervisor-channel-state.ts` (authenticated peers, readiness, assignments, questions, reports, and acknowledgements); `supervisor-channel-handlers.ts` implements that session's RPC handlers, and `supervisor-channel-errors.ts` holds its typed errors. Logical shutdown revokes admission and settles correlations before the resource owner closes the server scope and removes private state. One scoped `SupervisorChannel` binds only IPv4 loopback on an ephemeral TCP port and writes one 0600 connection document below a unique 0700 run directory in private agent state. Open uses staged Effect acquisition for the run directory, Effect NodeSocketServer listener, private config, and Effect RPC v3 server. Validation and listener setup remain interruptible; the private config writer is one bounded uninterruptible commit followed by an explicit interruption checkpoint, so cleanup never races an unsettled file handle and still removes every acquired stage before publication. The handle exposes no close: its one release runs exactly once and uninterruptibly, from partial cleanup during masked acquisition or from the owning scope's release, and it shuts peer sockets and the server scope before removing private state. Each connection has an Effect-owned authentication deadline that ends on authentication, detachment, or channel disposal. A 256-bit token authenticates every RPC request through native HMAC verification with a private non-extractable key. Authentication publication rechecks session and connection closure after verification; peers are loopback-checked and capped, Effect RPC schemas decode every payload/result/error, and NDJSON framing, queues, maps, calls, and strings are bounded. `supervisor-rpc-serialization.ts` keeps the Effect codec/encoder but owns strict bounded frame decoding, so malformed JSON closes the peer instead of being silently skipped. Event admission reserves cancellation capacity for the pending question and every admitted proxy RPC. Proxy acquisition and release keep each reservation owned through its interruptible response wait; cancellation publishes without waiting for consumers to drain the queue. Assignment updates use a server stream plus explicit adoption RPC, blocking questions use transport interruption plus explicit reply confirmation, and report delivery remains idempotent by bounded delivery identity. The erasable-TypeScript helper retains only the external MCP JSON-RPC stdio adapter over the shared supervisor client. Its minimal `.mjs` launcher uses the package-owned Jiti dependency so the same typed source runs from installed `node_modules`, where Node's native type stripping is intentionally disabled. Metadata contains only that fixed packaged helper command, private config path, and Claude JSON/Codex TOML MCP fragments, with no public profile fields, arbitrary command, user configuration, credentials, or environment.

## Local Claude

Local Claude starts only `claude --print --input-format stream-json --output-format stream-json --verbose --forward-subagent-text` with partial/replayed messages, an empty fixed settings-source list, strict MCP, explicit model/effort, no session persistence, and no slash commands or plugin arguments. The subagent prompt is appended with `--append-system-prompt-file`, so children keep Claude Code's native system prompt. Its generated settings refuse cross-session input because these headless children use the private supervisor channel for parent contact and cannot review an inbound-message prompt. Every launch requires current strict sandbox settings: enabled, failure when unavailable, no unsandboxed command fallback, strict empty network allowlist, and assigned-cwd filesystem write policy. Read-only exposes Bash for inspection/validation through sandbox-only auto-allow while excluding Edit, Write, and NotebookEdit and explicitly denying Bash writes to the assigned cwd. Writers expose the same sandboxed Bash and Edit through one canonical-cwd-scoped permission rule; bare Bash/Edit/Write are never permission grants. Unsupported Bash-sandbox platforms and writer path policies fail typed preflight. The subprocess sandbox directly confines Bash and keeps the shared `/tmp` and the parent's `$TMPDIR` read-only, but Claude Code points Bash's `$TMPDIR` at its own per-user temp directory and keeps that writable for read-only and writer children alike (`/tmp/claude-<uid>`, observed with 2.1.300), and that directory is shared with the user's other Claude Code sessions. Edit remains the current CLI's path/symlink-enforced file-tool permission policy rather than an OS sandbox, and Web/model traffic is not an offline/confidentiality boundary. `Agent`, `Task`, `TaskOutput`, `TaskStop`, and `SendMessage` are allowed. Their work inherits this parent policy and lease, remains inside the Claude process tree, and updates only the parent run's bounded native activity summary.

Claude startup sends the official initialize control, then one `shouldQuery:false` input to obtain native `system/init` without inference. It validates cwd, native session, selected/resolved model, MCP config errors, and a connected `pi_subagents_supervisor` inventory containing all four mandatory tools before returning startup state. Every outbound stream input carries a fresh UUID; acknowledgement requires the native replay of exactly that UUID from the active session, with no text matching. A delayed or duplicate replay of a bounded set of already-confirmed UUIDs is acknowledged silently only from that same session. User frames with a non-null `parent_tool_use_id` belong to native-agent forwarding rather than top-level stream-input replay. Their text becomes assignment activity, while forwarded tool results retain the nested tool lifecycle used by write-claim observation. Claude-owned, synthetic, unqualified `task-notification` and `auto-continuation` messages own one subturn/result inside the active assignment; a private identity and the result FIFO cover older frames that omit their UUID. Claude also replays each non-meta `<task-notification>…</task-notification>` command it drains from its own queue into a running turn, or folds into a merged turn, as `isReplay` with a fresh UUID and no synthetic flag; a background `Bash` or agent completion inside the subagent produces one mid-assignment. Current Claude labels that replay with the unqualified `task-notification` origin it derives only for its own task-notification commands, while 2.1.259 omitted the origin. The adapter accepts either form only as the complete same-session, active-assignment, text-only envelope with no parent, subkind, tool result, meta, compact-summary, or previously owned UUID evidence, and repeats of an owned UUID are suppressed. The labelled form is accepted while guidance is pending, because adapter stream input never carries an origin and confirms only by exact UUID; the unlabelled form stays fail closed then. A replay drained into a running turn owns no result, so result-window overflow evicts the oldest synthetic expectation before any adapter-owned one. The tag and origin identify a Claude-owned notification class but never confirm adapter input. Near misses, qualified task-notification subkinds, channel/peer origins, non-synthetic auto-continuations, and cross-session delivery remain foreign and fail closed.

Claude Code 2.1 ends a turn while background agents or shells run and starts a new turn when their completion notification arrives; it no longer offers `TaskOutput`. The adapter tracks `system/background_tasks_changed` and top-level `system/task_notification`. An assignment turn that ends without an accepted report waits for that continuation while background tasks run or a notification arrived since the last result; with nothing running it gives the continuation 20 seconds to start, then takes the usual missing-report path. While a continuation is awaited, the next same-session result is that continuation even when Claude correlates it to no issued input, and its report is checked then. After an assignment settles, a notification-driven turn only contributes usage. Synthetic `peer` turns, which carry messages Claude's own native agents send the main session, count as internal like task notifications; cross-session input stays refused.

An unexplained top-level replay before report acceptance remains a protocol error. A content digest can classify it against the bounded confirmed-input window for diagnostics, but neither content equality nor a matching UUID from another native session authorizes the frame. When the supervisor already holds the exact active assignment's accepted report, a trailing unexplained replay instead emits a bounded warning and reprojects that report so normal close-on-report settlement preserves completed work. The warning includes only sequence, booleans, finite content/session/origin classes, a length bucket, a recognized leading-tag class, outbound-age bucket, pending operation, report state, and trace state. It never contains message text, digests, UUIDs, session IDs, parent tool IDs, tool payloads, or report text.

`PI_SUBAGENTS_CLAUDE_DEBUG=1` enables a metadata-only tail ledger owned by `boundary/local-claude-debug.ts`; the gate is consumed by the adapter and is not forwarded to Claude. Each nonempty completed scope writes at most 512 entries and 64 KiB to a 0600 `replay-ledger.ndjson` inside a unique 0700 directory below `<agent-dir>/subagents/local-claude-debug-v1/`. The boundary retains at most eight package-owned directories, including pruning incomplete crash remnants, under one process-local commit lock. It hashes the run identity used in the directory name and stores no raw prompt/result text, native IDs, paths, foreign frames, tool arguments, or provider debug output. Diagnostic write or cleanup failure cannot change run behavior. The adapter deliberately does not enable Claude's raw `--debug-file`, whose content and size are outside this privacy contract. For an explicit live reproduction that may incur provider usage, set `PI_SUBAGENTS_REAL_CLAUDE_MODEL` and run `pnpm --filter pi-subagents smoke:local-claude-replay`; the gated scenario requests native `Agent`, `SendMessage`, and `TaskOutput` activity before supervisor report submission, and the installed `claude` executable determines the version under test.

Steering separates its ten-second caller wait from backend-owned delivery. Caller timeout returns `steer_outcome_uncertain` with the typed `pendingDelivery` flag, without terminating Claude or clearing the pending UUID; cancellation after handoff likewise leaves delivery owned. `subagent_send` reports that result as guidance awaiting confirmation, not as a tool error or a delivered message ([Tool result certainty](completion-delivery.md#tool-result-certainty)); unflagged steering uncertainty remains an unconfirmed error. While unresolved, additional stream inputs and queue-cancelling interruption are rejected; stop remains available. Only an exact same-session replay confirms guidance, and a private monotonic sequence prevents stale same-assignment events from resolving newer input. An absolute five-minute watchdog, measured from delivery ownership and never extended by activity, checks exact-epoch accepted-report evidence before closing admission and terminating an unresolved backend. This is a bounded-liveness policy, not proof that Claude is unhealthy. Initialization and start keep fail-closed deadlines of sixty seconds, allowing concurrent agent startup, and native transport-write uncertainty still closes the backend rather than entering the delayed-replay path. Nothing resends input automatically.

Accepted supervisor reports take precedence over unconfirmed guidance, including delayed report forwarding, native transport closure, and a correlated native assignment error after report acceptance. Completion then retains `report-unconfirmed`: the assignment completed, but guidance incorporation is unknown. Failed/stopped runs with pending guidance retain `unresolved`; retry admission and retry hints consult this fact independently of initial-assignment uncertainty. Primary typed backend failures survive exit rather than becoming a generic process-exited error; public text remains redacted and bounded. A failure snapshot records delivery ownership duration, last inbound category/age, active tool categories/count, an optional validated CLI release version, and termination reason. It contains no raw input, native identifiers, paths, tool arguments, or digests. Process termination is not cleanup proof; the existing scope/lease cleanup barrier remains authoritative.

### Live steering timing probe

The opt-in probe can incur provider usage; its 120-second execution bound is not a spending limit. Capture `claude --version`, then run one scenario without automatic retries:

```bash
PI_SUBAGENTS_REAL_CLAUDE_MODEL='<native model selector>' \
PI_SUBAGENTS_REAL_CLAUDE_STEERING_SCENARIO=generation \
pnpm --filter pi-subagents smoke:local-claude-steering
```

Scenarios are `tool` (default, foreground `sleep 25`), `generation`, and `native-agent`. The probe sends one guidance input after observed activity and drains backend events concurrently. It logs bounded metadata, distinguishes confirmed/late replay from completed-with-unconfirmed-guidance, and reports missing requested activity as inconclusive rather than successful. Read-only sandbox restrictions are unchanged; unavailable or refused tools can make a scenario inconclusive.

On 2026-09-26 with Claude 2.1.283 and `claude-opus-5-5`, the generation probe returned pending uncertainty after 10.003 seconds, then received the accepted assignment report about 2.138 seconds later without a guidance replay. This demonstrates why a ten-second replay miss is not proof of a failed worker; it does not establish the CLI's internal scheduling cause. The tool probe's sleep failed immediately and the native-agent probe did not invoke Agent, so neither established timing for those cases.

### Native results and interruption

Native results correlate to their originating input by `user_message_uuid` when reported, otherwise by the adapter-owned issue-order FIFO; the correlated initialization-probe result is a nonfatal artifact independent of any assignment epoch, eliminating the initialization/assignment race. Cumulative assistant usage repeated for the same native message id is deduplicated by nonnegative deltas under a total-token definition that includes cache-read/cache-write tokens. Each result carries the process's running totals so far: `modelUsage`, summed across models, which unlike the main-loop-only per-turn `usage` includes native agents and compaction, and the `total_cost_usd` estimate. A result contributes only the increase over what the process has already counted, so a child that produces several results (background-task continuations, absorbed notification turns, guidance or report-reminder turns) is charged its latest total once rather than the sum of its results. Zeroed crash/startup-error results never lower either watermark, and a regressing nonzero total warns rather than subtracts. Ordinary accepted supervisor reports are buffered for a ten-second bounded native-result-or-exit grace so usage/cost enters the backend event queue before report settlement closes the process scope; timeout or transport exit flushes the accepted report so missing telemetry cannot hang completion. The exceptional trailing-unknown-replay path bypasses that grace because preserving accepted completion and closing the unexplained-input process take priority over optional trailing telemetry. Initialization failure is post-spawn and never candidate fallback. Interrupt sends `cancel_queued:true` and remains correlated to its assignment until the control response, exact replayed marker, and exact `error_during_execution`/`aborted_streaming` result all arrive in either order; only that lifecycle is suppressed, while genuine result failures remain fatal. If the public interrupt times out uncertainly, the lifecycle stays exactly owned — a second interrupt is rejected as ambiguous — and a late marker+result pair settles the assignment through `run_settled` so orchestration pauses instead of failing; transport closure is the safe boundary that clears lingering ownership.

## Local Codex

Local Codex starts only `codex app-server --stdio --strict-config` against an isolated 0700 `CODEX_HOME`. The private configuration enables `[agents]` and `multi_agent` under Codex's runtime limits. Harness creation is failure-atomic after its unique private directory exists, and unconfirmable partial cleanup returns `harness_cleanup_unconfirmed` while preserving private fail-closed state. No other credential/environment keys cross. `thread/start` passes the subagent prompt as `developerInstructions`, keeping Codex's model-specific base instructions. `thread/start` and `turn/start` omit `environments` so Codex uses its default local environment; an empty list disables shell and file access. Generated config includes only the private supervisor MCP server, enables native agents, and disables apps, plugins, hooks, skills discovery, memories, browser/computer/image, web-search, network, and related extras. The accepted 0.145 generated v2 subset is `initialize`, `thread/start`, `turn/start`, `turn/steer`, `turn/interrupt`, their correlated responses, and bounded relevant turn/item/usage/warning notifications. Only known executable item types (`commandExecution`, `fileChange`, `mcpToolCall`, `webSearch`) own a `tool_started`/`tool_finished` lifecycle; bounded `fileChange` entries preserve every source path and update move destination for claim observation, and a claimed writer's recognized file mutation without an established path fails closed as a violation; `agentMessage`, `reasoning`, and unknown future informational items surface as activity or are acknowledged without fabricating tool entries, while `collabAgentToolCall` and `subAgentActivity` items update native activity. Those items only feed the activity projection, so added fields are ignored and a tool, status, or kind outside the generated subset counts as plain activity; an item without an id still fails the protocol. Approval is `never`; native sandbox policy is read-only or workspace-write with network disabled. Read-only children keep the read-only policy, so they cannot write it either. Server-initiated approval or other requests are protocol violations. An interrupt that times out uncertainly retains its exact turn/epoch lifecycle — a second interrupt is rejected as ambiguous — and a late matching interrupted turn completion settles through `run_settled` as a pause rather than a protocol error. Static current Codex effort policy permits only minimal/low/medium/high/xhigh/max because the generated effort schema itself is open string. `thread/tokenUsage/updated` carries only its own thread's running total, and native sub-agents run in threads of their own that the main thread's total excludes (observed with 0.162.1), so the adapter keeps a nonnegative running-total watermark per thread, for at most 64 threads, and adds each thread's increase whatever its turn. Every thread in the private app-server belongs to the child. Codex reports no client-side cost, so its usage cost remains unknown rather than a known `$0`.

### Live sandbox canaries

Opt-in canaries check that the installed Claude and Codex CLIs still enforce the generated sandbox and permission policy. They can incur provider usage:

```bash
PI_SUBAGENTS_REAL_CLAUDE_MODEL='<native model selector>' pnpm --filter pi-subagents smoke:local-claude-sandbox
PI_SUBAGENTS_REAL_CODEX_MODEL='<native model selector>' pnpm --filter pi-subagents smoke:local-codex-sandbox
```

Each runtime launches a read-only child and a writer child in a fresh `workspace` directory with an `outside` sibling, both under the package's `node_modules/.cache` so the cwd checks stay independent of the temp-directory checks. The child attempts Bash redirects inside and outside its cwd, into `/tmp`, and into the parent's `$TMPDIR` (captured before the child environment is built); a Codex child also writes through its own `$TMPDIR`, its private temp directory. It then attempts a file-tool edit inside and outside its cwd and reports each outcome. Read-only children must leave every canary unchanged; writers may change only the files inside their cwd and private temp directory and must succeed there. A canary written where it should be blocked is a security failure. A run without evidence of every attempt is inconclusive. Codex 0.162 app-server emits no item notifications for sandbox-denied commands or patches, so those attempts never reach the tool lifecycle or claim observation, and the canary relies on the child's report for them.

## Module responsibilities

Detailed responsibilities of the source files owning the behavior above:

- `src/backend/model.ts` — capability-oriented driver plus normalized readiness preflight, launch/event/handle/control, startup, bounded report-generation, and exit contracts for `local` × `pi|claude|codex` combinations.
- `src/backend/service.ts` and `src/layer.ts` — one shared backend registry, fail-before-ownership readiness resolution, and ordered composition of the three local drivers. The composition root reuses one constructed backend Layer for service provision and its final merge so Layer memoization shares the registry.
- `src/backend/local-pi.ts`, `local-pi-rpc.ts`, `local-pi-events.ts`, and `local-pi-protocol.ts` — the Pi handle (assignment epoch, usage, and controls), command-checked native RPC and correlated descendant-notification acknowledgment, normalized runtime events and typed parent-contact mapping, and the single pure Effect Schema definition for native RPC plus both IPC directions.
- `src/backend/local-cli-events.ts` — shared raw wire-event ownership for local Pi, Claude, and Codex: when one raw frame produces one or more normalized events, its transport ownership and byte budget stay attached through the final queued event until orchestration consumes it; adapter-internal events carry no raw owner, and a failed owning enqueue acknowledges the raw frame immediately. Each driver allocates this bounded ingress in its scope, which releases every still-owned raw frame and ends the queue on close.
- `src/backend/local-cli-interruption.ts` owns the exactly-owned Claude/Codex interrupt lifecycle: one pending interrupt, its bounded wait for the correlated response and native terminal evidence, and late settlement through `run_settled`. Its pure Exit classifier retains ownership for interruption-only causes and typed `interrupt_outcome_uncertain` failures; success, definite failure, and defects release it. Each adapter owns only its correlated response and the native evidence that completes the lifecycle.
- `src/backend/local-cli-driver.ts` is the shared Claude/Codex driver: supervisor-channel and process acquisition, the fixed supervisor-report instructions, scope-owned final report transfer that ends the event queue after enqueue or shutdown interruption without a lossy timeout, the supervisor reply, and refusal of the rename and peer-notice capabilities neither runtime advertises. When a CLI's output ends, the driver waits interruptibly for the exit receipt, which the transport has already settled, and fails pending initialization, requests, and input with the exit status on the first line followed by the end of the CLI's bounded, sanitized stderr, so a rejected flag or configuration reaches the failed launch and the run's exit diagnostic; scope teardown keeps the immediate generic closure and never waits.
- `src/backend/local-claude.ts`, `local-claude-protocol.ts`, and `local-claude-correlation.ts` — current Claude stream-JSON initialization/native-init/MCP inventory validation, same-session UUID-correlated replay/result confirmation, privacy-projected replay classification, exact-epoch accepted-report preservation, per-message-id usage deduplication with result-level usage/cost reconciliation, exact interrupt-marker/result lifecycle ownership (including late settlement after the public timeout), and MCP report ownership. `local-claude-correlation.ts` isolates separate bounded adapter-sent and Claude-internal UUID windows, sent-content classification, and the result-expectation map/FIFO, including synthetic-origin selection that cannot consume ordinary UUID-less results; `local-claude-report-delivery.ts` owns accepted-report buffering, the scoped ten-second grace, single-flight forwarding, and duplicate suppression. `local-claude-usage.ts` owns the pure usage arithmetic, the bounded assistant-message history, and the per-process token and cost watermarks, returning deltas and regression flags without emitting events. The handle retains telemetry-before-report ordering, transport-close recovery, interrupts, and the assignment epoch, sharing its state through `local-claude-context.ts`; `local-claude-user-events.ts` classifies user frames, `local-claude-results.ts` owns result usage reconciliation and report acceptance checks, and `local-claude-control.ts` owns control responses and initialization.
- `src/backend/local-claude-input-delivery.ts` keeps preparation caller-owned, then transfers native send and UUID acknowledgement into the backend scope.
  Exact replay resolves ownership, and accepted reports complete without claiming guidance incorporation.
  Caller cancellation cannot erase sent-input correlation, and closed backends reject new input.
- `src/backend/local-claude-diagnostics.ts` retains only bounded timing, frame and tool categories, a validated release version, and the termination reason.
- `src/backend/local-codex.ts` and `local-codex-protocol.ts` — generated Codex 0.145 app-server v2 JSON-RPC request/notification subset with native sub-agent items from the 0.162.1 schema, authenticated helper-readiness gating, dual-evidence interruption, fail-closed unowned interruption, causal report-completion checks, current warning variants, usage/tool normalization, and MCP report ownership.
- `src/backend/claude-policy.ts` — pure foreign Claude CLI policy shared by local harnesses: the scoped-Edit cwd rule grammar/types, fixed inspection, native-agent, and denied tool constants, the strict sandbox settings builder, allowed-tool logic (including the native-agent controls), and the local Claude argv. It imports no Effect and no Node APIs; callers pass the boundary-prevalidated writer cwd policy in.
- `src/boundary/child-process.ts` owns local Pi fresh/fork setup, launch-time trusted-tool activation, private run-directory ownership and reclamation, cooperative abort, and typed IPC attachment before spawn readiness. Pi passes oversized-line summaries and parser overflow to its backend and retains its existing outbound frame policy.
- `src/boundary/local-pi-ipc.ts` — the sole parent/child raw Node IPC adapter. It validates both wire directions, bounds send callbacks, preserves definite-versus-uncertain delivery evidence, reports malformed child contacts, and detaches message/disconnect listeners idempotently.
- `src/boundary/local-cli-harness.ts` — private local CLI harness/auth/config filesystem lifecycle: the absolute-path decision (`node:path`) that precedes the pure Claude cwd/scoped-Edit rule, launch and catalog harness roots, sanitized environment and approved API-key selection, the Codex run's private temp directory and temp variables, Codex config builders, failure-atomic Effect acquisition/removal with custom-source Codex auth-copy ownership, and cancelable bounded auth probes without an internal Effect runner. It owns no wire transport and never imports the `LocalCliProcess` service.
- `src/boundary/process-transport.ts` is the private local JSONL process owner for local Pi, Claude, and Codex, with bounded stdout/stderr and event byte budgets, `oversized_line` summaries for lines past the limit, spawn readiness, exact listener cleanup, frame writes, `awaitExit`, and fail-closed process-tree release. Acquisition is scoped: spawn through release-finalizer registration stays masked, so closing the caller's scope always releases a process that exists, and overflow-forced termination runs as a fiber of that scope rather than a detached daemon. `src/boundary/process-tree.ts` owns child-based policy over pi-cosmic-core's `signalProcessGroup`: pid-less children require no signal, and a failed group signal may fall back to a live leader. Cleanup always confirms process-group absence before releasing ownership. Pi's bash tool runs each command in its own process group, which dies only through a tool abort or Pi's SIGTERM/SIGHUP handler, so overflow-forced termination also sends SIGTERM and allows two seconds before SIGKILL. For writers, the transport also snapshots (`ps`, best effort) the process groups that the child's group members started outside it before any signal, because those processes are reparented once the child dies; release stays `cleanup_unconfirmed` while any recorded group survives. A child that exits on its own before release leaves no snapshot.
- `src/boundary/local-cli-transport.ts` keeps native transport contracts, fixed spawn inputs, outbound frame limits, and immediate termination when the parser's queued-byte budget overflows. Native release sends no cooperative protocol abort. Harness acquisition and transport-before-harness finalizer ordering remain in `local-cli-process.ts`.
- `src/boundary/local-cli-process.ts` — the reduced `LocalCliRuntime`/request/service door: preflight and probe orchestration, including the per-session CLI version cache and minimum-version gate, plus `makeLocalCliProcess`, the optional Claude diagnostic recorder attachment, and the stable Context.Service/Layer composition over the harness and transport boundaries; it re-exports none of their symbols. `src/backend/local-cli-version.ts` holds the pure version policy: CLI labels, minimums, parsing, and classification.
- `src/boundary/local-claude-debug.ts` — the opt-in metadata-only replay ledger, including its exact environment gate, in-memory tail bound, private scope-finalized filesystem publication, process-local retention commit, and best-effort failure isolation. It never owns correlation or enables Claude's raw debug-file output.
- `src/boundary/writer-lease.ts` — package-local adapter over pi-cosmic-core's `CrossProcessLock`: canonical launch paths plus stable device/inode directory identity, the per-agent-directory v3 lock root, opaque lease phases that fail closed, and typed conflict and commit errors. `src/run/writer-pool.ts`, `admission.ts`, and `record-cleanup.ts` own session pool membership, disjoint-claim admission, first-acquire/last-release ordering, and whole-pool quarantine.
- `src/supervisor/mcp-contract.ts`, `src/supervisor/tool-call.ts`, and `src/boundary/supervisor-channel.ts`, `supervisor-rpc-protocol.ts`, `supervisor-client.ts`, `supervisor-mcp-helper.mjs`, and `supervisor-mcp-helper.ts` — one import-free MCP semantic contract, backend-neutral Effect RPC v3 over scoped loopback Effect sockets, the one scoped supervisor RPC client and tool dispatch, and the packaged erasable-TypeScript MCP stdio adapter consumed by local Claude/Codex. The boundary returns adapter-owned connection and fixed MCP metadata; it is not registered as a public Pi tool.
