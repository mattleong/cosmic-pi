# Completion, projection, and delivery

Part of the [pi-subagents](../README.md) architecture documentation. See [ARCHITECTURE.md](../ARCHITECTURE.md) for the ownership map and cross-cutting invariants.

## Assignment epochs, questions, and phases

Assignment epochs are prepared monotonically before task issue, advance only after at least one current live authenticated helper acknowledges them, and become unready on disconnect until a new peer handshakes. Helper calls capture the observed epoch, so delayed prior-assignment events retain their old epoch. Progress and warning/question calls normalize to existing `supervisor_contact` events; warnings update parent-visible projection/session history without injecting a standalone model message, while the latest child warning and latest system warning are preserved separately and folded together into the terminal outcome. Questions remain immediate generation-aware parent actions, and child instructions escalate risks that could invalidate current parent work into questions. The channel assigns report sequence and current captured epoch before emitting existing `BackendReport` data. Report `deliveryId` retries with identical text return the original sequence without a second event, while conflicting reuse fails. Only one question may be used per assignment and only one may block per run at a time; parent reply, MCP cancellation, socket loss, adapter cancellation, and scope close settle the exact owned correlation. Every definite question-death path emits a bounded epoch/request-correlated cancellation event so orchestration clears `waiting_for_parent` instead of retaining a dead question. The channel reserves queue capacity for that cancellation; ownership is not cleared unless the cancellation is queued. A parent reply timeout after transmission returns `reply_outcome_uncertain`, closes the exact question without retry, and retains a bounded system warning.

The standalone helper exposes only `supervisor_progress`, `supervisor_warning`, `supervisor_question`, and `supervisor_submit_report`. It dispatches up to 16 calls concurrently, so a blocked question does not block ping, progress, reports, cancellation, or unrelated responses. Tool execution returns response data and never writes stdout. Only the supervisor RPC operation is interruptible; its `Exit` selects success, failure, or cancellation, then one narrow uninterruptible writer commit publishes and acknowledges exactly one JSON-RPC frame. Cancellation after an RPC reply therefore cannot add a second frame while stdout is backpressured. Writer shutdown still precedes active-call and socket interruption. It never silently retries an uncertain send. Parent death closes TCP and fails pending calls.

Every assignment has a monotonic never-reused epoch and a `preparing`/`issuing`/`running`/`reported` phase. Assignment-scoped events from older epochs, plus activity/tool/progress/warning/question events while idle `reported`, are ignored; handle-scoped lifecycle warnings remain visible in projection and session history but never trigger a parent model turn. A report received while `controls.start` is in flight is held in one bounded slot and committed only after start confirmation (or correlated `run_started` evidence following an outcome-uncertain result). Definite retained-start failure restores the prior view, report/warning fields, active tools, and assignment state under the matching attempt token while preserving bounded warning notices observed during the failed attempt. Outcome uncertainty keeps the new assignment and warning. Start confirmation never overwrites an already committed fast report. Runs retain Deferreds only for initialization, cleanup, writer preparation, and a pending pause; assignment settlement has no unused Deferred.

## Retained runs and session shutdown

A `closeOnReport: false` run transitions from working to nonterminal `reported`, increments `reportGeneration`, retains its backend handle/PID, and counts as finished for the current `all_finished`/`any_finished` assignment. Guidance from `reported` uses the backend's assignment-start control on the same handle, clears the displayed prior report, and makes await target the next generation. Stop and session shutdown still close the scope. Service validation independently rejects retained writers and non-Herdr retained launches.

Session shutdown/replacement/tree navigation/reload closes all local children and exact session-owned Herdr topology, then tombstones safely releasable writer leases. Local Pi private run directories remain while a completed run is resumable; failed, stopped, evicted, and session-ended records reclaim them after process cleanup. A graceful shutdown is not crash recovery: parent death after `spawn-started` intentionally leaves a manual-recovery lock even after a surviving backend later exits. Leasing is owned above the six-driver registry, so every writer shares the same protocol without adapter-specific locking.

## Projection and delivery

UI and tool renderers consume immutable projections. All public tool calls use bounded user-facing action summaries; start calls keep tasks expanded-only and final start results render immutable launch receipts rather than live run snapshots. Receipt rows always retain profile plus actual selected/attempted route and model, or an explicit resolving/no-eligible-route state; outcome icons distinguish complete, mixed, and failed batches, fallback/failure details stay expanded-only, and a single `/subagents` hint hands successful starts to the live surface. Non-start/await results persist bounded semantic profile routes, run cards, and per-target failures instead of reparsing prose. Live cards expose run identity, profile/host/runtime/model route (using compact `model:effort ⚡` notation for fast models), write intent, retention, bounded timing/activity, humanized aggregate usage, state-aware recovery, and expanded provenance/capabilities. Usage cost is optional/unknown: only a backend-reported known cost renders (Pi RPC totals and Claude's `total_cost_usd` estimate are known; Codex and Herdr remain unknown), unknown or zero-information usage renders nothing — in cards and in the detailed status output, which omits its `Usage` field rather than printing `unknown` — sub-cent prices trim trailing zeros, and a fleet cost subtotal over runs with unknown costs is explicitly marked as a lower bound (`≥`). Compact card fallback preserves capability evidence, and renderers treat absent capabilities as unknown-neutral while an explicit lack of `resume` keeps cannot-resume guidance. `subagent_models` renders effective source, defaults, candidate eligibility, and the explicit launch-check boundary from flat structured candidate cards. Discovery persists the eight candidate policy fields plus `status` and `reason`, never the old prose candidate/order/effective-context representation. Its renderer reads those fields directly. Full, compact, and minimal projections retain all seven routes and all 32 candidates per route; minimal uses short bounded ASCII model/reason fallbacks and marks `contentOmitted`. Persisted details use strict version 2 from one Effect Schema model. Start details require the full request-ordered entry list and optional matching failures, and never contain run cards. Await details require cards and `awaitUntil`; each non-start action has its own discriminant. The public details door applies explicit privacy projections, strips unknown fields, rejects malformed known children without salvage, and selects among semantic full, report-free, compact, and minimal candidates. Both makers and decoders return deeply frozen values whose canonical JSON is at most 48,000 characters. Version-1 or unsupported history uses the existing bounded terminal-sanitized text fallback; no compatibility parser reconstructs cards. Await cards include only the latest report generation and preserve explicit truncation/omission evidence when reports cannot fit. Collapsed live results preview bounded first report lines; expanded live cards wrap diagnostics and render a preserved report and error independently, while no-report completion and recovered omitted output are explicit. Progressive batch starts remain input-ordered, render pending/started/failed receipt slots, count pending/failing launches, and animate only the launch header; settled start rows are immutable. Management banners count the true run total (`runCount`), and a result whose bounded card list omits runs adds an explicit cue to query specific run IDs with `subagent_status`. Send acknowledgements distinguish steering guidance from retained (`closeOnReport: false`) next assignments — retained targets are reported as having started their next assignment with `subagent_await` targeting the new report generation, and mixed sends render both. `reported` is rendered as an idle retained resource with explicit next-assignment guidance, rename, and stop controls rather than as a dead process. Interrupt-capable backends that do not advertise resume remain stoppable and present stop/replacement recovery instead of suggesting an unsupported resume. The fleet keeps message/resume/rename input and action errors inside its full-screen overlay, consumes stop confirmation modally, and uses capability-aware actions.

The service stores every committed run mutation as one complete immutable `{ revision, runs }` snapshot in a `SubscriptionRef` while still holding the shared run lock, then invokes the best-effort host publisher. List and projection read that immutable snapshot without taking the run lock. Await still captures its revision in the same locked state check, then subscribes for a snapshot with a strictly newer revision; replay closes the check-to-subscribe race, every wake rechecks authoritative run state, and interruption releases the stream subscription with the caller scope.

Each accepted report or terminal failure creates one internal unresolved outcome-generation record. Successful reports retain their final text; failures retain their bounded error; both snapshot a bounded fold of the latest child warning and latest system warning without adding warning ownership to completion claims. The per-record `completionGenerations` map is the sole payload and outbox. There is no pending-completion queue or second receipt index. `completionClaims` remains a separate map from generation to one exclusive opaque owner token, never a refcount. Await atomically claims the current generation when the assignment is finished or the next generation while working, so a claim may exist before its payload. A second await fails with typed `completion_claim_conflict`. Stopped records with a retained unresolved generation still return a receipt to its matching claim. Competing status observes bounded metadata with report text/assistant transcript redacted and receives no receipt. A receipt carries the owner token, and consumption removes only that exact payload and matching claim.

Report and terminal transitions build the payload, call the lock-required synchronous insertion, open the completion latch, resolve any pending pause, and publish projection before releasing the service lock. Retained post-lock work is limited to peer notice and returning the committed view. Claim release removes only its matching token and opens the same latch in that locked transition. The completion worker takes the completion gate before the run lock, closes the latch, scans run IDs and generations deterministically for unclaimed payloads, and selects at most 12. It releases the run lock but keeps the gate through synchronous host notification, then deletes only selected payload objects whose exact `(runId, generation)` key was acknowledged. Partial acknowledgement retries only the remainder. If any eligible payload remains, the worker reopens the latch before releasing the run lock; a quiescent eligible payload cannot be left behind a closed latch. Retry delay starts at 100 ms, resets after progress, and caps at 30 seconds.

The host notifier is stateless. It bounds, sanitizes, redacts, and chunks messages, returning exact successful completion keys; an accept-then-throw result remains uncertain and is retried by the service. Questions use a separate run-ID-keyed map and latch worker without the completion gate. Normal synchronous return accepts a question, and acknowledgement deletes only the exact attempted object so a replacement question survives an older delivery result. A definite failed outcome whose frozen route still has candidates includes one bounded `subagent_lifecycle` retry hint; outcome-uncertain or exhausted runs do not. The retry action itself waits for confirmed cleanup, creates a linked successor, and never changes completion ownership for the predecessor. A failure after retained report generation N allocates N+1, preventing key collisions; public `reportGeneration` still counts accepted reports only.

Resolved generation records are removed, while the immutable public projection retains only the latest bounded report, error, and warning for human UI. Retained next-assignment admission requires fewer than 63 unresolved generations. The 63rd retained report fills the normal report budget; another retained assignment fails with typed `report_delivery_backlog`, reserving generation 64 for a later terminal backend failure. Terminal settlement cannot create generation 65. Close-on-report resume paths retain their existing admission below the hard 64-generation bound. Total run history never exceeds 50 records: start admission first evicts the oldest terminal record with no unresolved/claimed outcome, process, or cleanup ownership, and otherwise fails with typed `history_outbox_capacity`. Eviction is a two-phase reclaim-before-admit transaction: one eligible candidate is exclusively claimed under the lock without deletion by a single `evictionClaim` that simultaneously reserves the prospective process admission (and writer cwd digest, when present) before any destructive reclamation, its private run state is reclaimed outside the lock while it stays registered (resume rejects a claimed candidate), and a final locked phase revalidates eligibility and performs the delete+insert atomically while excluding its own reservation, creating the new record's scopes only after successful reclamation. Definite reclaim success is required before phase C, whose only outcome is admission — a second reclamation phase is impossible by construction. Reclaim failure or timeout clears only the claim (and with it the reserved admission), keeps the candidate registered, quarantines it against unsafe resume because partial deletion cannot be disproved, and admits nothing. Thus total report/outbox memory is bounded by 50 × 64, with no duplicate completion queue, plus the bounded event queues. Questions use one independent retryable object per run; ordinary warnings stay in projection/session history and are folded into an eventual terminal outcome instead of being sent through `pi.sendMessage`.

## Module responsibilities

- `src/run/assignment.ts`, `report-lifecycle.ts`, `settlement.ts`, and `resume.ts` own assignment epochs, report commit, terminal settlement, and retained generation rollover.
- `src/run/completion.ts`, `completion-observations.ts`, and `notification-delivery.ts` own outcome records, exclusive claims, receipt consumption, and the retrying delivery outbox.
- `src/run/projection.ts`, `state.ts`, `session-events.ts`, and `warnings.ts` own bounded immutable views and diagnostic/session-history projection.
- `src/tools/details.ts` is the sole public details door. Its private `details-schema.ts` room owns the strict version-2 Effect Schema model, focused decoders, canonical bound, and freezing; `format.ts` and `render*.ts` own bounded model-visible output.
- `src/ui/` and pure `src/settings/ui/` modules consume immutable projections and never own Effect resources.

Backend-specific completion evidence is documented in [Local backends](local-backends.md) and [Herdr ownership](herdr-ownership.md).
