# Routing, candidate planning, and the public launch contract

Part of the [pi-subagents](../README.md) architecture documentation. See [ARCHITECTURE.md](../ARCHITECTURE.md) for the ownership map and cross-cutting invariants.

## Version-6 routing and nesting domain

A normalized candidate has `host`, `runtime`, `model`, `effort`, `context`, `writeIntent`, optional `openaiFastMode`, and `closeOnReport`. Routes are disabled, one candidate, or ordered candidates. Version-6 global and trusted-project documents own scope-local named `profileSets`; each set has one required `profiles` object, and an optional `defaultProfileSet` selects the document's active set. Configuration has no denied/discouraged policy, execution, lifetime, or generic tool-policy fields. Configured values normally pass through unchanged. There are no host or report-lifetime rewrites.

Only the three `local` × `pi|claude|codex` combinations are supported. Required `host: "local"` remains part of version 6. Cross-field decoding rejects:

- fork outside local Pi;
- parent-model selection outside local Pi;
- `host: "herdr"`, including a remote candidate anywhere in a mixed route, and all `closeOnReport: false` candidates;
- fast mode for Claude, an unsupported explicit Pi selector, or malformed Codex syntax. Local-Pi `parent` remains statically valid for the active-model check, explicit Pi selectors accept every model from the `openai` and `openai-codex` providers, and syntactically valid Codex selectors defer `priority` support to the authenticated native catalog and launch confirmation;
- unknown candidate keys, runtime-incompatible effort levels, or malformed native selectors (Pi registry IDs may use bounded `@` context variants such as `cursor/gpt-5.5@1m`; Claude's exact numeric long-context suffixes such as `[1m]` are supported without admitting general glob syntax).

A present-invalid route fails closed. Resolution starts from built-ins, overlays the selected global set route by route, then overlays the selected trusted-project set route by route. Omitting a global default selects built-ins; omitting a project default selects the global layer. A malformed or missing declared default fails that scope's routes closed while leaving configuration inspection available for repair. Global and project set names never share identity. A complete in-memory session route overlays the loaded persistent result and records source `session`; removing it reveals the exact activation-time base again. Every built-in is an explicit local Pi parent candidate using profile context, write-intent, and effort defaults with omitted `openaiFastMode` (equivalent to false) and `closeOnReport: true`. An explicit launch profile always wins. An omitted profile resolves to `generalist`. The main agent chooses the profile by the required deliverable; the profile determines the configured model route. Only the seven declared profile IDs are accepted.

Versions 4, 5, and 6 are accepted. Legacy v4/v5 root `profiles` and candidate `fastMode` decode into the synthetic `default` set. A successful store write migrates them to v6 `profileSets.default.profiles`, `defaultProfileSet: "default"`, and `openaiFastMode`; invalid legacy routes, containers, or fields block migration. Version 6 never accepts or writes `fastMode`. Version 4 receives `{maxDirectChildren:12,maxDepth:3}`; versions 5 and 6 may declare `nesting`. Direct children must be an integer from 1 through 32 and depth an integer from 0 through 8. Present invalid values fail activation without clamping. Policy precedence is Session, trusted Project, Global, then Built-in. A start batch captures one route and policy revision. Admission counts active direct children and race reservations for one parent, with no tree-wide active-run budget.

## Candidate planning and host resolution

Pure planning preserves explicitly declared order and resolves Pi model catalog/auth compatibility for local Pi. The host boundary records dynamic typed skips in launch provenance and continues to the next declared candidate only before service ownership begins.

All three local adapters are implemented. The shared registry resolves host/runtime/context and performs bounded executable/auth/model-effort/write-policy/private-harness readiness before owning a run scope, writer lease, supervisor channel, or process. There is no derived local fallback or automatic host conversion. Once `SubagentService.start` begins, lease marking, spawn, transport uncertainty, or control errors never trigger candidate fallthrough.

Selection provenance records the route source. The actual selected host, runtime, `openaiFastMode`, and `closeOnReport` remain in the internal request and the run view. Version-2 persisted run cards keep the direct host/runtime/model/effort route and report-close fields without duplicating them inside selection provenance. Version-2 start details contain no cards. They require one request-ordered discriminated entry per input, preserving the requested profile and concrete actual route/model for success, the attempted route/model after post-selection failure, or an explicit resolving/no-eligible-route state. When a selected start admitted a run and then failed, compensation crosses the complete process, backend, harness, supervisor, and writer cleanup barrier before the failure returns. Its bounded `admittedRun` projection reports the failed run ID, authoritative cleanup disposition, retry disposition, and remaining frozen-route candidate count. Eligibility comes from settled run facts rather than error-code text; cleanup quarantine or outcome uncertainty remains blocked. Each public start batch captures one immutable profile snapshot before resolving its agents, so concurrent session edits cannot split a batch across route revisions. Current-version details pass through the strict schema and canonical 48,000-character privacy bound. Older or unsupported details use bounded terminal-sanitized text fallback and are never reconstructed.

## Explicit route continuation

A failed run with configured candidates after its selected candidate may be continued explicitly with `subagent_lifecycle({ action: "retry", runIds: [...] })`. This is a new launch and run ID, not implicit fallthrough or resurrection of the failed assignment. It preserves the original task, profile guidance, route source, and a deeply frozen copy of the complete launch-time route; later session/project/global edits do not alter the continuation. Planning begins strictly after the predecessor's selected candidate, preserves original zero-based candidate indexes, and performs the same current model/auth/executable/private-harness preflight across all remaining candidates before ownership.

Retry claims the failed predecessor exclusively. Exact writer claims travel with the frozen continuation and are rechecked against current pool ownership. After cleanup is confirmed, successor admission atomically revalidates that claim, marks the predecessor with its successor ID, and admits the linked run. Concurrent retry attempts have one winner, retry-claimed records cannot be evicted, and a successor that later fails carries its own advanced cursor. A failed retry plan records every remaining static/dynamic skip and marks the route exhausted; only then should the parent choose a generalist replacement.

Retry fails closed for non-failed, later-assignment, already-superseded, exhausted, outcome-uncertain, cleanup-quarantined, eviction-claimed, or concurrently retry-claimed records. Writers create a fresh execution and may repeat partial side effects, so parent prompt guidance permits writer continuation only when the original handoff and current user intent authorize it. These gates preserve the invariant that no spawn, transport, lease, or cleanup uncertainty automatically launches duplicate work.

## Public launch contract

`subagent_start` accepts one required array of 1–32 agents, subject to the caller's effective direct-child capacity. Root calls create children of the virtual depth-0 root. Authenticated nested calls create children of the server-bound caller run; the public and proxy schemas contain no ancestry override. Each item contains:

- required `task`;
- optional `profile`, defaulting to `generalist`; an explicit profile always wins;
- optional `name`;
- optional `writes`, containing 1–64 normalized, exact, workspace-relative POSIX file paths. `writes` requires writer intent; read-only candidates are skipped in order, and the launch fails before ownership when no writer candidate remains. Omission preserves exclusive whole-cwd writer ownership in shared-checkout mode; isolated worktree writers do not compete for the parent's cwd.

The TypeBox object is strict, and the service boundary independently rejects unknown launch overrides with `launch_override_not_allowed`. Workspace mode is not a profile candidate or start-item field. The persisted session setting `writerWorkspaceMode` selects `shared-checkout` by default or opt-in `worktree` for every writer. Admission freezes that choice; unresolved ownership/artifacts block mode switching. Worktree writers currently require a root caller; nested writer launches fail explicitly. Read-only nesting and shared-checkout nesting are unchanged. Launch/status projections include the chosen mode, workspace identity, actual cwd, and source cwd.

Start is always background and nonblocking. The public tool executes all admitted batch items without waiting. `subagent_await` supports `all_finished` and `any_finished` semantics. `subagent_lifecycle` action `retry` accepts failed run IDs and owns explicit next-candidate continuation; it never accepts task, model, candidate index, or route overrides.

Main-agent prompt metadata follows a read-only-first adoption policy: before substantial work, check for at least two independent workstreams; launch one to three bounded read-only assignments early; skip delegation for trivial or tightly serial work; continue independent parent work after launch; and await only at a dependency or final-synthesis barrier because unclaimed completion reports are delivered automatically. Worker launches remain explicit implementation handoffs. While shared-checkout writers are active, the parent coordinates and reviews but does not edit. A claimless shared-checkout worker is exclusive; pairwise-disjoint exact claims permit cooperative sharing. Isolated writers do not share the parent's cwd, so the parent may continue edits. Their reports remain proposals: the direct parent reviews every immutable diff page, prepares combined changes, runs relevant tests in the prepared cwd, and integrates only the exact revision/preparation pair as uncommitted edits. Parent drift requires another prepare/test pass. `subagent_workspace revise` requests a successor without silently approving the previous revision.

`subagent_models` projects every complete resolved candidate as a flat structured version-2 card with `host`, `runtime`, `model`, `effort`, `context`, `writeIntent`, `openaiFastMode`, `closeOnReport`, `status`, and `reason`. It does not persist candidate prose or derived order/context fields. Model-visible text labels candidates only at the output boundary, and the renderer formats the structured fields directly. Dynamic executable/auth/catalog/service-tier/private-harness readiness remains launch-time. Discovery does not promise runtime readiness.

## Module responsibilities

Detailed responsibilities of the source files owning the behavior above:

- `src/domain/routing.ts` — import-free leaf routing vocabulary: context/write-intent/host/runtime types, the effort scale, the shared runtime-native effort policy, and host-effort decoding. `src/domain/write-claims.ts` owns import-free exact-path normalization, conservative equality, bounds, and overlap policy. Profiles, config, run, backends, boundaries, and settings consume these leaves directly so the profile and run models stay cycle-free.
- `src/profiles/` — fixed definitions, explicit built-in routes, ordered candidate planning, and a revisioned Effect-owned session override service. `model.ts` alone owns candidate constants, native-selector grammar, normalization/equality, structural fast-mode support, local-Pi predicates, ordered issue policy, route normalization, and labels. Runtime effort vocabulary stays in `domain/routing.ts`; authenticated fast-tier/catalog policy stays under `run/`. `session-overrides.ts` owns immutable overlay snapshots and conflict transitions.
- `src/boundary/host-profile-resolution.ts` — local Pi model/auth capture, initial ordered candidate consumption, and fresh-environment resolution of frozen retry continuations. Typed readiness failures fall through only before service start. `src/tools/execute-start.ts` applies the explicit profile or `generalist` default and resolves its route from the captured batch snapshot.
- `src/run/retry.ts`, `src/run/tree.ts`, and `src/run/launch.ts` own exclusive failed-run claims, immutable ancestry, subtree visibility, per-parent capacity/depth admission, cleanup/exhaustion gates, retry/eviction exclusion, and atomic predecessor/successor lineage.
