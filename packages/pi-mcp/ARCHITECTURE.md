# pi-mcp architecture

`pi-mcp` owns one Pi `mcp` gateway, `/mcp` and `/mcp-settings` commands, and the producer side of `tools.mcp.request`. All execution goes through `McpExecution`; Code Mode does not own a second connection manager. The [README](./README.md) defines configuration, public actions, limits, and supported modes. The [original plan](../../docs/plans/pi-mcp.md), [UI upgrade record](../../docs/plans/pi-mcp-ui.md), and [modernization record](../../docs/plans/pi-mcp-modernization.md) record their historical acceptance evidence. [CAPABILITIES.md](./CAPABILITIES.md) separates supported behavior and restrictions; the [feature follow-up](../../docs/plans/pi-mcp-features.md) tracks current implementation and acceptance.

## Application and authority

`extension.ts` and `application/register.ts` register inert callbacks. `application/lifecycle.ts` is the Effect-to-Promise boundary and uses core's session-runtime slot for startup, replacement, tree changes, and shutdown. Preview settings load before wrapping the owned gateway. The same session runtime owns its preview animation scheduler. Startup returns it alongside execution and manager capabilities; the wrapper receives a generation-checked scheduler callback. Replacement and shutdown revoke scheduling and dispose existing ticks, including when Jiti isolates extension modules. `code-mode/presentation.ts` owns bounded, redacted outcome and recovery interpretation for replies and typed adapter failures. Its shared `presentation-evidence.ts` reads descriptors and gates gateway counters, pagination, discovery gaps, and capture truncation by operation identity, including retained origins; matching fields in remote tool output remain data. The card decoder and pure `ui/compact-summary.ts` provider share it for retained origins, output validation, cleanup, truncation, discovery relevance, and retained-result access. `code-mode/issues.ts` turns that projection into bounded `CompactIssue`s without changing v1 capability replies or envelope notices. Each issue has one short human message, from `ui/compact-descriptions.ts`, a remote error's first line, or the first unclassified notice (unless it opens with agent guidance), and keeps agent-facing recovery in its detail. When signing in is the remedy, the compact summary names the user's command, `/mcp auth <server>`. Codes distinguish remote failure, retained-read failure, original outcome, invalid or unavailable validation, execution uncertainty, cleanup, credential blockers, output loss, unclassified notices, and incomplete evidence; routine discovery notices and retained-output access are informational. Evidence beyond the issue bounds adds an incomplete or overflow warning rather than silently succeeding. `tools/controller.ts` owns `wrapMcpTool`, called after settings load by lifecycle registration. Compact expansion uses content-only callbacks; `ui/call-content.ts` preserves bounded, sanitized arguments through the existing descriptor-safe display copier, and result content keeps readable and raw JSON text under labels, while the shared shell owns the heading and issues. `code-mode/issues.ts` decodes the typed failure evidence once and builds the one boundary view with `ui/boundary-failure.ts`, which carries fixed diagnostics without parsing remote messages; uncertainty, cleanup and credential-mutation blockers remain separate visible issues. Nested receipts, the card, and the compact summary share that view; the card adds only its known-envelope and uncut-preview gates, and the view is exposed only when the bounded issue schema accepts it. Any origin, including a malformed null, malformed notices, more than 2,048 characters of sanitized notices, and raw-preview cuts decline this view; notices that sanitize to empty are dropped. The model-facing observation projection is unchanged. Nested consumers must apply their own receipt bounds and invocation attribution before transporting these issues. Unknown, incomplete, or unviewed adapter-failure summaries retain the detailed renderer, including historical text content; it draws the same issues with `renderCompactIssues` and lists notices beyond the issue budget, so no view renders an issue twice. Preview style keeps the original callbacks. Successful retained reads report delivery separately from the original operation's failure or uncertainty. Execution and native images are unchanged. A foreign `mcp` registration prevents installation without mutating its tools.

The activation owns tool-error receipts and a stable-session Code Mode provider. Deactivation revokes both before runtime disposal. Lifecycle settlement and final synchronous tool publication each recheck cancellation: late cancellation withholds payloads, images, and retained IDs without changing known execution certainty. Pinned Pi treats a resolved tool execution as successful, so the owned `tool_result` hook restores the gateway's explicit error flag while preserving bounded content/details. It does not modify foreign results. Commands use current-generation session capabilities; authentication never enters the model request union.

`code-mode/protocol.ts` exports producer-owned v1 codecs and a narrow Promise capability through `pi-mcp/code-mode`. `boundary/host-code-mode.ts` validates stable session identity, current activation, trust, and top-level tool activation on each query and call. The consumer must find exactly one provider. It cannot reach management, auth, config writes, or arbitrary wire methods. Nested calls bypass Pi hooks and checks from unrelated optional extensions, so MCP policy lives in shared services rather than a `tool_call` hook. Pi has no built-in approval middleware. Trusted sessions, enabled servers, and exact-name tool allow/deny rules are the intended authorization model; per-call approval is an optional product policy, not an unfinished implementation requirement.

## Configuration and connections

`config/store.ts` is the only persistence API. It reads global `extensions/pi-mcp.json`, project-root `.mcp.json`, then project `.pi/extensions/pi-mcp.json` in increasing precedence, with no ancestor search. Both project sources require trust; the Pi directory name follows the host constant. Each winning server retains its actual source path in its identity. Settings commands write only to the global or Pi-specific project file, never `.mcp.json`. The store reads documents whose required root is `mcpServers` with core's bounded JSON-document API, preserves unrelated fields, and publishes a frozen configuration in the atomic write commit. Legacy `version` and `servers` roots are schema errors and are never migrated. Missing files remain absent until a write creates the canonical `{ mcpServers: {} }` root. Reads reject an existing `{}` without modifying it; explicit settings/server mutations initialize that empty object inside the same atomic write. Nonempty invalid documents are never repaired. Untrusted sessions perform no project-document I/O. Settings merge per field; server definitions replace as a whole. Invalid project overrides disable execution instead of inheriting a different target's credentials. HTTP `auth: false` normalizes to no managed authentication without rewriting raw documents or changing canonical credential identity. After strict rejection, configuration diagnostics reuse the selected transport's field codecs and emit fixed field-level guidance, never raw schema issues, input values, or arbitrary keys. Manager snapshots carry that safe diagnostic into server details.

`connection/service.ts`, `registry.ts`, and `admission.ts` own child scopes, deduplicated acquisition, bounded session/per-server admission, queue deadlines, idle cleanup, and revocation. Requests recheck current trust, configuration, and tool policy, using the shared `discovery/policy.ts` predicate, after queued waits. Auth operations use the connection owner's auth fence so login/logout cannot race a new dispatch. Login/logout eligibility is checked against current configuration under the admission lock, including after waits, before installing that fence or revoking results. Unsupported commands leave existing authority intact; admitted auth failures retain the fence. Revocation happens before interruption and cleanup; no registry lock spans remote work or a user dialog. Unconfirmed cleanup blocks replacement admission, including after session replacement. The connector forwards native cleanup observations independently of acquisition errors. The registry merges sticky, exact-owner evidence after acquisition and after scope cleanup, so timeout or interruption cannot produce a false confirmed-cleanup receipt. `operation.ts` separates current-authority publication checks from continuation checks, which also require an accepting owner and fresh credential evidence. A 401 can stop further UI/browser/dispatch work without erasing a separately completed reply's publication authority. Changed credentials increment authorization revision, revoke metadata/results, and retire the old owner. Only a later fresh request after confirmed cleanup can acquire its replacement; refresh never retries the current operation.

`boundary/sdk-connection.ts` resolves `${NAME}` placeholders in stdio `env` and HTTP `headers` only at connection time through its captured `ConfigProvider`. `$$` escapes a dollar sign, substitution is single-pass, and command, args, URL, and cwd remain literal. Expanded values are checked for bounded length, NUL, and, for headers, CR/LF before native acquisition. Stdio gets `PATH` plus explicit environment entries, with no implicit shell or ambient credentials. A server executable remains trusted local code with user privileges, not an OS sandbox. Configuration cwd and allow/deny rules do not confine its filesystem or network access.

`discovery/` owns complete frozen metadata revisions, bounded remote pagination, list-change coalescing, exact lookup, and revision-bound gateway cursors. A notification that joins an existing refresh checks outstanding owner evidence after settlement and starts or joins at most one follow-up collection. This covers notifications during collection or between commit and shared settlement without retrying a notification-owned failure. `collect.ts` settles each advertised listing independently under one owner and budget. A first-page `completed/unsupported/rpc-method-not-found` response marks only that catalog unsupported and records a fixed diagnostic. Every other failure, including a later-page missing method, remains fatal. A complete revision combines full successful lists and explicitly unsupported catalogs; it never mixes partial pages or different revisions. `freshness.ts` derives monotonic expiry from bounded `ttlMs` and `cacheScope` hints. Pagination and collection choose the earliest page/family expiry and most restrictive scope. Missing, nonpositive, invalid, or greater-than-one-day TTL gives zero freshness. Active `ensure` reacquires expired revisions and uses a fresh zero-TTL revision once. Cursor continuations read the current cached revision locally even when expired; refresh, notification evidence, and auth/configuration invalidation invalidate them. Invocation freshness remains separate. Passive cached queries disclose staleness. Binding authorization revisions prevent reuse across auth contexts, including public metadata. Commit and revocation govern arrays, support flags, freshness, and diagnostics together. Gateway discovery captures selected snapshots and refresh evidence together; a matching-owner refresh failure adds a fixed notice for preserved metadata. Successful refresh clears that evidence for new replies without changing historical retained notices. `summary.ts` projects compact tool selections only after local pagination; snapshots and exact descriptions retain complete definitions. `search.ts` ranks full names, titles, and descriptions with locale-independent tie-breaking. Gateway and cached queries share matching and cursor pagination, without a second metadata cache. Unscoped discovery never connects every server. Resources and prompts use enabled-server authority. Resource URIs route only to that server; returned links are never followed locally. Prompt roles and server descriptions remain untrusted data, never system instructions or installed slash commands.

## Protocol and transport boundaries

`sdk-client.ts` captures an immutable, code-point-safe 64 KiB UTF-8 prefix of initialization instructions after a successful HTTP or stdio handshake. `McpConnection` owns that optional snapshot and passes it to admitted `McpOperation` values. `server.instructions` projects it through the existing owner-checked result retention path, without discovery or an application RPC. Missing and empty text remain distinct; capture truncation is durable result data, while notices are best-effort. Instructions are never inserted into the system prompt, and no separate instruction store or persistent cache is added. Reconnection captures a new handshake; completed retained results follow existing revocation rules.

The official client/core SDK 2.0.0 owns negotiation, framing, correlation, cancellation, and wire schemas for MCP `2026-07-28` and its supported legacy revisions. `boundary/mcp-protocol/contract.ts` defines the adapter contract; `select.ts` alone imports both `modern/` and `legacy/`. `shared/` holds owned protocol-neutral helpers and may use the selector, but cannot import either implementation directly. Neither era imports the other. Oxlint `no-restricted-imports` overrides enforce these static import boundaries without restricting tests or the selector. Removing legacy support changes its directory, selection policy, tests, and documentation, not auth, connection, discovery, results, tools, or UI services.

`client/` defines internal contracts, negotiated-version and observation-health evidence, and redacted errors; `tools/model.ts` owns the public request/reply union. `sdk-client.ts` uses public requests and SDK wire schemas; remote schema compilation stays off Pi's thread. Both transports accept optional `protocol: "auto" | "legacy"`, with modern-first negotiation on omission. Existing configuration remains valid without migration or aliases. Historical HTTP+SSE remains unsupported, without deprecating SSE inside Streamable HTTP. Modern optional interaction work and its acceptance status are tracked in the feature record; legacy server-driven elicitation is not advertised.

`boundary/sdk-lifecycle.ts` is the one SDK connection driver for both transports: a plain function, not a service or second scope owner. It owns the admission-time deadline, owner scope, immediate revocation, interruption-safe cached close, cleanup-evidence publication, observation budget, and connection assembly. Each transport supplies native acquisition, its exchange, one named close policy, and its own agent-visible messages; both share its limit fields. `boundary/sdk-stdio.ts` supplies stdio acquisition. Its close policy finalizes subscription owners while the native writer is still available, then unconditionally joins SDK/native cleanup; failed cancellation writes and native uncertainty remain sticky. `sdk-stdio-transport.ts` uses public SDK framing over core's macOS duplex process. The SDK's native close lacks the required root/group/pipe confirmation. A child scope owns bounded readers, writer queues, and cancellation ingress. Auto negotiation uses a disposable owned probe child and admits the application child only after confirmed probe cleanup. Explicit legacy selection skips this probe. Generic failures, malformed negotiation, auth rejection, and HTTP timeouts do not authorize fallback. The selector's rejected-probe error survives SDK wrapping through `shared/negotiation-error.ts`; HTTP and stdio map it to fixed protocol-compatibility guidance without changing dispatch certainty. A silent stdio probe may select legacy after its bounded deadline and confirmed cleanup. Early-exiting pre-initialize servers need explicit legacy mode. Cancelling one request does not close a healthy shared connection or undo remote work.

`sdk-http.ts` supplies Streamable HTTP acquisition and native teardown to the same driver; `sdk-http-request.ts` holds per-request execution and finalization against that same state and operation registry. `sdk-http-transport.ts` owns admission, dispatch/completion evidence, and continuous native-resource leases. The extraction adds no separate owner or service. GET, DELETE, and notifications have session traffic ownership separate from application calls. Its close policy revokes admission, aborts and joins every operation before closing the owner scope, and recomputes cleanup evidence; the driver caches that result even if the first caller is interrupted. Consumer abort is not proof that native source cleanup finished. A session-bearing legacy POST 404 revokes reuse without replaying the failed application call. The legacy adapter accepts DELETE 404 as remote absence, but local owners still need confirmed cleanup before replacement. Modern stateless HTTP has no legacy session to delete. Optional GET 405 and sessionless GET 404 do not invalidate a usable POST connection; session-bearing 404, authorization failures, and outages still do.

`sdk-fetch.ts` adapts the injected Effect fetch capability to SDK Promises/ReadableStreams, strips internal correlation headers, rejects redirects, and bounds bodies before SDK parsing. SSE accounting bounds each event and incomplete line rather than the stream's lifetime bytes. Native callbacks transfer fetch/body ownership without an idle gap. `sdk-http-control.ts` gives uncorrelated non-GET traffic its own 16-slot admission cap and scoped deadlines, independent of application permits. Cleanup uncertainty disables reuse. Native body leases release only after EOF/error or actual source-cancel settlement, not consumer cancellation or SDK close. Core's scoped `NativeContext` captures request/subscription context around public SDK calls on both transports. HTTP uses inherited callbacks for exact request-stream observations; stdio binds outbound SDK-generated IDs before sends. Context grants no authority and adds neither a foreign parser nor an Effect runner.

`sdk-protocol-error.ts` maps SDK `ProtocolError` replies and shared public SDK client errors into fixed categories for HTTP and stdio; each transport keeps its own fallback and wording. Both protocol adapters use `mcp-protocol/shared/subscription-failure.ts` when transport-specific failure evidence is unavailable. Legacy subscription rejection preserves the completed protocol error and does not invent establishment uncertainty. Only a correlated rejection or proven non-dispatch clears that uncertainty on failure; malformed replies, timeouts, and interruption remain fenced, and native cleanup must still settle independently. It distinguishes unsupported methods, rejected parameters/requests, missing resources, and server errors without copying remote messages, data, or custom codes. Each transport keeps its existing dispatch/completion evidence and cleanup precedence. Diagnostics preserve safe failure detail for completed operations without assuming retained output; unknown outcomes still prohibit automatic replay.

Modern metadata subscriptions use an acknowledgement deadline and connection-scoped lifetime, separate from ordinary application requests. Lost observation revokes stale discovery authority. The registry retains a bounded, identity-scoped failure diagnostic after owner retirement and clears it on fresh successful acquisition or authority change. Legacy list notifications retain their connection channel.

Transport auth is token-only, with automatic insufficient-scope recovery and SDK reconnection disabled. It cannot start login UI or replay a rejected application request. Request admission leaves configured HTTP headers intact for `auth: none`; managed authentication still publishes token updates and explicit transport token clearing revokes Authorization.

## Optional operations

`completion/operations.ts` validates exact advertised prompt/template references and argument names before admitted dispatch, with at most 100 returned values. `observations/` owns a session-local ring of 128 events/128 KiB with 4 KiB log/progress text and coalesced operation progress. `events.read` uses string cursors and pages of 1 to 100 events, default 32, without connecting. Current-authority progress works on both transports and reaches bounded top-level `onUpdate` callbacks; it never implies completion. Explicit `logLevel` requires modern HTTP and advertised logging support. Legacy and modern stdio reject it before dispatch. Raw HTTP ingress checks exact request-stream provenance and severity. Structured Logging is deprecated compatibility, without global logging or a telemetry exporter.

`resources/subscriptions.ts` owns explicit subscribe/unsubscribe and local active-status inspection, with 16 leases per connection owner and 32 per session. Leases prevent idle retirement and end with owner or stream closure; no automatic reads or re-listening occur. One owner finalizer is registered before publication and visits only current entries. Normal child-scope closure detaches per-entry cleanup, so historical subscriptions do not accumulate. `sdk-events.ts` captures SDK-generated listen IDs and validates modern updates against their acknowledged URI filters at raw ingress. Both eras allocate the private subscription symbol before acquisition and carry it through the bounded queue. Raw modern ACK evidence permits at most 32 staged updates; SDK/filter acceptance is still required before queueing. Overflow contributes to ingress drops. Publication waits for matching entry readiness outside the registry lock, rejects stale identities before waiting, then rechecks the active handle and removes the symbol before retention. Legacy wire notifications cannot identify old server work first received after replacement. HTTP close joins native source cancellation. `sdk-subscription-traffic.ts` separately tracks stdio send reservations and native write settlement, so SDK logical close cannot hide failed cancellation writes. A successful write is not a remote acknowledgement. Failed writes preserve ownership until child cleanup. Unknown legacy pre-acknowledgement outcomes retire the connection. Modern acquisition errors retain the owned HTTP operation's dispatch/completion evidence and fixed error category; stdio failures without terminal or predispatch evidence remain unknown. Subscription auth rejection uses the same credential-rejection fence and private challenge handling as ordinary requests.

`interaction/conversation.ts` owns modern `input-required` exchanges only for tool calls, resource reads, and prompt retrieval under the originating deadline. It bounds dispatch rounds to 8, input requests to 16, and request/response batches and state to 64 KiB each. SDK constructor capabilities stay empty; only current same-session TUI/RPC providers authorize per-request elicitation advertisement. Legacy/headless sessions never advertise it. `form.ts` maps strict flat schemas with at most 16 fields and 64 enum choices total; its sensitive-text heuristic is not a complete secret detector. The existing validator checks accepted content. `sdk-elicitation.ts` keeps opaque continuation state separate from terminal replies. No public answer, `inputResponses`, or `requestState` API exists.

`host-ask-user.ts` resolves current providers and waits up to one second for exact-owner cancellation. Its module-wide process-local set retains an opaque token per unresolved cancel attempt across runtime/session replacement. Only that Promise's successful native settlement removes the token; timeout or rejection does not establish cleanup and blocks later provider resolution. Ask User owns private presentation. `host-elicitation-browser.ts` owns macOS system-browser navigation after full inert URL/host consent and fresh authority checks, followed by explicit manual resume. There is no polling, second executor, fake subagent identity, or permission engine. Final acceptance belongs in the [feature record](../../docs/plans/pi-mcp-features.md).

## Authentication

`auth/service.ts` owns grant access, publication authority, and logout. Headerless URL servers with omitted auth start anonymous and unchecked until rejection, login, or an explicit user credential check activates grant access. Explicit none/false and custom-header defaults stay outside managed OAuth. `auth/authority.ts` owns process-local identity permits and blocks across runtime replacement. Rejection of a managed OAuth token blocks reuse even without expiry until successful explicit sign-in. Session revocation clears implicit activation and private challenge hints, not these blocks. Rejection evidence is not persisted and does not survive process restart. No failed operation is replayed.

`boundary/sdk-auth.ts` adapts SDK public-client discovery, registration, PKCE S256, exchange, and refresh. `sdk-http-challenge.ts` privately correlates bounded POST 401/403 challenges with their exact failed operation, not the connection's last response. `sdk-auth-discovery.ts` validates a retained challenge for later explicit login before considering an unauthenticated GET probe. That headers-only probe joins socket closure without draining an SSE body and sends no configured headers or credentials. A validated `resource_metadata` hint wins over well-known discovery; malformed or unsafe hints fail closed. Only exclusively 404/410 metadata responses permit the optional configured-issuer or endpoint-origin fallback. An owned fetch guard rejects the SDK's broader fallback, and real authorization-server metadata remains required. Restoration rechecks persisted discovery provenance and issuer/resource authority. Validated canonical resource URLs allow equivalent root spellings, not different paths or queries; configured issuer pins remain exact, with trailing-slash equivalence only for inferred root issuers.

`auth/scopes.ts` validates scope tokens and proposes permissions for explicit login. Omitted scopes use validated challenge or protected-resource evidence, never the authorization server's general catalog; explicit `[]` disables inference. A retained insufficient-scope challenge can propose configured-scope additions. Conditional `offline_access` requires advertisement and refresh-grant support. Added or inferred permissions require private confirmation through `host-auth.ts` with current-attempt, abort, trust, and deadline checks. The authorization URL must match approved scopes. These proposals grant no automatic escalation, login, or replay authority.

`sdk-auth-registration.ts` reuses compatible sanitized dynamic-registration receipts across cancellation and repeated sign-in, rechecking identity, issuer, resource, scope capacity, and callback binding. SDK native-client metadata permits a port change only for automatic local loopback callbacks with a revalidated native binding; fixed/manual callbacks remain exact. New registration checkpoints persist before browser handoff without replacing a prior grant. Rejection of a reused client never triggers automatic fresh registration. `sdk-auth-client.ts` enforces public-client-only authentication. Explicit `none` permits discarding an unused secret and its expiry; secret-bearing missing-method receipts and declared non-public methods are rejected. Stored method evidence survives SDK decoding, and only normalized client information reaches exchange, refresh, and persistence. Legacy secretless grants without a method remain supported.

`boundary/auth-fetch.ts` owns bounded OAuth HTTP requests. Core's `NetworkAddresses` resolves candidates; MCP policy approves them; `pinnedNetworkLookup` supplies exactly that set to a scoped HTTP agent. Every allowed discovery redirect is checked again. The core resolver supplies no OAuth policy and makes no second DNS lookup at connection time.

`boundary/auth-callback.ts` owns a scoped IPv4 loopback listener using core's `nodeHttpServerLayer`. The auth attempt owns route, Host, origin, redirect, and one-use callback checks. Core owns native listener acquisition and connection closure; active clients cannot keep the listener alive after shutdown. `boundary/host-auth.ts` adapts explicit-user TUI/RPC dialogs and browser opening. Manual callbacks use the user-only dialog and require a fixed registered redirect. Print/JSON mode checks existing grants without interactive login and preserves actionable fixed failure reasons. URL, DNS, issuer, PKCE, and resource checks still apply before credential use; no challenge expands trusted destinations.

`boundary/credential-store.ts` is the credential persistence door. `auth/credential-record.ts` reads legacy v1 grants and writes a v2 envelope with optional grant and sanitized dynamic-registration checkpoint in the same Keychain service/account. Registration updates preserve the prior good grant, including after cancelled login. `auth/refresh.ts` persists quarantine before SDK refresh consumption and clears it only after validated clean-grant persistence. Failed, uncertain, or cancelled refresh cannot reuse the old token across process restarts. `auth/credential-transaction.ts` uses the store's transaction API, its only grant and registration read/write path, which holds core's cross-process lock for the actual Keychain service/account across reread, refresh quarantine and exchange, registration/grant updates, and logout. The production `.cosmic-pi-locks-v1` namespace uses the actual OS account home, independent of `HOME` and agent directories. Core propagates one monotonic admission budget through auth authority, store permits, and filesystem queues. The default `acquireTimeoutMs` is 15 seconds, independent of native Keychain `timeoutMs`; it never expires admitted work. Live trust/configuration checks run after waits and before credential refresh or publication, including headless access. Managed bearer credentials cannot reach remote plaintext HTTP.

`keychain.ts` lazily loads macOS `@napi-rs/keyring`; there is no plaintext or session-only fallback. Native mutation fences survive runtime replacement. The cross-process lock journals pending native mutations durably. Confirmed native settlement, not waiter cancellation, clears that phase. A dead quiescent owner is reclaimable; a dead native-pending owner requires recovery and remains blocked. Normal exact-owned `.released-<token>` cleanup is best-effort. Dead-recovery `.retired-<token>` barriers and crash/malformed artifacts are not garbage-collected; there is no global storage bound. Offline maintenance must stop all participating processes and reclaimers and independently prove native settlement before touching pending evidence. The [README recovery procedure](./README.md#credential-coordination-recovery) forbids bulk root deletion and preserves refresh quarantine. There is no reset CLI, and explicit sign-in cannot bypass unresolved native evidence. Deletion must join an earlier mutation before it can report success. Logout revokes connection/result authority before deleting both the grant and registration checkpoint, with no provider-revocation claim.

## Manager and auth presentation

`auth/flow.ts` owns one explicit-user presentation around `McpExecution.login`. `auth/progress.ts` contains immutable, secret-free phase evidence. The auth service binds outer-completion hooks to the exact inner login receipt, so stale callbacks cannot publish readiness for a replacement attempt. Passive status starts at `unchecked`; native mutation observations do not read Keychain. A saved grant is not successful sign-in until the connection fence settles.

`host-auth.ts` keeps browser URLs and callback values in private user capabilities. RPC uses fixed-title stock confirmation/input/select dialogs. `host-auth-panel.ts` owns the TUI prompt, repaint subscription, independent cancellation signal, and nonqueuing reopen ingress. It opens on Cosmic UI's shared `dock` surface, which draws the sign-in panel full-width above the editor; an empty overlay owns keyboard focus without covering the input or footer. Both the widget and focus overlay hide for stock permission and manual-callback dialogs through the mounted handle. The surface's external close serves the cancellation fiber and terminal-phase cancel, and its close removes the uniquely owned widget, including failed or late mounts. Flow admission and native browser-call settlement each guard repeated opens. The callback page is static and acknowledges receipt only.

`manager/service.ts` owns view admission, action tickets, and coalesced local invalidation. Its projections use connection status, cached discovery summaries, and catalog-only local reads for authoritative availability and permitted tool counts, never gateway status polling or credential access. Invalidation clears counts and marks metadata as checking; trust loss marks it unavailable. Discovery dispatch returns count feedback only when the admitted revision remains authorized in the published view. Every mutating action rechecks the displayed configuration, exact server identity, and operation revision at admission. The dashboard asks before a risky action on its own screen, like every other manager, and closes with the warning the person accepted; `manager/controller.ts` runs such an action only with that accepted warning. The controller closes and joins the dashboard before dispatch or auth, then reopens from safe navigation state. Typed `/mcp` commands confirm through the stock dialog in `boundary/host-ui.ts`.

`discovery/cached.ts` implements bounded, policy-filtered reads across complete cached revisions. The discovery service remains the only metadata store. Internal queries return data and notices from the same revision. Catalog-only queries reuse that evidence without producing entries or consuming pagination cursors. Gateway projection preserves those notices through retained reads; cached catalogs and manager summaries expose the same per-family evidence. Connection-owner expiry and revocation withdraw content. Metadata TTL expiry instead marks passive content stale; refresh failure may preserve the last authorized revision with its failure state. The result service publishes scoped store-change notifications, so capacity eviction also withdraws open viewer text. Reads do not notify or allocate new results. UI components discard text immediately on invalidation and restore expansion/scroll state only through authorized local reads. Result navigation keeps one authorized raw/readable page plus bounded previous offsets; a local mode preference holds no output authority.

`boundary/host-ui.ts` opens manager overlays on Cosmic UI's shared `screen` surface, which owns the handle acknowledgment and guarded completion, so late mounts and cancellation cannot pop an unrelated newer overlay. The wrapper keeps MCP's own lifecycle: it disposes the component before `done`, stops rendering once disposed or no longer current, and maps a failed close to "could not be closed safely". Each browser/result-manager opening uses Cosmic UI's live screen viewport for both overlay bounds and component height, including the frame: centered 90% at terminals at least 125 columns by 30 rows, otherwise full bounds. The compact authentication panel uses the above-editor dock instead of this viewport. Top-level `ui/` contains pure components and tool renderers; it has no service runners or I/O. The manager delegates pane-focus borders, headings, aligned detail fields, and semantic identity/value roles to `pi-cosmic-ui`. Saved server scopes use the shared saved role; retained-result metadata uses typed origin evidence rather than interpreting result text. Docked auth explicitly preserves its existing border style. The shared full-screen styles do not alter tool cards; MCP retains status/auth interpretation, table column priorities, notices, action policy, and metadata disclosure. Shared tables measure the complete server dataset. The manager uses narrow list/inspection views below 60 columns, stacked panes at 60–99, and side-by-side panes at 100+. Wrapped detail windows retain position indicators; loading placeholders do not change their scroll anchors. Tool cards preserve the execution envelope, native images, retained IDs, and error-receipt identity beneath `withCodePreviewShell`. `ui/content-preview.ts` owns bounded, descriptor-read display copies, terminal sanitization, diagnostic redaction, recognized MCP text extraction, and explicit display-cut evidence. Card raw/readable sections share one budget. Retained raw uses a separate page-sized budget; only complete authorized JSON pages enable readable mode. Partial pages are never decoded or assembled, and display text never supplies cursor coordinates. Roles and links stay inert data in both views.

`activity/service.ts` holds a bounded observational journal, not a scheduler. Actual shared auth/connect/metadata owners publish one row each, including work started through Code Mode. Terminal retention follows completion order. `host-mcp-status.ts` publishes Activity v1 and one keyed status contribution through Cosmic UI's public APIs. Inspect capabilities recheck activation and row revision, then delegate to the lifecycle-owned manager opener. They contain no auth capability. Deactivation removes only the old activation's subscriptions and contributions.

All new services compose in `layer.ts` under the existing session runtime. `application/lifecycle.ts` remains the sole submission boundary. No settings form, parallel persistence API, custom RPC protocol, or generated runtime was added.

## Validation and results

`results/validation-notices.ts` owns the unchanged producer message catalog. The shared card decoder uses `ui/validation-notices.ts` to consolidate only exact raw catalog messages or their deterministic 128-byte projection prefixes, with coherent completed envelope and origin evidence. It keeps failed validation distinct from unavailable validation, preserves separate remote failures, and never inspects remote `data.result` notices for suppression. Model-facing envelopes and retained text are unchanged. Compact summaries pair action and target with one evidence-based count. Tool searches include a bounded, descriptor-read query alongside any server target. Discovery pagination combines returned/total counts and next-page availability in that detail.
