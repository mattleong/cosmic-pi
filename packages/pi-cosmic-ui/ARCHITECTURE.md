# Cosmic UI architecture

Cosmic UI hosts the composable Pi footer, repository probes, working row, activity tree, settings, and plain-data contribution protocols.

## Session and host ownership

`src/extension.ts` is the entrypoint. `src/application.ts` owns registration, protocol subscriptions, and session orchestration. `src/layer.ts` composes the config store, footer host, and activity services. It injects the plain process contract into its consumer rather than adding an adapter service.

Startup passes the activity service through the session slot. A host lifecycle generation guards delayed shutdown and failed-start continuations so old cleanup cannot clear replacement context, totals, footer contributions, or projections. Each input also owns publication authority revoked before synchronous replacement/reset and disposal; masked config commits may finish durably/private-only but cannot republish or repaint after retirement or failed replacement initialization.

`src/boundary/` contains Pi I/O and hostile host-callback handling. Footer getters are materialized through core's `invokeHostCallback` with neutral fallbacks; usage numbers are Schema-decoded before arithmetic. Settings, usage, and protocols share pi-cosmic-core's `decodeUnknownOrUndefined`, which also contains hostile proxies. `host-exec.ts` is the sole Git/`gh` boundary; probe policy remains in `src/probe/` and checks Git currentness after each process yield.

`host-status.ts` supports sanitized TUI/RPC status while keeping custom-footer declarations TUI-only. It republishes placement on host replacement. `host-ui-ticker-pool.ts` owns one scoped fiber per cadence, isolates failing callbacks, and interrupts a cadence on final unsubscribe. Shutdown rotates the cross-extension status owner and awaits the old pool before reuse.

Usage totals come only from validated `sessionManager.getEntries()` snapshots, including assistant and tool-result usage, compaction and branch-summary usage, and usage entries of any kind. Failed reads, malformed records, or overflow preserve the last complete snapshot. Startup resets totals; turn end, compaction, tree changes, and agent settlement rescan persisted entries. Turn end and Bash, edit, and write completions fork their Git refresh, because Pi awaits these handlers before its agent loop continues. Message-end payloads never add charges. Pi has no public extension `entry_appended` event, so a lifecycle-guarded subscription to the existing one-second ticker also picks up idle cache warming. Unchanged idle totals do not republish or request rendering. Replacement and shutdown unsubscribe the old ticker.

## Footer and configuration

`CosmicUiService` in `src/protocol/service.ts` publishes frozen config, totals, Git, and pull-request projections. Branch invalidation acquires the Git then PR refresh gates before clearing authoritative probe state, excluding both post-validation publication windows; individual commits never acquire the other engine's gate. `src/footer/registry.ts` is a synchronous keyed store of text and status contributions, plain presentation state under the effect-v4 exception. `application.ts` calls it directly from its protocol event handlers, so events apply inside `pi.events.emit`. Each entry owns a contribution detached and frozen when the event arrives; normalized values retain identity. Every operation publishes its snapshot before it requests a render, and only a changed entry list replaces the snapshot; an upsert of the same canonical value still renders. An operation emitted during another one, for example from a render request, queues behind it. One outermost operation accepts at most 128 reentrant operations and drops the rest; each operation is isolated, so a throw cannot strand queued work or reach the producer. While no session is active the store keeps at most 128 distinct keys, evicting the oldest; an active session has no key cap. Deactivating an activated session clears the store after the footer is uninstalled. A start that never activated keeps pre-session contributions, and the generation-guarded shutdown continuation clears the store unconditionally.

`src/footer/installation.ts` owns synchronous pending and active installation attempts, disposal, and the render request. Only the newest instance of the active attempt receives guarded render requests; stale or disposed instances can neither receive nor clear them. Footer components read the registry snapshot and detached projections without running Effect. Layout sanitizes text/status and resolves semantic tones to Pi theme tokens.

`src/protocol/protocol.ts` defines the public v2 footer protocol for text and status contributions and owns their copying, freezing, and identity reuse. Discovery reports live footer ownership, settings readiness (from activation, after startup loads the session's preferences), and hidden IDs. Providers wait for preferences before automatic fetching, honor hidden IDs in contribution and fallback paths, and never install a footer themselves.

`src/config/store.ts` is the only persistence entrypoint, using core's scoped config store without a default document. Resolution never writes; explicit updates create documents. `schema.ts` owns defaults, leaf schemas, and fresh fallback values; the store decodes fields tolerantly. `src/settings/controller.ts` registers `/cosmic-ui`, whose `settings` subcommand and picker come from the shared settings shell in `boundary/host-settings-command.ts`. Current settlements reread authoritative config, failures roll back, and stale settlements cannot overwrite newer optimistic values.

## Activity

`src/activity/service.ts` owns the session provider registry, registration generations, retained summaries, and scoped clock. Core's frozen projection transaction allows interruptible validation and lock waiting, followed by atomic publication; an optional `changed` hook runs after each commit so the host can refresh followed details. Invalid snapshots withdraw rows, starting counts, and acknowledgement together, and valid publication can restore them. Validation runs on cleaned items and also enforces workflow consistency: only workflow items carry `phases`, phase titles are unique, a workflow's `phase` names one of them, a phase's `work` counts are consistent (finished at most items, and stopped plus the optional failed and skipped at most finished), a workflow never needs input or blocks, a `planned` item is never a workflow and is pending, when it may offer actions such as a skip, or cancelled without actions, and only cancelled work that is neither planned, a workflow nor a question is `skipped`. Active launch-request counts take precedence over overlapping pending agent counts; counts drive startup visibility and the 100 ms clock even without rows. Planned items are declarations, not launches, so they count toward neither.

The v1 client in `src/activity/protocol.ts` carries exact session ID, host activation nonce, and producer registration token. Same-session replacement rejects replay, and revoked registrations cannot return. Summaries are bounded, detached, sanitized, and credential-redacted before broadcast and again at ingress, through the private `detach.ts` routine, which clips each field to its own limit; only the detail cleaner differs per direction. `limits.ts` holds `ACTIVITY_LIMITS`, every bound the schemas, detachment, and cleaners enforce; the public entry re-exports it so producers clip to the same numbers. Callbacks are checked capabilities, not services or runtimes. `registerRevisionedActivityProvider` is the shared producer wrapper that rechecks the producer session, exact item revision, cancellation, and offered action before a detail or action callback runs. Its action callback also receives an availability-bound `invocationCurrent` guard for rechecking after prompts; restored availability never revives an old invocation. Providers hide legacy panels only after successful widget installation and an accepted snapshot acknowledge ownership. Disposal, invalid publication, and teardown restore fallback availability. The published `pi-cosmic-ui/activity/testing` subpath holds `fakeActivityHost`, a test-runner-independent in-memory host for producer tests, and `activityGalleryFrames`, which renders producer items as plain-text widget and manager frames for presentation galleries.

Workflows travel through the same snapshots. A producer publishes one `kind: "workflow"` item per run with ordered `phases`, optionally with its own per-phase `work` counts, and the current `phase`; its status, details, and actions (such as stop) belong to the producer. Work items join a workflow through their existing `parent` and name a `phase`; queued work is an ordinary pending item without a start time. Planned work is a `planned` item that keeps its id when it becomes real work; while pending, its producer may offer actions on it, such as skipping it before it starts, which revision checks guard like any other action. Cancelled work the producer skipped before it started, such as an agent the user skipped or a budget refused, carries `skipped: true`, so Activity calls it skipped rather than stopped and counts it apart. A phase may carry the producer's own `planned` count and `failed` and `skipped` counts within its `work`, and a workflow its `unphasedPlanned` count for planned members outside its published phases. A workflow's `summary` is its narrator line. Activity derives display state only and never schedules or retries work.

`src/activity/model.ts` resolves explicit ownership over an existing row map for retention and display. Missing direct parents become roots; every path entering a cycle becomes an independent root, so a member whose workflow was evicted falls back to its own kind's section. Retention caps removable completed rows at 128 per branch and 1,024 per session, plus 100 finished root branches: those their sources dropped longest ago go first, then the earliest ended. Live/awaited rows and their resolved ancestors are protected. Planned rows that never ran are pruned before real results and stay out of omission counts, because producer planned counts still cover them. Omission counts are lower bounds and do not grow from repeated snapshots. Source-removed finished rows carry an internal-only `retained: true` marker and no actions. `grouped-tree.ts` assigns only roots to the Workflows, Subagents, Tasks, and Attention sections and nests everything else under its owner; a workflow's direct children sit under the phase they name, or directly under the workflow. `group-summary.ts` holds the pure summary and phase-state rules. Planned rows count only as planned or, once their workflow ends, not run, never as work, so they cannot make a phase running or done; within a branch they follow real work, finished or not. The tree replaces visible planned rows with the producer's phase `planned` and workflow `unphasedPlanned` counts when present, and a phase's visible work and failures with its `work` counts, since retention, row caps, and eviction can hide finished members, so phase, workflow, and section totals agree. History placement reads visible rows only, so producer counts never hide a member that is still running. A live workflow's current phase stays running between its sequential members; settled work that was all skipped is skipped, settled work that all stopped or was skipped is stopped, settled work with any failure is failed and shows attention rather than success, and phases without work that were passed or never reached are skipped. While the workflow is live, planned agents keep such a phase pending instead. Workflow phase counts show done phases out of all phases and name stopped and skipped phases separately, and the workflow detail also names failed phases, which rows leave to their agents' failure notices; done, failed, stopped, and skipped phases have all settled for history placement. A workflow moves to history once its row and whole subtree finish. Selection, collapse, and focus preferences remain session-owned.

`widget-projection.ts` owns pure widget allocation: reserve workflow rows, phases (those with attention first, then running ones, when not all fit; shown phases keep their declared order), and root workflows' narrator lines, then live failures, before sharing member detail, then planned rows, preserve standalone capacity, and count omitted work, planned rows, phases, and workflows separately. A live workflow keeps its two most recent failed direct members in view, each with its clipped summary as the reason. The rest are counted per phase, or for members outside its phases, on a line beneath that branch's last failure shown, or beneath the branch row when none is, so a count never reads as another phase's; a count line that does not fit, or whose branch is collapsed, joins the omitted-work count. They leave with the workflow once it ends. Phase rows always count their planned agents, and phased workflow rows count those outside their phases, so clipped planned rows remain visible as counts. Narrator lines are widget-only entries beside the grouped tree, not manager rows. It builds the checklist once per published rows array, so height and every frame reuse that tree; the host grows the widget for phase checklists, planned rows, live failures, and narrator lines up to half the terminal. `row-render.ts` supplies one row geometry for sources, workflows, and phases, which `row-line.ts` and `workflow-row.ts` fill. It keeps the tree guide, kind, and the first title columns (a short title reserves only its own width) before optional status parts, which go first as elapsed time, then progress, then phase counts, then the row's own state; attention notices always stay. Manager history rows recede through their identity tone instead of a marker, so every row keeps the same guide columns.

`component.ts` uses shared manager components and caches its trees per rows array and presentation state. Destructive producer actions require separate confirmation, given by Enter or the letter shortcut that asked for it, never a number key. `action-keys.ts` maps common action ids to direct keys for both input and footer hints; the default footer shows a row's only direct-key action, the number-key hint counts the actions on the shown page, and `a` appears only past one page of nine. A confirmed or pressed action is retargeted to the row's current revision when the same row and generation still offer an identical action; otherwise the displayed revision goes out and the producer rejects it as stale. Actions close the manager first because the producer may open its own UI; only actions marked `handoff: false` run in place while the manager stays open. `attention.ts` classifies human input, parent waits, and blocked states; protocol validation requires explicit attention metadata. Details load on explicit open/refresh or opt-in follow, remain marked stale across updates, and are bounded/redacted by the service. A newly selected item's detail opens at its first lines, since producers write details most important first, and then stays where it is as text grows or the reader scrolls; follow pins it to the newest lines and a refresh keeps the reader's place. Capability checks surround fetching, and callbacks receive Effect cancellation signals. Producers must also recheck their own session, revision, and action policy.

`src/boundary/host-activity.ts` owns scoped subscriptions, synchronous projections, widget acknowledgement, and single-owner manager admission. The manager opens on the shared `screen` surface, current only while its binding is active and owns the manager; the surface's external close becomes `binding.close`, and closing aborts detail loads before `done`. `binding.render` is restored after close. The manager does not render questionnaires. `host-activity-view.ts` answers `pi-cosmic-ui/activity/view` discovery so `/activity`, `/subagents`, and `/tasks` open the same manager at a requested section; it exposes only a checked, installation-bound Promise capability that is unavailable without the TUI host. Busy, stale, or cancelled openings reject rather than authorize a fallback, and successful opens resolve only after closing. These named host boundaries are the only places that submit Activity Effects to the session runtime.

## Shared presentation

`boundary/host-input-dock.ts` gives questionnaires a full-width above-editor widget plus an empty overlay for keyboard focus. The shared surface's `dock` placement mounts it and disposes it on every close, including before mount, and hands callers the wrapped overlay handle for hide/resume. Callers retain their prompt lifecycle. Unique widget keys isolate late cleanup from newer presenters. The optional height budget is 60% of terminal rows; Pi owns final allocation and can clip widgets on crowded or tiny terminals. In Pi's fullscreen layout all above-editor widgets share one shrinking slot, so visible docks register in a process-wide presence slot (each extension loads its own module copy) and the Activity widget compacts to a three-row summary while any dock is visible. Manager overlays keep their existing screen viewport.

`boundary/host-surface.ts` is the shared owner of one `ctx.ui.custom` opening. `mountOwnedSurface` is a synchronous callback core with Effect and Promise doors. It owns the factory and done latches, the finish held until `onHandle`, the inert component for late or stale factories, admission beside `custom`, the external close handed out before `custom`, viewport attachment, dock mount and pre-mount disposal, and the pinned-Pi guarded close for overlay placements. Inline surfaces call a guarded `done` directly. `onClose` revokes callback authority before `done`; an admission release runs after `done` and dock disposal; every settlement closes the surface. Callers keep domain lifecycle, error wording, and any render gating: questionnaires, the Activity manager, every inline settings picker, `/tasks`, the `/subagents` fleets and profile dashboard, and `/code-previews health`. `openCommandSurface` is the Promise door for a command's own view: it rejects a failed opening, as Pi's custom Promise does. Other Promise callers map `Failed` themselves. The published `pi-cosmic-ui/testing` subpath (`src/testing/custom-surface.ts`) holds `fakeCustomSurfaceHost`, a Vitest-free model of Pi's custom host (unchanged from 0.86 through the pinned 1.0): synchronous factory, explicit mount, global-pop `done`, non-capturing guards, `setWidget`, and one-shot faults at owned hide, guard creation, `done`, and guard hide.

`boundary/host-settings-command.ts` builds the shared `settings` subcommand, `/<extension> settings`, over core's pure completion and dispatch; each extension adds it to the command core's `registerExtensionCommand` registers. Every workspace settings subcommand uses it. It owns completions, `help` with examples and notes, `status`, optional scopes named before the setting id (with `scopeBlocked` refusals such as an untrusted project), guarded diagnostics, the invalid, missing, and unknown messages, and the scripted and interactive apply. Success runs the extension's `afterApply` and either notifies `id = value` or shows the committed value in an optimistic picker row, through `displayValue` when a scope's own value differs from the effective one. A typed failure shows its message and restores the persisted value; a `stale` failure, or a `show` that reports a newer choice, stays silent; a rejection warns that the settings are unavailable. `openValues` descriptors accept values beyond their presets for `apply` to validate. `onInvoke` runs on every invocation and before each apply. A `required` signal is read once per invocation, and a throwing getter makes the settings unavailable. An `optional` signal is reread for each apply, a throwing getter applies without one, and a rejection stays silent once its signal has aborted. A bare command opens the extension's picker only when `hasCustomSurface` holds and otherwise shows help. `withInvocationAuthority` rebuilds the subcommand for each invocation with the originating-session authority captured then: the shell guards every apply, delayed notification, picker display, and after-apply callback with it, so providers need no checks of their own, and never adapts or mutates Pi context objects. The extension supplies its rows; the session's `picker` opens them as the `<title> settings` list on the `inline` surface. Each change shows at once and settles through the shared apply, a `<scope>:<id>` row applies to that scope, and a per-row latch keeps an older settlement from overwriting a newer choice. `openSettingsList` opens an extension's own list, such as Better OpenAI's grouped one, with the same guarded keybinding, render, styling, and bridge callbacks. `Blocked` reports missing config and `Failed` an unopenable surface.

`src/manager/` contains Effect-free chrome, key resolution/labels, list navigation, list/detail composition, selectors, and settings adapters. `viewport.ts` resolves outer screen bounds: centered 90% width and height at 125 columns and 30 rows or larger, otherwise full terminal bounds. Borders and footer consume that allocation, not extra terminal rows. `boundary/host-viewport.ts` binds a live terminal reader per opening and supplies matching overlay bounds and component height. Pi (0.86 through 1.0) resolves its options callback only at mount but rereads retained options properties during rendering, so the adapter uses getters that must not be copied or spread. Embedded children inherit their parent's allocation; separate overlays resolve from the terminal. The shared surface owns owned-overlay cleanup; callers keep focus and domain lifecycle. `key-labels.ts` also adapts Pi's keybindings into manager `matchesKeybinding`/`keybindingLabel` options, and `configuredKeyLabels` gives every screen's hints the configured labels minus the keys that screen reserves. `ListDetailShell` owns generic selection, pane/layout, scroll, page sizes, and keymap chord state. Actions, confirmation policy, follow policy, domain predicates, and content stay caller-owned. `manager/style.ts` owns the shared full-screen roles: session uses `success`, saved scope uses `border`, identity uses `customMessageLabel`, and values use `borderAccent`. `focusedField` adds `selectedBg`, bold, and `accent` to the active control. These roles use theme tokens, never fixed colors. `listDetailFrame` keeps enclosing frames muted and derives each wide or stacked pane edge from current focus, `listDetailHeading` supplies consistent focused headings with a stable marker gutter, and `detailFieldRows` owns dim labels, readable values, group alignment, and spacing. Callers supply sanitized text and semantic tones and retain wrapping and disclosure decisions. Tasks, the subagent fleet, and Activity use those focus defaults. Screens without pane navigation keep neutral frames. Shared frame helpers bound output, preserve empty sizes and top-only single rows, and frame caller-supplied bodies. Searchable selectors retain selection identity through filtering and theme invalidation and use those helpers. They dim disabled choices and can show caller-provided short hints while retaining full blocked reasons on confirmation. Callers choose the initial selection; selectors never execute it automatically. Model pickers only project already-authorized catalogs. Acquisition, validation, persistence, and lifecycle remain with callers.

`settings-surface.ts` supplies public theme callbacks for focused controls and cyan values, without extending the private settings adapter. Generic selectors keep choices neutral; model pickers explicitly mark model values. Diagnostics panels stay read-only with neutral frames. Manager roles do not change transcript, tool, footer, widget, or questionnaire presentation. `settings-surface.ts` composes caller headers, Pi `SettingsList`, `VimSettingsAdapter`, and the focus/render bridge; it also owns submenu composition. Its host callback guards are injected by `boundary/host-settings-command.ts`, which also owns provider command grammar and copy; the inline opening and close belong to `boundary/host-surface.ts`. `settings-adapter.ts` deliberately couples to pinned pi-tui private `searchInput`, its `setValue`, `applyFilter`, and `submenuComponent`. Esc leaving search clears and reapplies the filter without closing the child. Review this bridge directly on pi-tui upgrades.

`manager/table.ts` measures complete caller-supplied datasets using display widths, reserves columns by priority, and renders stable two-space gaps. Callers retain column policy and cell tones. `managerTabs` keeps the active tab visible when the full strip cannot fit. Full-screen lists focus identity cells separately from status and warning cells; technical inspectors wrap content before calculating scroll windows.

`src/tool/presentation.ts` renders semantic tool headers, status lines, and expansion affordances. It does not own code-preview shells, highlighting, caching, or scheduling. The package root exports only the extension; named subpaths expose shared protocols and presentation components.

## Working row and prompt identity

`src/working/row.ts` owns Pi's working row: its run and prompt state, elapsed and output-rate clocks, and ticker. It is plain presentation state under the effect-v4 exception and feature-local host I/O, whose only effect is a guarded `setWorkingMessage` write. `application.ts` calls it directly from its Pi event handlers, so each event changes the row within the call that observed it. Activation binds the row to the session's context `MutableRef` without writing. Deactivation, including abort and shutdown, clears a running row through that context, stops its ticker, and unbinds it; idle deactivation writes nothing, because Pi resets the row when it rebinds extension UI.

A writable run repaints each second from the shared host ticker pool. A failed write keeps the row writable and retries on the next tick. An unavailable host stops the ticker and freezes both clocks until a later write succeeds. Tool execution and message end pause only the output clock. The outer prompt freezes both clocks and drops output; prompt end restores prior elapsed time. Duplicate agent starts and prompt events do nothing.

A prompt opens only inside a running agent run, and a prompt end applies only while that prompt is open. Agent settlement and deactivation clear both. Pi prompt events have neither prompt nor session identity. A stale start first arriving after replacement while the new agent is active is indistinguishable from a current prompt and is attributed to the replacement session.

## Lifecycle

```text
protocol events -> synchronous registry -> frozen snapshot -> active footer render request
session_start -> application -> layer -> services -> footer installation
agent_start + streaming deltas -> working row clocks -> setWorkingMessage on pool ticks -> agent_end clear
ui_prompt_start -> freeze row clocks -> ui_prompt_end -> resume elapsed
Pi changes -> service refresh -> frozen projection -> render request
session_shutdown -> subscriptions/footer/runtime disposed -> ticker pool rotated and awaited
```
