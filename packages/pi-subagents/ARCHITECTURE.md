# Architecture

`pi-subagents` is an Effect-managed Pi extension for session-scoped child-agent processes. Pi RPC and Claude Code CLI children share one backend-neutral run model while retaining backend-specific protocols and capabilities.

## Source map

- `src/extension.ts` — thin Pi registration entrypoint and child-recursion guard.
- `src/layer.ts` — session Layer composition. The application layer exposes only `SubagentService` and `SubagentProfileService`; filesystem, path, and config-store internals stay private to the composition.
- `src/application/` — tool, command, notification, and session lifecycle wiring.
- `src/boundary/child-process.ts` — child backend dispatch plus the Pi RPC process, session-fork, and process-tree adapter.
- `src/boundary/claude-preflight.ts` — process-cached, single-flight Claude CLI readiness probe (`claude auth status --json`): executable presence and CLI authentication only, run before the first claude-cli spawn; concurrent probes share one process, success is cached per command, and failures are never cached.
- `src/boundary/claude-process.ts` — installed `claude -p` process ownership, CLI-managed authentication, explicit native-tool policy, and NDJSON transport.
- `src/boundary/process-tree.ts` — shared detached process-group termination, including post-leader-exit POSIX cleanup.
- `src/boundary/claude-protocol.ts` — bounded Claude stream-json decoding and backend-neutral event translation.
- `src/boundary/host-child.ts` — child-only `contact_parent` Pi extension and IPC bridge. This headless child-boundary tool intentionally bypasses the parent TUI's `pi-code-previews` shell because no interactive preview host exists in the RPC child.
- `src/boundary/host-profile-resolution.ts` — Pi host model-registry/auth capture plus concrete profile-start resolution. It consumes pure ordered plans, performs automatic Claude preflight and Pi runtime-auth checks before reservation, and builds the concrete backend request and provenance.
- `src/boundary/native-clock.ts` — synchronous native clock isolated for Pi render callbacks.
- `src/boundary/host-environment.ts` — process-role detection.
- `src/boundary/host-notifier.ts` — exception-safe, deduplicated parent delivery for completions, questions, and warnings; routine progress remains projection-only.
- `src/boundary/host-ui.ts` — synchronous immutable fleet projection bridge and disposable manager repaint ticker.
- `src/config/` — the single profile-policy persistence door. `schema.ts` owns tolerant Effect Schema decoding and bounds, `options.ts` owns global/project merge and deny matching, and `store.ts` reads global `<agent-dir>/pi-subagents.json` plus trusted project `<cwd>/<CONFIG_DIR_NAME>/pi-subagents.json` documents. Field/item corruption is recovered independently; unreadable or invalid JSON and a declared unsupported `version` fail activation closed with path-safe diagnostics so hard denies are never silently discarded and a partially understood document is never applied.
- `src/profiles/` — fixed profile vocabulary and pure role guidance (`definitions.ts`), profile/policy contracts (`model.ts`), deterministic ordered candidate planning (`resolve.ts`), and the session-loaded `SubagentProfileService` (`service.ts`). Built-in routes are intentionally model-neutral parent fallbacks; profile definitions independently carry role-specific effort defaults, with `delegate` inheriting parent effort. Those defaults are soft preferences: only per-call and candidate-configured efforts are hard requirements, so a model that cannot honor a soft preference starts and reports its effective level.
- `src/run/` — backend/capability and run models, normalized child events, transport-specific Pi protocol decoders, errors, bounded structured child-session timelines, projection, and scoped fleet owner. `service.ts` remains the sole registry/lock owner and reauthorizes model denies immediately before reservation; `completion.ts`, `rate-limit.ts`, `process-lifecycle.ts`, and `control.ts` are internal policy/orchestration rooms. `coordination.ts` owns the shared orchestration-tool denylist, parent-message bounds, profile-guidance injection, and child prompts; the denylist is still applied at both the tool and the process boundary. `model-catalog.ts` is the pure explicit model-discovery and selector-resolution room: accepted-selector discovery lines with a truthful 100-result truncation marker (shown only when matches were actually dropped), AND-semantics ranked search, deterministic Pi selector resolution, and claude-cli/Pi selector mismatch detection.
- `src/tools/subagent.ts` — the focused agent-facing tool suite (`models`, `start`, `list`, `status`, `await`, `send`, `reply`, lifecycle, and rename), with non-overlapping parameter contracts, bounded per-agent launch validation, partial-failure projection with machine-actionable failure codes, and cooperative `pi-code-previews` shell rendering.
- `src/ui/session-output.ts` — shared width-aware child-session presentation for fleet details, with grouped activity, Markdown final reports, and optional technical metadata.
- `src/settings/controller.ts` — `/subagents` command registration.
- `src/ui/` — pure responsive fleet presentation, run-state glyph/color projection, scroll projection, and terminal-text sanitization. Fixed-width activity frames and responsive grouped footer fitting come from `pi-cosmic-ui/manager`, shared with `/ps`.

## Ownership

### Runtime and registry ownership

`SubagentService` is the only run-registry owner. Every child process is acquired in a child Scope forked from the session runtime. Closing the session runtime aborts and terminates every process, settles pending requests, and clears the host projection. A successful `session_tree` event replaces that runtime, so children rooted in the abandoned branch are stopped silently and the selected branch starts with an empty fleet.

### Backend startup and protocol validation

Profile discovery and launch share one contract: `subagent_models` exposes the configured default profile plus all seven fixed profiles, their default context and effort, configured candidate order, static eligibility/skips (including fork availability), and fallback alongside accepted concrete `backend` and `model` selectors; aggregate discovery text is bounded and Claude executable/authentication/model readiness is checked only at launch. `backend: "auto"` resolves the selected profile or configured `defaultProfile` before service reservation; a concrete backend/model may override routing while retaining profile guidance. Built-ins contain no opinionated model aliases and explicitly fall back to the parent. Launch validation resolves Pi selectors deterministically against the authenticated registry — exact canonical `provider/model` first, then a bare model ID only when it identifies exactly one provider. Ambiguous bare IDs fail listing every canonical authenticated candidate, unknown selectors fail with near matches, and a Pi selector supplied to claude-cli fails with a `backend_model_mismatch` code before any process work. Claude aliases are never substituted for exact-version requests; an exact Claude version requires its full model ID. Invalid claude-cli combinations (forked context, `off`/`minimal` effort, untrusted projects, Pi selectors) are rejected at the tool layer with structured codes and re-checked in `SubagentService.start`, so they can never reach a spawn. Automatic candidate selection resolves effort in strict precedence order — per-call override, candidate effort, profile default, parent effort — before compatibility/readiness checks; only the first two are hard requirements, while profile-default and parent efforts are soft preferences that never fail a model reporting a different effective level. It then skips denied, discouraged, unavailable, incompatible, and preflight-failing candidates in declared order; only `fail` and parent fallback exist. Claude candidates keep their specific `claude_context_unsupported` skip reason even when forked context is additionally unavailable, while fork-viable candidates and the parent fallback report `fork_context_unavailable`. An identical parent fallback is not retried after an explicit parent candidate. Denied models are hidden from launch-ready selector lines, Claude selector lines are hidden in untrusted projects, explicit discouraged selections carry a visible warning, and `SubagentService.start` reauthorizes hard denies before capacity or writer reservation. Claude alias/full-ID policies cover dated members of the same model family. Automatic Claude candidates run the cached CLI preflight at most once per agent resolution and before reservation, so candidate fallback remains strictly pre-start. Only `oracle` defaults to forked context; an unavailable parent branch fails instead of degrading to fresh.

Child Pi processes run in RPC mode. Standard Pi RPC uses stdin/stdout; a separate Node IPC channel carries `contact_parent` requests and peer-awareness notices. Claude children run the installed `claude -p` command with streaming JSON input/output, the CLI's normal authentication resolution, safe mode, and backend-owned read-only or writer tool allowlists. Before the first claude-cli spawn in the extension process, the process boundary runs a bounded, cached, single-flight `claude auth status --json` preflight that verifies only executable presence and CLI authentication — never model availability. Explicit negative auth status carries `claude_cli_unauthenticated`; missing executables carry `claude_cli_not_found`; other non-zero or incompatible probes carry `claude_cli_preflight_failed`. Failures are not retried as transient initialization failures and are not cached, so a corrected installation or login is picked up on the next launch. The Phase 1 flag contract is verified against Claude Code 2.1.220; `--tools` restricts the available native tools, while role-specific `--disallowedTools` entries provide a second deny layer. Claude raw messages are decoded and translated before entering shared run state. Terminal result decoding requires the result discriminant but tolerates optional-field drift. Assistant text is accepted up to the transport envelope and clipped only at bounded projection/session-output boundaries; oversized terminal report text is likewise clipped at the existing projection bound. Structured Claude rate-limit events distinguish allowed requests with unavailable overage, paid-overage continuation, and actual rejection: all utilization updates refresh the UI, while parent notifications are limited to the first 80%, 90%, and 95% crossing in each reset window, the first paid-overage continuation, and rejection. Active or available paid overage remains non-terminal and uses allowance-exhaustion wording. Only rejection combined with explicitly unavailable overage starts a short grace period for the authoritative result envelope; ambiguous limit events defer to that result rather than terminating a usable session. Backend capabilities prevent unsupported operations from being approximated: Phase 1 Claude runs support fresh start, completion, stop, local rename, and continuation after completion, but not steering, interruption, forked Pi context, peer notices, or parent contact. Agent-facing tool descriptions, detailed status output, and typed capability errors expose those limits with exact-tool recovery guidance before or after an attempted operation. The process boundary tags transports, and each is decoded against only its permitted bounded protocol schema. Pi blocking parent questions execute sequentially, and the parent claims each question before sending its single reply. Fresh Pi children use a dedicated session directory with filesystem-safe session/run segments. Forked Pi children receive a private copy of the stable parent branch, never the live parent file; non-portable provider thinking blocks are removed from that copy. Runtime-only Pi API keys cross the process boundary through an ephemeral environment bootstrap rather than process arguments.

### Process lifecycle and cleanup

Child finalization bounds transport writes and uses backend-specific graceful shutdown before process-tree termination. POSIX cleanup signals the detached process group even after its leader exits and performs a final forced group sweep. Live Windows trees use a bounded `taskkill`; once the leader has exited, PID-based sweeping is deliberately skipped to avoid targeting an unrelated PID-reused process until a native Job Object adapter is introduced. Completed processes close their owned scope immediately while session identity and output remain in the run record; a later resume reacquires a process from the Pi session file or Claude session ID. Claude initialization has a separate 60-second readiness deadline. Because stream-json emits `system/init` only after receiving its first user frame, the service submits the initial task frame before awaiting initialization, then verifies the complete role-specific resolved tool set for both read-only and writer runs before accepting startup. A single fresh-process retry is allowed only for transient spawn, initialization-stream, or readiness failures; policy, authentication, model, permission, and limit errors fail without retry. Steady-state RPC remains bounded to 10 seconds. Process exit is observed only after stdio closes, buffered RPC events drain before exit settlement, exited handles cannot signal stale PIDs, and failed writers retain ownership until external scope cleanup completes. Stop cleanup continues independently when its requesting tool is cancelled. Resume waits at most ten seconds for prior cleanup and reports `cleanup_timeout` rather than polling forever; capacity failures distinguish active saturation from transient cleanup-owned slots.

### Controls and settlement

RPC registration, failure ownership, and stop-time response sweeping are serialized by the service lock. RPC transport sends race their response Deferred so stop or run failure interrupts a blocked send promptly. Terminal state transitions are atomic and monotonic; stop is a no-op for terminal records, and starting or terminal records may be renamed locally without contacting a process. Foreground questions, pauses, and settlements release the owning tool waiter exactly once. Accepted replies, interrupts, and resumes commit in the session scope if their requesting tool is cancelled. Interrupt settlement is correlated independently from the RPC response so delayed abort responses cannot turn a pause into completion, and post-pause parent contacts are ignored. Post-send state races and interrupt response timeouts carry explicit outcome-uncertain codes and tell the parent to inspect status before retrying an operation that may already have applied. Child-controlled stdout, stderr, transcripts, identifiers, and management messages are bounded; stderr included in direct boundary errors is sanitized and redacted. Successful and failed Claude result envelopes both contribute their reported usage before terminal settlement. Unknown protocol values are decoded with Effect Schema before entering run state, including normalization of Pi's structured RPC model descriptor and Claude's string model identifier. Token-delta activity publication is coalesced to one update per second so streaming children do not repeatedly clone and render the fleet.

### Completion delivery and notifications

The service owns revision-driven fleet waiters, completion claims, acknowledgement generations, and an Effect-clock delivery scheduler. The public await conditions are `all_finished` and `any_finished`; “finished” projects the internal completed, failed, and stopped terminal states into user-facing language. Either condition also returns early when a selected Pi run enters `waiting_for_parent`, rendering its question and exact `subagent_reply` call so the parent can answer and await again instead of deadlocking behind its own active tool call. `await` acquires selected-run claims with an atomic Effect bracket before sleeping on revision Deferreds, updates one partial tool result on state changes, and releases claims on success, attention, timeout, or cancellation without touching child scopes. `status` and `await` hold a completion claim through generation receipt rendering and consumption, preventing automatic delivery from racing a full tool result. Only reports represented in full by the bounded tool result are consumed, while truncated reports remain notification-eligible. Unclaimed completions are batched and delivered with generation IDs. The host notifier sizes every chunk using its actual continuation header, resets deduplication at session deactivation, and acknowledges only successfully sent chunks. Unacknowledged generations retry indefinitely with exponential backoff capped at 30 seconds. Steer delivery joins an active orchestration run instead of accumulating behind its final response. Routine progress is projection-only; questions and warnings remain actionable parent messages. Non-triggering warnings use steer delivery so they appear immediately while the parent is idle or after its active tool batch, rather than waiting for another user prompt.

### UI and projection ownership

The UI and host notifications consume immutable projections. Await progress and completed start/await cards carry immutable run snapshots in tool details; each run snapshot persists its profile plus selection source/candidate index, reason, skipped candidates, and policy warning. Model-facing status/start/await output renders that provenance, compact cards identify the profile, expanded cards show selection details, and `/subagents` exposes the complete provenance under technical details. Run history is the structured `sessionEvents` timeline plus `finalText`, with no parallel string transcript. The renderer uses shared humanized state labels, status-aware headers, the fleet state palette, and Pi’s thinking-effort palette. Width-aware summary components align wide columns, preserve names and statuses before truncating models, and fall back to multi-line narrow rows. Await projections show the same name/model/effort/status fields as completed summaries, animate active glyphs from the cooperative shell’s render clock, and clearly project timeout, cancellation, and first-finished outcomes. Collapsed cards and partial launch failures stay compact and advertise expandable reports explicitly. Expanded bounded reports use the host Markdown component; model-facing tool content independently retains the full report for completion acknowledgement. They never own child sessions or processes. Session startup activates no runtime when cooperative tool registration throws; it shuts down the slot and emits one bounded host error notification instead of exposing a partially active command/UI-only extension.

## Write coordination

Every launch declares `writeIntent: "writer" | "read-only"`. `subagent_start` has one canonical request shape: a required `agents` array containing one to twelve independent per-agent specifications, with at most one foreground item per call so one child question cannot be hidden behind another foreground waiter. Launch failures are reported by item while successful peers remain owned by the session service, and foreground starts publish progress after process readiness before waiting. The remaining agent operations use focused schemas so provider-generated optional fields cannot introduce unrelated target or action forms; only interrupt, resume, and stop share `subagent_lifecycle` because they have the same run-ID-oriented contract, and its optional message is valid only for resume. Multi-target status, guidance, and lifecycle calls collect per-run successes and typed failures instead of failing fast after potentially applying or resolving an unreported subset. Duplicate IDs are normalized, stale status IDs remain model-visible beside valid results, and failure codes are rendered in tool content rather than existing only in render metadata. The service permits only one active writer in the shared cwd. Pi writers receive the parent active tools except recursive orchestration tools. Pi read-only children receive only the conservative inspection allowlist (`read`, `grep`, `find`, `ls`, and the web content tools); shell, mutation, orchestration, and unknown extension tools are excluded at both tool resolution and process launch. Claude children instead receive a backend-owned native-tool allowlist: read-only runs omit and explicitly deny mutation and shell tools, while writer runs add Edit, Write, and Bash. Read-only Claude runs still permit WebFetch and WebSearch, so read-only describes local workspace mutation rather than network isolation. Pi peer notices make shared-workspace concurrency explicit. True parallel writers are deferred until isolated worktrees are implemented.
