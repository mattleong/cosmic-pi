# Activity

The shared Activity view behind `/activity`, `/subagents`, and `/tasks`, and the protocol producers use to publish into it. See the [README](../README.md) for an overview. [ARCHITECTURE.md](../ARCHITECTURE.md#activity) maps ownership and links the grouping, retention, and allocation implementations.

## Activity view

`/activity`, `/subagents`, and `/tasks` open the same full-screen, two-pane manager titled **Activity**, with **Subagents → Tasks** sections (plus **Attention** for standalone questions still waiting on someone). Empty sections are omitted, and a settled standalone question leaves Attention because its answer lives in the transcript. The latter commands select matching standalone work first, or reveal a matching nested item; they do not filter other sections away. When Activity is unavailable, `/subagents` and `/tasks` show a notice instead. Ordinary `/activity` preserves the session selection and zoom when reopened.

Nested work appears beneath its explicit owner. Queued agents show as queued until they start, and work cancelled before it started shows its producer's reason beside its row.

The persistent view normally uses up to eight rows, growing for visible failures up to half the terminal height so the conversation and editor stay visible. Overflow notices keep attention counts visible; very narrow views combine attention into a total rather than imply none. Finished detail leaves the persistent view, but a failure that finished in the last ten minutes stays countable on one muted line pointing to `/activity`. A "Needs you" heading appears only for waiting items the checklist cannot show itself. While an input dock such as a questionnaire is on screen, its own waiting rows are left to the dock; a hidden request that offers a `resume` action shows its producer's summary, such as `/ask-user to resume`, as its status. Section headings appear only in the full-screen manager, where they lead with what needs attention so a clipped heading keeps it.

Rows lead with their title, followed by a quiet suffix: the agent's profile, or `task` for commands (questions need none, since their glyph and status say what they are). They also show state, elapsed time, and an explicitly awaited marker; model routes appear only in technical details. Human input ("needs you"), parent waits ("waiting"), blocked work, and failures are counted separately; paused work is counted with live work rather than as attention. Use shared arrow/Vim navigation and page keys: `h`/Left collapses or returns to the parent row; `l`/Right expands, then inspects; Enter inspects a section summary or source details. The right pane previews the selected source at once, loading its details and keeping the preview current while the tree has focus; inspected details stay put for reading until refreshed or followed. Detail leads with the status, then the provider's sections such as a failure's cause, a report, or output. `?` expands the hint bar into a full help panel, `z` zooms, and `w` cycles only through human-input attention. Sections show summaries only and have no actions.

Number keys invoke the displayed source's actions. Source shortcuts are `x` stop, `i` interrupt, `u` resume, `m` reply/message, `e` rename, and `c` clear; `?` lists every action key. Esc or `q` declines a confirmation. An action is retargeted to the current revision only when the row still offers an identical action (same id, label, confirmation, and handoff), so unrelated progress doesn't void the choice. `r` refreshes lazy details without moving the viewed log slice; `t` toggles the Technical section: the provider's identity and diagnostic fields plus source identity and revision metadata. `f` follows the selected source from either pane, refreshing on every change and keeping the newest output in view; it is off by default. Selection changes, follow-off, and close revoke pending delivery and cancel the host request. Esc returns to the list, then closes; `q` closes immediately.

## Producer protocol

Producers import `registerActivityProvider` and `ActivityItem` from `pi-cosmic-ui/activity`. Register once per producer session with `pi.events`, the exact `ctx.sessionManager.getSessionId()`, a stable provider ID, a synchronous `snapshot()` returning plain summaries, and `invoke(itemId, actionId, revision, signal)`. Call `publish()` after changes and `dispose()` during session teardown. `parent: { providerId, itemId }` is explicit ownership, never an inference from labels or start times. `registerRevisionedActivityProvider` wraps this for producers whose details and actions must be current; it republishes on the supplied change sources and returns the disposer. Its action callback receives `invocationCurrent()` as its fourth argument: recheck it after user input or another await before changing source state. For tests, `fakeActivityHost` from `pi-cosmic-ui/activity/testing` answers discovery and acknowledges registration, and `activityGalleryFrames` from the same subpath renders items through the real widget and manager, with chosen items' details opened.

Every item includes a stable `id`, `kind`, `title`, `status`, and `revision`. Statuses distinguish pending, running, paused, stopping, blocked, needs-input, done, failed, and cancelled. Needs-input rows wait on a decision and show as attention, not warnings; paused rows are held work; blocked rows and failures are problems. Every needs-input item must supply `inputTarget: "user" | "parent"`; other statuses cannot carry it. Blocked rows may supply `blockedReason: "parent-review" | "file-access-review" | "file-access" | "write-containment"`; other statuses cannot carry a blocked reason. Optional `startedAt`, `endedAt`, and `updatedAt` are finite epoch milliseconds for elapsed/update information. Optional `summary`, static `detail`, and `{ id, label, confirmation?, handoff? }` actions must contain display-safe information, not credentials or raw provider errors. Destructive actions must supply a `confirmation` prompt that describes their scope, including affected descendants. Set `handoff: false` on actions that open no UI, such as stop, so they run with the manager open. Snapshots are limited to 512 items per provider and 16 actions per item, and details to 16,384 characters; `ACTIVITY_LIMITS`, exported from `pi-cosmic-ui/activity`, lists every bound the protocol enforces. The registration helpers publish the first 512 items and the first 16 actions of each item, so producers that need a different selection should clip to these bounds themselves. Use optional `getDetail(itemId, revision, signal)` for logs or other lazy detail. It resolves to a plain string, shown verbatim, or an `ActivityDetail`: ordered `sections` of `{ title?, body, format? }` that lead with what the user came for (a failure's cause, a report, recent output), and optional `technical` `{ label, value }` fields such as IDs, PIDs, cursors, paths, and routes, which appear only behind the Technical toggle. Use `format: "markdown"` only for agent-authored prose; logs stay verbatim. Malformed sections or fields are dropped individually; anything else is rejected. It runs when a source is selected, previewed while it changes, refreshed, or followed, never on render, resize, or theme invalidation. Revisions must change whenever the item or its available actions change. Keep them per item, for example a hash of the item's published fields, so one item's progress never makes another item's action stale.

Nested items are ordinary items whose `parent` names their owner; attention rolls up to owners and sections. [ActivityService](../src/activity/service.ts) validates snapshot consistency, such as unique item and action IDs; invalid publication withdraws rows, starting counts, and acknowledgement together. [Service tests](../tests/activity-service.test.ts) cover rejection and recovery, while [group summaries](../src/activity/group-summary.ts) derive display state from accepted data.

`onAvailability(available)` and `isAvailable()` report acknowledged replacement ownership, not merely that Cosmic UI was discovered: keep the old panel until availability becomes true and restore it when availability becomes false. RPC and headless sessions never acknowledge the TUI replacement. An envelope that bypasses the helpers and exceeds these bounds withdraws acknowledgement like an invalid one, and the next valid publication can recover.
