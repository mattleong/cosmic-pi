# Suite UI conventions

Every visible Cosmic Pi surface follows these conventions: tool rows, the footer, Activity, settings, panels, questionnaires, notices, and command output. They keep the suite reading as one product. [Tool presentation](tool-presentation.md) adds the rules specific to tool rows and issues.

Every surface must read well at both a desktop terminal (180×56) and a phone client (57×46). Check both sizes for every surface you change, as described in [Reviewing a surface](#reviewing-a-surface).

## Reviewing a surface

Review every changed surface live, at 180×56 and 57×46, in a throwaway Pi session opened in a Rex tab. Extensions load from this checkout, so the session shows the working tree.

```sh
created=$(rex window new -s "$REX_SESSION" review -c "$PWD" --focus=false --json -- pi)
block=$(printf '%s' "$created" | jq -er '.block_ids[0]')
rex block call -s "$REX_SESSION" -b "$block" resize '{"columns":57,"rows":46}'
rex send -s "$REX_SESSION" -b "$block" '/activity' && rex send-key -s "$REX_SESSION" -b "$block" enter
rex capture -s "$REX_SESSION" -b "$block" | tail -n 46          # the visible screen as text
rex capture -s "$REX_SESSION" -b "$block" --format=html > screen.html   # with colours
```

- Drive the surface with `rex send-key` (`enter`, `escape`, `tab`, `down`, letters). Wait about a second after startup and after each key before capturing. Close the session with `/quit` when done.
- Look at real data: a full model catalogue, long tool output, and enough rows to scroll show problems that small fixtures hide.
- Never confirm a change to saved settings while reviewing; open pickers and back out with Esc.

## Separators

- Use `·` (middle dot with spaces) between facts everywhere: tool rows, footer, Activity, notices, and hint bars.
- Don't use `•`, `|`, or `│` as inline separators. Box-drawing characters are for borders, gutters, and tree structure only.

## Key hints

- A hint is a `Key Verb` pair with a Title Case verb, such as `Enter Inspect`. Pairs are joined by `·`: `↑↓ Move · Enter Inspect · Esc Close · ? More`.
- Name keys the way `formatKeyIds` does: `Enter`, `Esc`, `Tab`, `Space`, `PgUp`, `PgDn`, arrows as `↑↓←→`, and modifiers as `C-g`, `A-x`, `⇧Tab`. Show the configured key when Pi has one. Arrows inside a hint name keys; they are not glyphs.
- Configured keys from Pi go through the same formatting. A surface given `keybindingLabel` reads its keys with `configuredKeyLabels`, and a surface built on pi-tui lists reads Pi's `tui.select.*` keys with `piSelectHintKeys`. The default bar names only each binding's primary key (`binding(id).key`, `primary(id)`); the binding's other keys, such as `C-c` for cancel, join `exitAliases`. Up and down read as one label, `↑↓` (`movementKeyLabel`), never `↑/↓`.
- A run of consecutive digit keys reads as one range joined by an en dash, never a hyphen: `1–2 Actions`, `Enter/1–9 Choose`. Build it with `keyRangeLabel(first, last)`, which names a one-key run as the key alone.
- Keys a host handles beside a shared component belong in its bar as pairs, never in subtitle text: the model picker's scope switch reads `Tab All models` (`SearchableSelectPage`'s `hints`).
- Keep the default bar short. Put aliases (`j/k`, `h`, `l`, `q`, `C-c`, `Space`, `C-u/C-d`, `gg/G`) and less common keys behind `? More`, which toggles to `? Less`.
- The expanded bar is a superset. It keeps every default pair and adds to it; it never replaces them. `keyHintBar({ hints, more, exit, exitAliases }, expanded)` enforces this, and every bar with an exit goes through it (`keyHintBarParts` or `framedKeyHintBar` when the surface needs the pieces).
- Expanded, keys that share a verb merge into one pair at the default pair's place, primary key first: `↑↓/j/k Move`, `Enter/Space/l Toggle`, `←→/Tab/⇧Tab/h/l Switch`, and the exit `Esc/C-c/q Close`, `Esc/h Back`. An alias whose verb differs gets its own pair, such as `q Close` beside `Esc/h Back` in a nested view. Never show two pairs with the same verb (`↑↓ Move · j/k Move`, `C-c Close · q Close`). `keyHintBar` and `keyHintBarParts` merge them, a `more` pair with the exit's verb joins the exit, and a bar built without them uses `mergeKeyHintPairs`.
- Show one hint line per surface. A nested view replaces its parent's hint; it never stacks a second one.

### Action keys

- Each action has exactly one key. Use its letter wherever one exists: `x` Stop, `i` Interrupt, `m` Message, `e` Rename, `c` Clear.
- An action list shows that same key, `[x] Stop`, and the hint bar names the same key, `x Stop`. Never offer the same action under a letter in one place and a digit in another.
- An action reads the same on every row: `[x] Stop` on a parent and on its child, never `Stop agent` on one and `Stop` on another. The pane and the confirmation already name the item. Producers supply the label; Activity shows it as given.
- A confirmation names the item and what else the action affects, such as `Stop "Review authentication" and its 5 subagents?`. Never write `this agent`.
- Digits are only for actions that have no letter, and then the list and the hint both show the digit.
- An action on a whole section, such as `c Clear all finished`, is offered on the section heading. Its key still works from the section's rows, where only expanded help names it.

### Wrapping

- When a bar doesn't fit, wrap it between complete `Key Verb` pairs: `wrapKeyHints(hint, width)` returns the rows, and `keyHintRows(hint, width, style)` returns them styled with the surface's one-column gutter. Never clip a pair mid-way.
- Wrapping takes rows; it never drops essential hints. At every width, including 57 columns, the bar keeps Move or Scroll, the primary action, and the exit (`Esc Close`, `Esc Back`, or `Esc Cancel`). Only `? More` content may wait for expansion.
- A framed surface puts its whole bar in the bottom border when it fits. Otherwise the border keeps the exit and `? More` (or `? Less`), and the remaining pairs wrap into rows above it, set off by a divider: `framedKeyHintBar(bar, expanded, inner)` returns the border text and the overflow, and `framedBodyWithHints` places the wrapped overflow rows. This holds for expanded help too: the border never empties while its pairs move into the body. Never choose a shorter bar by dropping pairs, and never clip the border without `…`.
- Each pane of a multi-pane surface names its own movement and what Enter does there, such as `Enter Open` in a list and `Enter Change` on a field.
- Offer only keys that do something now. An empty list drops Move, Inspect, and its item actions; the exit and `? More` stay.
- Running work opens following its newest output, with `f Unfollow` in the bar; other work opens at its top, so a question or a failure's cause is read first. Offer `f Follow` only for work that has started and not finished.
- A key the user needs now moves into the default bar: `w Next input` shows while something waits on the user, and at no other time.
- One key has one verb everywhere it appears: Activity's `w` reads `w Next input` in its banner and in its help.

## Leaving a surface

- `Esc` backs out one level, or closes the surface at the top level.
- Label it `Esc Back` when nested, `Esc Close` at the top, and `Esc Cancel` for a pending decision. `exitKeyHint(level)` produces each one.
- Show only that primary exit key. Aliases such as `C-c`, `q`, and `h` (in Vim-style lists) work where they apply but appear only in the expanded `? More` help, never as `Esc/C-c` in the default bar. `q` and `h` are aliases on non-text surfaces only.
- Expanded, every key that leaves the level is named, in one pair: if `C-c` closes a settings surface, picker, or panel, its expanded exit reads `Esc/C-c/h/q Close` like Activity's `Esc/C-c/q Close`.
- A surface with a pending sub-state backs that out first: with a settings or picker filter applied, `Esc Clear` clears the filter, and the next `Esc` closes. A picker opened straight into search, where the search is the whole surface, reads `Esc Cancel` instead.
- Nothing closes on "any key".

## Lists and selection

- Mark the focused row with `›` (`LIST_CURSOR`) in every list, picker, and tree. Never let a pi-tui default such as `→` stand in for it.
- Use `[ ]`/`[x]` for multi-select and `( )`/`(•)` for single-select (`selectionMarker`).
- A picker that chooses a value marks every row `( )` and the current value `(•)`, so the current value stays visible while the cursor moves: settings choice lists do this, and `SearchableSelectPage` does it when given `markedValue`. Action and navigation lists carry no marker. Don't repeat the marker as `(current)` text.
- A picker's inherit row reads `( ) inherit (value)` with the value it would apply, such as `( ) inherit (low)` or `( ) inherit (claude-bridge/claude-opus-5-5)`. It is the only row that names the inherited value: no `(profile default)` row repeating another row, and no `Current Pi model →` label. It comes first in every choice list, before the pinned values.
- Show scroll position as `n of N` or `n–m of N`. A pane heading says what its scrolled-off rows hold instead, `Items · 2 more above · 7 more below`, or which lines show, `Details · lines 1–22 of 27` (`paneHeadingText`).
- A long choice list may group its rows under headings that can't be selected, such as models under their provider (`SearchableSelectPage` choices' `group`). A row then drops what its heading says (`gpt-6-luna` under `openai-codex`), while search still matches the whole `provider/model`. Ungrouped rows, such as `inherit (…)`, come first; `n of N` counts choices, not headings; and a heading scrolled off the top stays on the first row.
- The row Enter would select keeps its highlight while a search field takes the typing, so the cursor never disappears into a long list.
- An empty list says what will appear there, such as `Subagents, tasks, and questions appear here.`, not just that nothing has happened yet.
- What needs the user comes first: Activity lists Attention above Subagents and Tasks, and opens on the first item waiting for input.
- Enter on a tree's section or group heading folds or unfolds it (`Enter Fold`, `Enter Unfold`, like `h/l Fold`). A heading is never a pane to enter, though its summary may preview beside the list. Folding never moves the preview.
- A tree's `/` filter keeps the owners of every match and only the headings that have one. While typing, the bar reads `Type to filter · ↑↓ Move · Enter Done · Esc Clear`; the list heading counts the matches (`Items · 3 matches for "fail"`), and an empty result says so (`No items match "zzz".`).
- A preview shows the short form of each fact, such as one line per tool call; the output behind it shows once the item is inspected with Enter.
- A heading over a group of rows reads as a heading, with its rows indented beneath. A note such as `No project sets saved` is muted and never drawn in a selectable row's colour.

## Frames

- Text inside a frame keeps a one-column gutter from each border: `│ Items`, `│ Choose model`, `│ › (•) provider/gpt-6-luna`, `│ Status: ready`. This covers list-detail panes, pickers, panels, confirmation text, and wrapped hint rows. `framedGutter(rows, paneWidth)` sets rows in, and content renders at `paneWidth - 2 * FRAME_GUTTER`.
- A right-aligned column, such as elapsed time, also stops one column short of the border or pane divider.
- A two-pane surface sets its rows by width alone (`managerDensity`: narrow rows wrap and drop columns below 60 columns) and arranges its panes by width and height (`managerArrangement`): side by side from 100 columns, the list above the detail below that, including on a tall narrow frame such as a phone at 57×46. Only a narrow frame under 30 rows shows one pane at a time, where Enter opens the detail. In a stacked arrangement Enter moves focus to the detail and the list stays in view.
- A confirmation keeps the surface in view: its prompt wraps in a band above the bottom border, set off by a divider (`framedBodyWithPrompt`), and the border names the decision keys (`x/Enter Stop · Esc Cancel`). The panes above show no focus until the decision is made.
- A host can place a short choice list inside one of its panes: `SearchableSelectPage.renderBody(width, height)` draws it without a frame and `keyHints(inner)` returns its bar for the host's border.
- Short choice lists, menus, name prompts, and confirmations stay inside the surface that opened them; only a list too long for a pane, such as the model picker, takes the whole screen. A prompt band whose rows must not wrap, such as a text input, passes `framedBodyWithPrompt` its lines already fitted.
- Entering or leaving a detail pane keeps the line at its top in place; a followed detail stays on its newest line.
- A pane scrolled into a section keeps that section's heading, such as a scope or a candidate, on its first line.
- A tabbed surface names its tabs in its top border, the current one highlighted and the others muted, and never repeats the tab's name as a title, rule, or pane heading. One status row under the border holds the tab's standing context, such as `Based on Global/nightly · 2 profiles changed`; a transient message (progress, a finished change, an error) takes that row while it applies.
- A picker's title names the choice (`Choose model`) and its subtitle only what the border's breadcrumb doesn't (`Scoped models`). A short title and subtitle share one line.
- Attention and failure counts in a frame title take the tones their row glyphs use.

## Glyphs

Each glyph has one meaning, suite-wide. Don't introduce a glyph that isn't listed here, and don't reuse a listed glyph for something else, such as `○` or `✓` for an unanswered tab or a static tab icon. Add a row here in the same change that adds a glyph.

### Status

| Glyph                           | Meaning                                                                                                                                                     |
| ------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `✓`                             | Succeeded or done                                                                                                                                           |
| `✗`                             | Failed or error                                                                                                                                             |
| `⚠`                             | Warning                                                                                                                                                     |
| `ℹ`                             | Information: an expanded-only note that is neither a problem nor a result                                                                                   |
| `?`                             | Waiting on the user, or on an agent's reply or decision (attention)                                                                                         |
| `⊘`                             | Stopped or cancelled                                                                                                                                        |
| `≈`                             | Uncertain: the outcome could not be confirmed                                                                                                               |
| `‖`                             | Paused                                                                                                                                                      |
| `○`                             | Queued or not started                                                                                                                                       |
| `◌ ◔ ◑ ◕` (animated)            | Starting                                                                                                                                                    |
| `⠋ ⠙ ⠹ ⠸ ⠼ ⠴ ⠦ ⠧ ⠇ ⠏` (spinner) | Running, on a surface that redraws                                                                                                                          |
| `◒`                             | Stopping                                                                                                                                                    |
| `•`                             | Neutral: no verdict, such as work still running when a saved snapshot was taken (where a spinner would freeze) or a call that returned without pass or fail |

`SUITE_STATUS_GLYPHS`, `managerActivityGlyph`, and `managerNoticeGlyph` own these; use them instead of literals.

## Settings

- Every `/<extension> settings` surface opens the same way: a blank row, then the accent title `<Name> settings` at column 1. Pass the title as `openSettingsList`'s string `header`; custom surfaces use `settingsSurfaceHeader`. A nested list or choice list puts its own title and description in the same column.
- Booleans read `on`/`off`. Automatic choices read `auto`. An inherited value reads `inherit (value)`, showing the value that applies, never a bare `inherit` or `parent`, on every surface: rows, choice lists, pickers, and tool output.
- A group's summary shows the short values in effect, inherited or not, most important first, such as `on · 8 running · 256 KB per task`. It never reads `inherit` or `inherit all`.
- A nested list is titled with the label of the row that opened it (`Fast mode`, `Image tool`, `Global`).
- A picker lists an inherited value as its own row, `( ) inherit (low)`, beside the pinned values, never as a `(profile default)` row that repeats one of them. A narrow column drops an inherited model's provider, `inherit (claude-opus-5-5)`, rather than clip it.
- A row's description names the session's value as a sentence: `On in this session.`, `This session uses 1 MB.`
- A setting's label names it without its group, since help, status, and confirmations show it alone. Facts no row shows, such as diagnostics, follow the rows as titled sections of `Name: value` lines.
- A saved change shows at once everywhere it is visible: after a save, every inherited `inherit (value)` label, choice list, and group summary that depends on it reflects the new value within the same invocation. A group whose rows depend on another group's values passes `children` as a function that reads the owner's current state, including a value put back after a failed optimistic save. The shared surface re-reads every group `summary` each time it draws, and re-derives an open group's rows, values and choice lists alike, when it opens and whenever any save settles, shows its value, or rolls back, keeping the cursor on the same row; a choice list open from that group follows too, keeping its cursor on the same choice (the inherit choice stays focused as `inherit (8)` becomes `inherit (16)`). A row with its own save still pending keeps the value it shows until that save settles.
- `createSettingsChoiceSubmenu` puts inherit choices first; owners don't order them. A table cell may drop `inherit (…)` around a value only when keeping it would clip the table's main column.
- A setting that applies only after a reload says so in one wording: `Changes apply after /reload.` in descriptions, help, and status notes, and `applies after /reload` in a confirmation. Never "take effect".
- An interactive surface posts no notice for a successful change; the row shows the new value. A failed change is reported (a rejected value as a warning, a failed save as an error) and restores the saved value, even when it settles after the surface closed. A command-line change (`/<ext> settings <id> <value>`) confirms with `Label: value`, led by its scope and followed by a note when it has one: `Global · Running at once: 16 · applies after /reload`.
- Values read as people say them: `Shared checkout`, not `shared-checkout`. Sizes and durations use `formatBytes` and `formatDuration` (`256 KB`, `2s`, `inherit (256 KB)`), and units stay out of labels. Accept the same forms as input, and treat a bare number as the setting's own unit.
- Enter says what it does, and the hint names it:
  - On a boolean it toggles and saves: `Enter Toggle`.
  - On an enum it opens a choice list: `Enter Change`. Moving through the list saves nothing; Enter on a new value saves it, and Esc returns without a change.
  - On a group or a view it opens it: `Enter Open`.
- The shared settings surface infers this from each row: `values` of exactly `on`/`off` toggle, any other `values` open a choice list, and a `submenu` opens. Mark a submenu that picks a value with `kind: "setting"` so it reads `Enter Change`.
- Group related rows instead of prefixing every label with its scope or category. In a settings session's picker, a row with `children` becomes a group row whose nested list saves its rows like top-level ones; `summary` supplies the group's value.
- `/` filters the list. While typing, the hint reads `Type to filter · … · Esc Clear`; once a filter is applied, `Esc Clear` stays until it is cleared.
- A component shown inside a settings surface may implement `settingsHint(expanded)` to supply the single hint line while it is active. Use `settingsListHint` for a component that wraps a pi-tui `SettingsList`.
- Show every row when it fits. Don't hide one row behind a scroll indicator.
- A pane of settings lists settings only. Actions on the focused item, such as `a Manage`, `+ Add fallback`, or `u Undo`, are keys in the hint bar, offered only when they would do something now. A setting saved the moment it changes says so in its status row, and a separate save action names what it saves (`s Save as set`).
- An inline surface ends with a blank row so its hint never touches the footer below it.

## Command help

`/<command> help`, and a bare `/<command>` without its own handler, show one overview, built by `registerExtensionCommand` through `extensionCommandOverview`. Don't hand-write help text. Every command registers through `registerExtensionCommand`, including one whose only action opens a surface (`/activity`, `/ask-user`): it sets a `bare` action, so `help` still shows the overview and an unknown subcommand warns.

- `help` is a built-in subcommand: it posts the overview as info, never as an unknown command. A command whose bare form opens a surface sets `bare.description`, and the overview lists that bare action first (`/tasks  Open background tasks`). The overview ends with `/<name> help  Show this help`.

- The title line reads `/<name>: <description>` at column 1. If it wraps, continuation lines hang two columns in.
- Each subcommand gets one line: a two-column indent, then `/<name> <sub> [args]` padded to the widest entry, two spaces, and a short description, such as `  /code-previews health    Show renderer health`.
- Every line stays within 55 columns, because Pi draws notices one column in and doesn't hang-indent its own wraps. If any aligned line would be wider, the whole list switches to a stacked form: the command on its own line, and its description on the next line indented four columns, wrapping with the same indent. A command too wide for its line continues six columns in, past the description's column, so it never reads as description. Nothing wraps flush-left at 57 columns.
- Notes such as examples (`overviewNotes`) follow the list verbatim.
- An unknown subcommand warns `Unknown /<name> command: <sub>` and then shows the same overview; `registerExtensionCommand` does this. Never warn with a bare `Usage:` line. When a known subcommand gets wrong arguments, say what is wrong and show the correct form, such as `Add a prompt: /openai image <prompt>`.
- `/<ext> settings help`, `status`, and their errors follow the same rules; the settings shell builds them. Help opens with the overview, then lists each setting as `Label (id): value` with its description beneath, indented four columns. A row too wide for its line continues six columns in, like a stacked command, so a wrapped value never sits in the description's column (`Image fallback model (image.defaultModel):` above `      gpt-6.1-sol`). Status, including an owner's own status sections, lists the same `Label (id): value` rows (`settingsStatusText`), never raw `id = value`: the pair reads in the order rejections use, so the id's parentheses never sit beside a value's (`Delegation (delegation): inherit (normal)`). A missing value reads `Add a value: /openai settings fast.enabled on|off`, and an unknown setting says where the ids are: `See the setting ids: /openai settings help`.
- An invalid value is a warning that reads `Label (id) <rule>`, such as `Fast mode (fast.enabled) must be on or off`, whether the shell's own check or the owner rejected it. An owner rejects a value by failing `apply` with an `InvalidSettingError` or a message that leads with the id and states only the rule (`fast.enabled must be on or off`); the shell replaces the leading id with `Label (id)`. A free-form setting states its rule in its descriptor's `rule`, phrased to follow the name (`must be a duration such as 30s or 2m`), and `decodeSettingUpdate` rejects with `<id> <rule>`; only a descriptor without one falls back to `<id> can't be set to <value>`. A save that couldn't be written is an error, shown as the owner wrote it.
- Subcommand descriptions also serve as autocomplete text. Pi's autocomplete shows only about 21 columns of description at 57 columns, so keep every autocomplete description within about 20 columns (`Footer settings`, `Show renderer health`), in sentence case, with no trailing period. Put detail in the settings surface or the overview notes, not the description. Setting-id and value completions (`completeSettingsArguments`) describe each id with its setting label, such as `maxRunning  Running at once`, never its description sentence, so every setting label fits 20 columns (`Usage on plans only`, `Tokens and cost`). Shorten the label itself, keeping the setting's one name in its row, help, status, and completion; `completeSettingsArguments` cuts any longer description at a word boundary with `…` only as a safety net.

## Panels, tables, and long text

- Read-only text uses `TextPanelComponent`. It wraps long lines with a hanging indent, scrolls when it doesn't fit, and closes with `Esc`.
- Put one fact per row as `Label: value`. Split long lists into one row per item.
- A check row (such as `/subagents doctor`) reads `✓ Label: detail`: the detail is a clause that never repeats its label and never ends with a period.
- Columns use `managerTable`, which drops a column whose cells are all empty so the space goes to columns with content.
- A table's column headings (`managerTable` columns' `header`) are muted, and give way before its values: a heading that doesn't fit is left out, never clipped.
- Inherited values are drawn dimmer than pinned ones, in tables and fields alike, and still read `inherit (value)`.

## Tool rows

- A collapsed row that has more ends its heading's first row with a tag, never a separate line: `▸ label` flush with the row's right edge from 80 columns when it fits, otherwise a bare `▸`, at least two columns after the content. The tags of a transcript form one column. A compact or message heading shortens its subject for the tag by the usual rules rather than letting it overlap, and gives the label up before it would shorten its subject or counter: it shows `▸ label` only where its content is the same as beside a bare `▸`, so the label never costs content. Where even a bare `▸` would drop the first fact the row shows without a tag, the subject gives up three of its 12 columns to keep it. A row too narrow to show its tool name whole beside a tag draws none. A preview heading keeps room for the tag on its first row, taking one more row rather than being cut where it fits the width but not beside the tag, and keeps no room when the row draws no tag. In border mode the bottom corner shows `▸ label`, or a bare `▸` where the label can't fit. No row names the key: Pi's own header teaches `ctrl+o`, so never write `C-o Expand` or `ctrl+o to expand` on a row. An expanded row has no tag.
- The label is a lowercase noun phrase naming what expansion reveals: `error`, `output`, `18 more lines`, `2 more tasks · 1 failed`, `answers`. Never a sentence (`Showing 8 of 10 tasks`) or Title Case (`Error`, `Full answers`). A label standing in for hidden rows names what they hold, including failures.
- Producers declare what expansion reveals and the Code Previews shell draws the affordance, in compact and preview styles alike. A tool row sets `expandLabel` on its compact summary, or `false` when expansion adds nothing; a message sets `expandLabel` on its message presenter. Set it wherever expansion reveals retained content, such as details, prompts, identities, full conversations, or questions, including running calls whose arguments are hidden. Never draw the row's tag by hand. A summary may mark its affordance as revealing only the subject; the shell then drops it when the collapsed compact row showed the subject whole. See [tool presentation](tool-presentation.md).
- In preview style, a message's body, sent or received, indents two columns under its `Message → name` or `Reply ← name` heading.
- Collapsed, a `Message → name` or `Reply ← name` heading is one row: a long name is cut at a word boundary, or after a `-`, `_`, or `.` in a long name. Expanded, the heading shows the name whole.
- Every workspace tool expands into one layout: the body indents two columns under the heading, labeled sections use the Code Previews style, and technical facts close in a dim `Details` section. Build it with the `pi-code-previews` helpers described in [expanded body layout](tool-presentation.md#expanded-body-layout).
- `Details` lead with the subject's ID, such as the task ID. An agent gets one line, `name: id · profile → provider/model:effort · short facts`, with longer evidence (saved files, the next route candidate, skipped candidates) nested beneath it.
- A nested fact indents two columns under its parent; a wrapped continuation of any `Details` line hangs four, two past a nested fact, so a continuation never sits in a nested fact's column (`wrapFacts(facts, width, hangingIndent)`).
- Compact subjects that don't fit are cut at the end on a word boundary; file paths (`pathSubject`) lose their middle so the file name stays.
- A collapsed heading tries its subject's narrower whole forms (`subjectAlternatives`) before it cuts the subject or drops its first fact: `⊘ subagents_stopped auth-review +1 · on reload`, not `auth-review… · on reload`. A list of names gets alternatives where it is the only place the row counts them; beside its own count (`· 2 answers`) it is cut with `…`.
- A read or write heading names a file's language only when its content gave it, such as a shebang in an extensionless script (`✏️ write bin/deploy · 39 bytes · 3 lines · bash`). A language its name or extension gives (`src/a.ts`, `.env`) is left out, since the path already shows it; highlighting still uses it.
- Producers pass subjects whole; any safety cap is at least 120 characters. The shell cuts collapsed rows and wraps expanded headings, so a body never adds a `Name` fact to make up for a cut heading. The one exception is a name longer than its 120-character safety cap, such as an intercom session name (which may run to 1,024 characters): its body keeps a `Name` fact with the whole name.
- A heading never loses its outcome, for any subject length. A collapsed heading reserves room for its whole outcome fact before it shortens the subject, and an expanded heading keeps every outcome fact. An expanded preview heading wraps the whole subject; an expanded compact heading wraps up to three rows, cutting at a word boundary with `…` (paths lose their middle), and its body then shows the subject whole. Measurement and drawing share one width budget, and no heading shows `[truncated]`.
- A body drops a field that repeats the subject only when the shell reports that the heading showed it whole in the same style (`headingShowedSubject`), never because two strings are equal.
- A questionnaire's lone answer to a lone question leaves out its `Title:` label where the heading showed that title whole (`headingShowedSubject`); several answers, a clipped title, notes (`Note:`), and expanded Answers keep labels.
- An expanded call's `Requested …` line names only targets nothing else on its row names: every target until the result arrives, then only those its rows, Details, and issues don't name, so an ID in `Not found: agent-12` or `agent-12: not stopped` isn't repeated. A running wait whose progress tree draws its runs names them too, unless the Activity panel draws that tree instead. A failure that shows only its error, or an undecodable result, names nothing, so its row keeps every target. The call's terms (`until the first finishes`, `timeout 30s`) stay.
- Every preview-style heading that can wrap is drawn with `previewHeadingText(() => renderToolHeader(…))`, so its continuation rows hang two columns. No heading wraps flush-left.
- An expanded compact heading never shortens its subject mid-word. Within its three rows it wraps like a preview heading, with the counter on a hanging continuation row when it doesn't fit, and it uses the same counter alternative the collapsed row shows.
- A count heading supplies one combined counter, with shorter aggregate alternatives, never independent counts as alternatives. Join counts with `·`: `1 unavailable · 1 not answering`.
- A heading never restates its status glyph: a counter or metadata fact that is only the word the glyph shows is left out, so `✓ write src/new.ts`, not `✓ write src/new.ts · new file`, and `⠋ agent_await auth-review`, not `· running`. A fact that measures the glyph's state keeps only its duration: `✓ background_task typecheck · 1m 33s`, not `· finished in 1m 33s`, and likewise `failed after` beside `✗` and `stopped after` beside `⊘`. A spinner or starting glyph says `running`, `starting`, `started`, or `in progress`; `✓` says `done`, `finished`, `succeeded`, `success`, `completed`, or `started`; `✗` says `failed` or `error`; `⊘` says `stopped` or `cancelled`; `◒` says `stopping`; `○` says `queued`; `‖` says `paused`; `≈` says `outcome unknown`, `uncertain`, or `unconfirmed`. `STATUS_GLYPH_WORDS` owns this table for every surface. Counts (`1 of 2 finished`, `2 failed`) and other facts (`timed out`, `needs your input`, `waiting for reply`) stay, as does a word beside a glyph that doesn't say it: the neutral `•`, the shared `?`, `⚠`, and the `→`/`←` message glyphs (`→ agent_send main · queued` means held for delivery). The Code Previews shell applies this to every compact and message heading, each `·` part of a combined counter included; a producer whose heading draws its own glyph follows it too. It doesn't apply where no glyph shows the state on the same row: preview headings (`Background task typecheck · finished in 1m 33s`), the expanded preview's status line, and issues keep their words. Nor does it apply to facts about the subject rather than the call: a summary whose counters and metadata describe its subject's state sets `subjectState`, so `✓ agent_read refresh-fix · finished` keeps the agent's `finished`, since its `✓` says only that the read succeeded.
- Each row of a listed result starts with its status glyph and, like a heading, leaves out the state word its glyph says or an issue beneath the row already says. This covers tool-body lists, Activity, and the live widget: `○ Password reset · reviewer → openai-codex/gpt-6-sol`, not `· queued`, and `✗ Unit tests` with a bare `28s`, not `failed after 28s`, since beside a glyph that says how work ended a bare duration is its run time. The room this frees goes to what the row was dropping, such as the profile or a continuation row's identity. A row keeps counts (`1 failed` on a folded branch, `2 failed` in a banner), failure causes, blocked reasons, `?` words, and the attention of its descendants. A banner for one failure names it beside its glyph, `✗ Unit tests · /activity`; one for several counts them, `✗ 2 failed · /activity`. Listed sessions use glyphs by meaning: idle at its prompt `✓`, working when listed `•`, state not confirmed `≈`, unreachable `✗`.
- A row says what kind of work it is (`· task`, `· subagent`) only where nothing above it does: under the Activity manager's `▾ Tasks` or `▾ Subagents` heading the kind is left out, while the live widget, which has no section headings, and a focused subtree keep it.
- A line grouping listed rows by state drops a verb its glyph says (`⊘ auth-review, schema-check`); verbs that say more, `✓ Already finished`, `✗ Already failed`, `• Still running`, `? Waiting for reply`, stay. A start's `✓ Started docs-sweep` keeps its verb: there `✓` marks the launch, while beside a run's name it would say the run finished.
- Recent tool calls in Activity details lead with their state glyph, `✓ bash · sleep 25`, `✗ bash · pnpm test`; a call still running when the details drew shows the neutral `• bash · sleep 25 · running`.
- An empty listing says so once, in the same words: its compact counter and its preview body both read `no active tasks`, and it shows no expansion affordance.
- Paths in notices, panels, and diagnostics use `formatDisplayPath`, on failure branches as well as success: cwd-relative or `~/…`, never absolute under home. Checks and stored evidence keep the real path. A working directory always reads home-relative (`~/web`); short lines may elide its middle components (`~/…/platform/web-frontend`), never switch to a bare basename. A wrapped path breaks after its last `/` before it breaks inside the file name, in issue details as in Details: both wrap with the same path-aware, whole-fact wrapper. A path of which only a sliver would fit beside the words before it starts on the next row; a name with no part narrow enough to break after fills each row rather than stranding a fragment. Masked identifiers use `…` (`acct…41b8`).
- A collapsed row never wraps a path. Show the display path when it fits, otherwise its file name, shortened in the middle if still too wide; the full path belongs in expanded Details.
- A paused run is stated by its `‖` row; don't add an `ℹ … is paused` issue.
- A quote cut before the end of its source text ends with `…`. When expanding mainly reveals the quoted text, the affordance names it (`▸ question`), not `▸ details`.
- Lists that nest rows, such as agent trees and questions with their choices, hang a wrapped row's continuation two columns past its children's column, as Details do, so a continuation never sits in a child's column. A fact that moves to a continuation row starts with its `· ` separator.
- A list of sessions, agents, or tasks starts each row with the same status glyph on every surface: tool rows, expanded bodies, and command notices.
- A stand-in for hidden rows sits where the rows are hidden and names them: a log's middle `▸ 18 more lines`, a tail's leading `▸ 6 earlier lines`, a list's trailing `▸ 2 more tasks · 1 failed`.
- A clipped body draws exactly one affordance for its hidden rows, at the spot they are hidden, with `renderExpansionAffordance` and no key: between head and tail, `▸ 7 more output lines`; before a streaming tail, `▸ 7 earlier lines` directly under the running line. A row whose result body draws such a stand-in shows no heading tag. A stand-in for a call's own clipped input names only that input, so the heading keeps its tag for the rest: a collapsed preview codemode row shows both `▸ program` where its program is clipped and `▸ output` on its heading for the output it hides. Never a separate `… 7 lines hidden` marker plus a footer for the same rows. This holds for bash, read, grep, find, ls, and every other clipped preview body.
- A started call's collapsed preview row shows its live state (`⠋ Running…`) until it first reports, matching its expanded row.
- A received message's expanded body has no section label; the heading already says what it is, unless its heading wraps, when the body is labeled (`Message`, or the presenter's `bodyLabel` such as `Report` or `Question`) so the heading's continuation doesn't read as the body's first line.
- In an expanded view, a row of `·`-joined facts wraps with `wrapFacts` and is never clipped; only collapsed rows clip. A row that starts a new fact leads with `· `, as nested lists do, in Details, fields, Activity, and notices alike (`running · 12s` / `  · task-12`); the continuation of a fact too wide for its row hangs two columns past its `· `, and a `→` continuation takes no `· `, so a leading `·` always marks a new fact.
- A run's pending question is an attention issue that quotes it, `name asks: …`, on every surface that raises it. A body that also draws the run shows only its state, adding the rest of the question only when the quote was cut.
- A call waiting on the user once its question is on screen sets `waiting` and reads `needs your input`; a call waiting on an agent's reply reads `waiting for reply`. Both show `?`. A queued request shows `○`, and a call that returned because a run paused shows `‖`.

## Time

- Durations: `850ms`, `2.1s`, `1m 25s`.
- Ages: `23s ago`.
- Absolute times come from `formatClockTime(at, now)`: `10:59 PM` on the same local day, otherwise `Nov 3, 10:59 PM`. Never show seconds. A diagnostic read out of context omits `now` and always shows the date.
- Sizes come from `formatBytes`: `512 bytes`, `18 KB`, `1.5 MB`. A trailing `.0` is dropped, as durations drop it.
- Label times whose meaning isn't obvious, such as `resets 10:59 PM`, so they don't read as a clock.
- Reset times are absolute on every surface: `resets 10:59 PM` today, `resets Nov 10, 11:03 PM` otherwise. A countdown (`resets in 6d 22h`) may follow the absolute time as an optional `· in 6d 22h` suffix, or replace it only as a narrow-width fallback where the absolute form doesn't fit, such as the footer's `↺ 2h 3m`.
- Never show epoch numbers.

## Identity

- Show human names first. Add an ID only when two names collide, as a short suffix.
- An agent names its profile and the model it actually runs on: `scout → openai-codex/gpt-6-luna:high ⚡`. The qualifiers after the colon are effort, `⚡` for fast mode, and `(fallback)` or `(override)` when the profile's first choice wasn't used. As a row narrows, live activity gives way first, then the qualifiers, then the profile, then the human title shortens with `…` to about 12 columns; `provider/model`, the elapsed time, the tree branch, and the status glyph stay. Below that floor, the Activity manager moves the identity to a continuation line under the title rather than cut the model. The live widget keeps one line per row, so it shortens the title further and gives up a long status before the model.
- Full IDs, PIDs, cursors, session paths, and raw routing internals belong behind a Technical disclosure.

## Errors and agent text

- Normal states, such as a feature paused for the current model or data that isn't available for this model, are info notices. Warnings are for failures. Every warning names the thing involved (for example, the saved `provider/model`) and its next step, using the real Pi command that fixes it (`/login <provider>`, `/model`, `/thinking`, `/new`, `/btw`), never a vague "choose one" and never a tool only the agent can call.

- A collapsed issue is one short human sentence, such as "File not found", "Rate limited by provider", or "Exit 2: missing semicolon". Raw diagnostics, stack frames, and endpoints appear only in expanded detail. See [Issues](tool-presentation.md#issues).
- Agent-authored text, such as reports and results, renders markdown the way Pi renders assistant text. Inline code is styled, not shown with raw backticks.

## Density and width

- State each fact once per surface. Don't repeat titles, statuses, or results.
- A body never repeats a count its heading or rows already show: an await's compact heading counts how many finished, failed, and stopped, so its body adds only other states, usage, and descendants; a single awaited run's row glyph is its count. A preview heading has no counter, so a multi-run preview body keeps every count.
- Label compact values whose meaning isn't obvious (`cache r163k`, `1 modified`) when there is room, and fall back to the short form only when narrow or when the user chose compact density. A label replaces a sign rather than following it, so `!1` becomes `1 modified`, never `!1 modified`. `~` before a number always means "about" (`~50 tokens/s`), never a git count.
- Line counts are git's own totals, `+15217 −4470 lines`, as `git diff --shortstat` reports them. Never fold replaced lines into a separate count, and never write `~` before a count of lines.
- Counts from 1,000 group digits (`152,310 characters`, `1,024 characters`) through `formatCount` or `countLabel`; never hand-format a count. Git's line totals, `+N −M` summaries, and the diff line totals beside them stay as git prints them.
- Token counts read `23k tokens` wherever there is room, on every surface; the abbreviation `tok` is only a narrow-width fallback. Two surfaces in the same pane never use different words for the same count. Rates read the same way: `~50 tokens/s`, whole numbers from 10 up and one decimal below (`~7.4 tokens/s`).
- Count summaries use the Unicode minus `−` (U+2212): `+4 −2`, `+48 −7`. Diff line prefixes inside diff bodies stay ASCII `+` and `-`.
- A line standing in for rows that don't fit says how many and what they hold, with no separator stranded after the ellipsis: `… 9 more · 1 needs your input · 3 running`.
- A line of facts wraps between whole facts, so no line ends with `·`, `→`, or `←`; in a heading as in a body, an arrow travels with what follows it (`Message` above `  → billing-…`). A fact too wide for its line breaks before its `→`, which then leads the continuation: `researcher` above `→ claude-bridge/claude-sonnet-5-5:medium`. Facts after a broken fact keep packing onto its last line.
- Wrapped lines use a hanging indent. Truncation uses `…`. Nothing is cut mid-word without an ellipsis, and a cut at a word boundary closes up before it (`Approve…`, not `Approve …`). A message cut to a length budget ends at its last whole word when that keeps most of the budget (`clipProse`, as `endElide` does for widths); only one long token is cut mid-word.

## Waiting and delivery words

One state has one name on every surface, in titles, rows, banners, and counts:

- Work waiting on the user **needs your input** (`1 needs your input`, `Needs your input: Deploy`, the working row's `Needs your input`).
- Work waiting on another agent's reply is **waiting for reply**, in agent tools, lists, Activity, the widget, and parent-contact rows. Never write `asks a question`. A narrow count drops it before shortening it. A waiting row keeps its `?` glyph and elapsed time; where the row is too narrow for both the words and the time, the words give way.
- A message its recipient will read later is **held**, never "holding".
