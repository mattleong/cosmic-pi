# Activity

The shared Activity view behind `/activity`, `/subagents`, and `/tasks`, and the protocol producers use to publish into it. See the [README](../README.md) for an overview. [ARCHITECTURE.md](../ARCHITECTURE.md#activity) owns the phase-state, retention, widget allocation, action dispatch, and validation rules; this file links to it rather than repeating them.

## Activity view

`/activity`, `/subagents`, and `/tasks` open the same two-pane manager, with **Workflows → Subagents → Tasks** sections (plus **Attention** for standalone questions). The latter commands select matching standalone work first, or reveal a matching member inside a workflow; they do not filter other sections away. Producer managers remain fallbacks when Activity is unavailable. Ordinary `/activity` preserves the session selection and zoom when reopened.

A workflow appears as **workflow → phases → agents**. The workflow row shows its own state, elapsed time, and how many of its phases are done; a stopped workflow's own state word covers its stopped phases. Each phase shows a state glyph (not started, running, finished, stopped, or skipped) or a warning when any of its work failed, and a settled phase shows how long its agents took. Queued agents show as queued until they start. Work cancelled before it started shows its producer's reason, such as being skipped or refused, beside its row. Planned agents show dim and static, and a phase whose only members are planned stays not started while the workflow runs because the script can still call them. The persistent view shows a live workflow's narrator line, such as its latest log line, dim and clipped beneath its row; the manager shows it in the workflow's detail.

The persistent view normally uses up to eight rows and grows for workflow checklists, up to half the terminal height so the conversation and editor stay visible. Overflow notices keep attention counts visible; very narrow views combine attention into a total rather than imply none. Finished member detail leaves the persistent view, while phase rows and their attention counts remain. Section headings appear only in the full-screen manager, where they lead with what needs attention so a clipped heading keeps it, and manager collapse can reduce member detail but not the phase checklist.

Rows show their `WORKFLOW`, `SUBAGENT`, `TASK`, or `QUESTION` type, the selected profile, state, elapsed time, and an explicitly awaited marker. Human input ("needs you"), parent waits ("waiting"), blocked work, and failures are counted separately. Use shared arrow/Vim navigation and page keys: `h`/Left collapses or returns to the parent row; `l`/Right expands, then inspects; Enter inspects a phase summary or source details. `?` shows more help, `z` zooms, and `w` cycles only through human-input attention. Phase rows and sections show summaries only and have no actions.

Number keys invoke the displayed source's actions. Source shortcuts are `x` stop or skip, `i` interrupt, `u` resume, `m` reply/message, `e` rename, and `c` clear; `?` lists every action key. Esc or `q` declines a confirmation. An action is retargeted to the current revision only when the row still offers an identical action (same id, label, confirmation, and handoff), so unrelated progress doesn't void the choice. `r` refreshes lazy details without moving the viewed log slice; `t` toggles technical source identity and revision metadata. `f` opts the selected source into follow refresh, off by default. Selection changes, follow-off, and close revoke pending delivery and cancel the host request. Esc returns to the list, then closes; `q` closes immediately.

## Producer protocol

Producers import `registerActivityProvider` and `ActivityItem` from `pi-cosmic-ui/activity`. Register once per producer session with `pi.events`, the exact `ctx.sessionManager.getSessionId()`, a stable provider ID, a synchronous `snapshot()` returning plain summaries, and `invoke(itemId, actionId, revision, signal)`. Call `publish()` after changes and `dispose()` during session teardown. `parent: { providerId, itemId }` is explicit ownership, never an inference from labels or start times. `registerRevisionedActivityProvider` wraps this for producers whose details and actions must be current; it republishes on the supplied change sources and returns the disposer. Its action callback receives `invocationCurrent()` as its fourth argument: recheck it after user input or another await before changing source state. For tests, `fakeActivityHost` from `pi-cosmic-ui/activity/testing` answers discovery and acknowledges registration, and `activityGalleryFrames` from the same subpath renders items through the real widget and manager, with chosen items' details opened.

Every item includes a stable `id`, `kind`, `title`, `status`, and `revision`. Statuses distinguish pending, running, stopping, blocked, needs-input, done, failed, and cancelled. Every needs-input item must supply `inputTarget: "user" | "parent"`; other statuses cannot carry it. Blocked rows may supply `blockedReason: "parent-review" | "file-access-review" | "file-access" | "write-containment"`; other statuses cannot carry a blocked reason. Optional `startedAt`, `endedAt`, and `updatedAt` are finite epoch milliseconds for elapsed/update information. Optional `summary`, static `detail`, and `{ id, label, confirmation?, handoff? }` actions must contain display-safe information, not credentials or raw provider errors. Destructive actions must supply a `confirmation` prompt that describes their scope, including affected descendants. Set `handoff: false` on actions that open no UI, such as stop or skip, so they run with the manager open. Snapshots are limited to 512 items per provider and 16 actions per item, and details to 16,384 characters; `ACTIVITY_LIMITS`, exported from `pi-cosmic-ui/activity`, lists every bound the protocol enforces, so producers can clip to it. Use optional `getDetail(itemId, revision, signal): Promise<string>` for logs or other lazy detail. It runs only when the user opens or refreshes details, or opts into follow and the selected source updates, never on render, resize, or theme invalidation. Revisions must change whenever the item or its available actions change. Keep them per item, for example a hash of the item's published fields, so one item's progress never makes another item's action stale.

A `kind: "workflow"` item may carry ordered `phases` (up to 32 `{ title, detail?, work?, planned? }`) and the current `phase` title. A phase's optional `work: { items, finished, stopped, failed?, skipped? }` is the producer's own count, including members it no longer publishes; `stopped`, `failed` and `skipped` count disjoint parts of the finished work. A phase's optional `planned` count likewise includes planned members the producer doesn't publish, and a workflow's optional `unphasedPlanned` count covers planned members outside its published phases, such as those past the 32 shown. Only workflow items may carry `phases` or `unphasedPlanned`. Members are ordinary items whose `parent` is the workflow item and whose `phase` names one of its phases. Publish declared work that hasn't been requested with `planned: true`, and keep its `id` when it becomes real work so selection follows it. Give a planned item that will never run its owner's `endedAt`, so retention drops older ones first. Workflow attention comes from its members. The remaining workflow semantics and the validation rules whose violation withdraws the snapshot are in [ARCHITECTURE.md](../ARCHITECTURE.md#activity).

`onAvailability(available)` and `isAvailable()` report acknowledged replacement ownership, not merely that Cosmic UI was discovered: keep the old panel until availability becomes true and restore it when availability becomes false. RPC and headless sessions never acknowledge the TUI replacement. Oversized snapshots withdraw acknowledgement like invalid ones, and the next valid publication can recover.
