# Shared tool presentation

This contract applies to workspace-owned visible tools. The [suite UI conventions](ui-conventions.md) apply to every visible surface, tool rows included. Code Previews owns shell policy and composition; each tool package owns domain classification and unique content. Rendering must preserve execution, permissions, result content, retained evidence, and native images. Headless tools and command/settings interfaces do not need the tool shell.

## Registration and policy

Use `withCodePreviewShell` for executable definitions owned by the extension, and declare `pi-code-previews` as a runtime dependency. When project settings apply, call `loadCodePreviewSettings(ctx.cwd, ctx.isProjectTrusted())` inside `session_start` before wrapping and registering. Wrapping captures collapsed style and background mode. Renderer-only integrations use `withCodePreviewRenderers`; never wrap another extension's execution definition.

For tools registered during `session_start`, install `registerCodePreviewReplay` at factory time, anchored to the extension's unique command. Wrap through its `shell`, publish only after successful tool registration, call `finishStartup` when startup settles, and `retire` on shutdown. Exact public tool/command source identity controls adoption. History reconstructed before startup keeps its retained call/result content and fixed self shell, then adopts only its originating first-ready owner's appearance. Replay never executes tools or changes activation, and old rows never borrow replacement settings or schedulers. Historical custom-message renderers also register at factory time without restoring delivery authority.

Code Previews requires Pi 1.5.0 or later and is tested with 1.5.0. One stable factory-time `pi.registerToolRenderer` resolver uses only public renderer fields from `next()`. Exact builtin metadata admits native presentation. Explicit third-party adapters use separate exact package/source/name admission; unsupported or ambiguous ownership falls through. No native factory interception, manager replacement, private execution lookup, forced takeover, or configuration mutation is permitted. Write's actual before-write snapshot hook is the sole exception to presentation-only registration and preserves native mutation-queue and activation semantics; see [Pi boundaries](pi-boundaries.md#tool-and-native-manager-integration).

`CompactSummary` describes action, subject, counters, metadata, outcome, issues, and optional children. Settled summaries explicitly classify domain outcomes, neutral `returned` delivery, `queued` work that hasn't started (`○`), or `paused` work (`‖`). While pending or running, `waiting: true` marks a call that is open but waiting on a person's or agent's reply, such as an open question: its row shows the attention `?` in place of the spinner and keeps its elapsed time. Set it only once the question is actually shown. `queued: true` marks an open call whose request waits its turn in a queue: its row shows the muted queued `○` in place of the spinner; `waiting` wins when both are set. Transport success and a false Pi error flag do not prove domain success. Keep cancellation, uncertainty, delivery failure, and cleanup blockers distinct. `resolveCompactSummary` reconciles host errors; `planCompactPresentation` supplies conservative fallback for absent or malformed summaries. Neither infers domain semantics from rendered text.

A parent's outcome is its own. Children can contribute attention without turning a handled failure into a second parent error. Green checks indicate semantic success; neutral returns remain neutral even where native Code Mode uses `returnedCheckmark` for completed dispatches. Unknown outcomes never become success by default.

Collapsed calls have one semantic heading and at most one routine detail. Counters precede metadata and measured timing; the call's issues follow. Counters are alternatives, widest first: the row shows the first that fits. An expanded compact heading never cuts its subject mid-word: it wraps as a preview heading does, between words or after a `/` in a path, with a counter that doesn't fit on a hanging continuation row, and keeps the alternative its collapsed row shows at the same terminal width. Only a subject too long for three rows is shortened, as the collapsed row shortens it, and the body then shows it whole.

A subject that doesn't fit is prose by default and is cut at the end on a word boundary with `…`, so every word that remains is whole. A subject that is a file path, or ends in one (`src/app.ts`, `TODO in src`), sets `pathSubject: true` and loses its middle instead, so the file name stays visible. Producers pass the subject whole; don't pre-truncate it.

Producers declare what expansion reveals; the shell draws it. A collapsed row whose expansion reveals more ends with `▸ label · C-o Expand` in both collapsed styles: indented like its issues on a compact row, and closing a preview row after its timing line (a bordered row puts the same `▸ label · C-o Expand` in its bottom corner instead, or only the key hint where the label can't fit). A label is a lowercase noun phrase naming what expansion reveals, such as `diff`, `questions`, `program`, `error`, or `7 more output lines`, never a sentence or Title Case. `expandLabel` is drawn whenever it is set; `expandLabel: false` omits the affordance because expansion only repeats the row. Declare a label wherever expansion reveals retained content the collapsed row hides, such as details, prompts, identities, or full conversations; a tool whose collapsed bodies differ between styles reads `captureCodePreviewPresentationPolicy()` when it wraps and declares the label true for that style. Without a declaration, a compact row says `output` (`error` for a failure) when its result has visible content, and `details` when issues keep information or detail for expansion or a call that hasn't settled has arguments; a partial result without visible content counts as no result. A preview row, whose bodies already show arguments and output, says `output` or `error` when its collapsed result body draws nothing of a result that has content, else `details` for issues kept for expansion, so a failure the collapsed body leaves out reads `error` in both styles. A collapsed row that already shows an affordance, such as a clipped quote's or a body's own `▸ 3 more lines`, doesn't get a second one, and an affordance a result body ends with moves below the timing line. Producers never write the row's affordance themselves; a body draws its own only for content it clips, naming what it hides (`▸ 7 more output lines`). That affordance is the one stand-in for the hidden rows and sits where they are hidden: between the head and tail of a clipped preview, or after a head shown alone; no separate marker or footer counts the same rows. A running preview row whose partial result streams output shows the latest few lines beneath its running line, with `▸ 7 earlier lines` directly under the running line, before the tail. Call trees show at most five children, prioritizing active/problem calls and accounting for hidden failures. All retained children contribute attention before selection. Counters and omission counts must not lose digits or failure evidence at narrow widths. Missing or incomplete summaries preserve an expansion path rather than presenting a speculative success card.

Native presentation adds these evidence constraints:

- `tool_search` requires exact `builtin:tool-search` ownership. Bounded `details.loaded` receipts support neutral listing counts, not claims about current availability. Rendering never discovers or activates tools.
- Codemode inspects only the latest 256 call slots, validates neighbors independently, and retains coverage uncertainty when records are missing or rejected. Listed records are not inferred dispatch totals; settled `running` records remain unconfirmed. Expansion preserves bounded receipts and diagnostics without reading persisted artifacts.
- Parsed program source can supply discovery intent, never execution receipts. Recognize direct unshadowed helpers only; require explicit static MCP targets/namespace filters for MCP specificity. Inert text, unused bodies, aliases, dynamic callees, unsupported source, and exhausted budgets decline. Do not synthesize children or infer discovery from guest output.
- MCP names and observed argument scalars support readable labels only when unambiguous. Never expand hashes or ambiguous aliases into guessed remote identities. Standalone MCP admission is independent of builtin/codemode preview selection; historical aliases require an independently builtin-owned `/mcp` manager. Pi retains all manager, execution, authentication, exposure, and image ownership.

Native source previews retain an eight-wrapped-row bound, including theme fallback, and expose full source on expansion. Timing is measured only: parent duration is not the sum of concurrent children, and replay without an observed start stays untimed. Normal timing appears after `TIMING_VISIBLE_MS`; native `showShortTiming` can expose measured subsecond values. `animateProgress` is opt-in and independent of timing; a renderer that draws time-based frames must set it (or run its own invalidation ticker), because rows without it redraw only when the whole-second elapsed label changes. Scheduling always belongs to the registering session and stops on retirement. See [integration APIs](../../packages/pi-code-previews/docs/extension-authors.md) and [native behavior](../../packages/pi-code-previews/docs/reference.md).

## Issues

`CompactIssue` is `{ severity: error | warning | attention | info, code, message, detail? }`. Errors, warnings, and attention show the same short human-facing `message` collapsed and expanded. Attention marks work waiting on a person's or agent's reply or decision: it ranks below warnings, never escalates an outcome to warning, and never explains or hides a host error. Agent procedures, retry instructions, tool-call syntax, internal IDs, and raw diagnostics belong in expanded-only `detail`. Routine information, including pagination and usable saved-output locations, appears only when expanded. Equal code/severity/message entries merge while retaining distinct detail lines.

Producers own classification and wording:

- Name the subject and specific event, avoiding repeated category labels, error-class prefixes, internal type names, and trailing periods.
- Prefer the actual warning or question over saying one exists, unless the quoted text is an instruction to the agent.
- Use `error` and `warning` for problems and `attention` for a question or decision someone is waiting on; routine stops, held work, and changes awaiting ordinary review are metadata or information.
- Add at most one short, redacted cause when status alone does not explain failure. Aim for about 70 characters; messages wrap rather than disappear through clipping.

Use `failureMessage(text, fallback)` for unclassified failures and `firstLineMessage(text, fallback)` for other text. They sanitize and bound the first nonblank line; `isAgentGuidance` detects leading procedures. Full raw evidence remains in agent-facing results and expansion. `compactSubject` changes compact labels only.

Render all issues through `renderCompactIssues`, including nested and asynchronous consumers. Both appearance styles use the same issues in the same words. Producers check messages with `issueMessageStyleProblems` rather than exact-copy assertions.

Output clipping is informational only when bounded native metadata supplies a usable saved-output path. Missing recovery and save failures remain warnings. Standalone MCP preview replaces a recognized, owned, non-error saved-output envelope with a neutral expansion affordance. When an owned envelope's truncation is stated by its issues, the collapsed preview shows only the output inside the envelope. A failed MCP call collapses to its issue and a `▸ error` affordance in both styles, and its expanded `Error` section doesn't restate the issue as its first line. A call Pi rejected for its arguments shows the rejection only as its issue and detail; expansion adds just the `Received arguments` the call's own fields can't show. Extra text, unknown envelopes, and progress retain original behavior. Full envelopes and recovery paths remain expanded; a path does not establish that the artifact still exists or that the agent read it. Rendering never reads spill files.

## Expanded composition

`expandedContent.renderCall` and `expandedContent.renderResult` use the original signatures and return unique content without a second heading or issue list. An empty `Container` intentionally contributes no content; an omitted callback preserves the original slot.

For valid summaries, compact expansion composes the shared heading, issues with details, unique call content, then unique result content. Conversational surfaces follow the [conversation rules](#conversation-surfaces) instead of showing model-facing frames. Missing or malformed summaries retain original renderers. Preserve complete arguments, source, commands, proposed edits, output, and recovery instructions, including after failure. Do not subtract evidence merely because an issue repeats it; label raw content or agent notes instead. The one exception is an issue's own detail: when it is exactly the issue's message, omit it, because the message already shows those words. Input that the heading cannot show exactly remains available in full.

### Expanded body layout

Every workspace tool row and custom message expands into the same layout. The heading sits at the frame's column; everything below it indents two columns beneath the heading:

```text
 ✗ background_task tests · failed
   ✗ Exited with code 1: FAIL tests/auth.test.ts > rejects expired tokens
   Command       pnpm test
   Notify        when it finishes
   Output
     ✓ tests/session.test.ts (4 tests) 18ms
     FAIL tests/auth.test.ts > rejects expired tokens
   Details
     task-15 · /project · pid 48633
```

- Issues come first, through the shell.
- Short labeled facts use one muted label column. When the value column would be narrower than 16 cells, as at 57 columns with a long label, each value stacks beneath its label.
- A longer body is a section: a muted label such as `Output`, `Message`, `Reply`, or `Questions`, with its content indented two more columns. A row whose only body is its result, such as a successful `read` or `bash`, may show it unlabeled at the body column; once a row has two kinds of body, label each one.
- Technical facts such as IDs, routes, paths, PIDs, and usage come last, in a dim `Details` section.
- Nothing in the body sits flush with the heading, and no section repeats the heading's facts, including options a preview heading states, such as grep's glob and limit. A preview listing that reached its limit ends its rows with a muted `Limit reached`, collapsed and expanded alike, adding the number only when the heading doesn't show the limit.

Build bodies with the helpers exported from `pi-code-previews`; don't indent or label sections by hand:

| Helper                                           | Draws                                                                                                                     |
| ------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------- |
| `expandedBody(...parts)`                         | The parts in order; `undefined` and empty parts take no space                                                             |
| `expandedFields(theme, [{ label, lines }])`      | Labeled facts in a shared label column                                                                                    |
| `expandedText(theme, label, lines, tone?)`       | A labeled section of plain text; a line may carry its own `ExpandedTone`                                                  |
| `expandedAuthoredText(theme, label, text)`       | Words an agent or session wrote, in full, as markdown                                                                     |
| `expandedDetails(theme, lines)`                  | The dim `Details` section; leading spaces nest a fact under the previous                                                  |
| `expandedSection(theme, label, ...components)`   | A labeled section around any component, such as a diff or a table                                                         |
| `expandedArguments(theme, args)`                 | The raw `Arguments` section, for input the labeled facts can't show; a wrapped line hangs two columns past its own indent |
| `authoredTextLines(text, width, theme, options)` | Authored markdown as lines, collapsed to about ten rows or in full                                                        |

Fields and details wrap a line of `·`-joined facts with Cosmic UI's `wrapFacts`: between whole facts, so no row ends with `·` or `→`. A field's continuation rows hang two columns; a `Details` line's hang four, two past a nested fact, so a continuation never sits in a nested fact's column; other text wraps between words, and a long path after a `/`. Each helper returns a `Component`, so `expandedContent.renderCall`/`renderResult` and message renderers return the composed body directly; a renderer that builds lines calls `render(width)`. Values are plain text: the helpers make control characters visible and apply the tone, so pass unstyled text. Stderr, for example, is a line with the `error` tone rather than a `[stderr]` prefix.

Original and content-only callbacks keep independent call/result `lastComponent` caches. Retained components capture needed values and renderer state, not the render context whose prior component would chain history. Preserve existing invalidation, mouse routing, live panels, and owner-scoped animation. Construction or drawing failure restores safe raw-result fallback without replaying the failing renderer. External adapters preserve opaque downstream components and append complete arguments/raw evidence when the provider's expansion may clip them. Pi retains native images and transcript separators.

## Conversation surfaces

Agent and session messaging, questions, reports, and agent status are read by the user, not the model. Their presentation shows what was said and only the status the user needs:

- Text an agent or session wrote renders as markdown the way Pi renders assistant text. It appears collapsed with its line breaks, bounded to about ten wrapped lines with an expansion affordance, and in full when expanded. `CompactSummary.quote` and `authoredTextLines` collapse it; `expandedAuthoredText` shows it in full.
- Display names identify agents and sessions. Run and session IDs appear only in expanded details.
- Ordinary delivery or completion adds no explanation. Queued, held, resumed, or answered delivery is a short muted status; failures and uncertainty are issues.
- Model routes, usage, cost, timing, ancestry, selection reasons, workspace identifiers, and saved-file paths appear only in a compact expanded details section. Collapsed aggregates may show one muted usage total.
- Agent procedures, tool-call syntax, authority reminders, and coordination rules remain in model-facing content and are never drawn.

The emitting boundary records bounded, sanitized display fields in `details`; renderers never parse model-facing content. Entries saved without those fields fall back to a generic heading collapsed and their raw content expanded.

Workspace custom messages render through the Code Previews message shell, `withCodePreviewMessageShell`, so they share the settled tool row's frame, heading, and outcome tone in every background mode and collapsed style, without timing. Collapsed compact messages are bare compact rows like collapsed compact tool rows, with their words indented beneath like issues; other views keep the words inside the frame. In both styles a collapsed message ends with the affordance for its presenter's `expandLabel` (else its summary's), unless its words already end in one; set it whenever expansion reveals more, such as details, a prompt, or a full conversation. A collapsed message heading is one row in both styles: a subject that doesn't fit is cut as compact headings cut it (prose at the end on a word boundary, a `pathSubject` in the middle), and metadata follows only a whole subject. An expanded message heading wraps with its subject whole in both styles, as an expanded tool heading does, so its body may leave out a subject the heading showed. Expanded, the message's issues indent with its body in every style. Native images follow the message as Pi draws a tool result's images.

## Preview style

Preview is the default. Collapsed, it retains tool call/result bodies and inserts shared issues between them. A call body containing a diff or proposed file places `previewIssuesSlot(context)` beneath its heading. Argument-derived warnings remain visible before execution or approval. A failed theme falls back to plain messages.

Expanded, a row with a valid summary and an `expandedContent.renderCall` uses the same composition as compact expansion under its own preview heading, so a row reads the same collapsed and expanded. The heading is the tool's collapsed call drawn up to where it places `previewIssuesSlot(context)`, or the whole collapsed call when it places none, so a call body that draws more than its heading places the slot right after it. Preview headings wrap rather than clip: continuation rows hang two columns in, a long path breaks after a `/`, and each `·` fact stays whole with its separator, so no row ends with one; `previewHeadingText` draws one.

No fact may disappear on expansion. A body leaves out its subject only when `headingShowedSubject(state)` reports that the heading drawn in the same style and pass showed it whole. A heading row that ends in `…` cut something, so in either style the shell never reports that heading's subject complete, whatever its layout claims, and the body keeps the subject.

A preview heading carries no status glyph, so a line beneath it states the row's state; it exists only so the state never disappears on expansion. Issues carry state, so a row that shows any has no state line, except a cancelled row whose collapsed `Cancelled` gives way to issues only expansion shows. Otherwise a running row shows `Running…` and a waiting, queued, or paused row the state words its compact heading shows beside its glyph, its summary's first counter, else its first metadata (else `Waiting for reply`, `Queued`, or `Paused`), unless the heading or body already states that state: a row at the body's own column begins with the state's glyph (a spinner frame, `?`, `○`, or `‖`), a row opens with the state word or a count of it (`Paused by the user`, `1 paused`) or holds a later `·` fact that begins with it (`auth-review · waiting for reply`), or the expanded rows contain the line's text, matched as the text the rows wrap, so a fact broken across rows, even after a `/`, still counts, and a fact cut with `…` counts wherever the rows continue its words. A nested row led by a glyph, such as a program's running call, and a tree branch state a child's state, not the row's; prose that merely mentions the word doesn't count. A producer whose wait is on the user, not an agent, supplies its own words (`needs your input`), since `Waiting for reply` names waiting on an agent. A cancelled, unconfirmed, or other settled row keeps the fact a compact heading shows beside its glyph (the first counter, else the first metadata): each `·` part the collapsed row states and the expanded heading, issues, and bodies don't, else `Cancelled` or `Outcome unconfirmed`. The line's glyph is the state's own; a settled row without issues never gets a warning glyph. Issues and the content-only call and result bodies follow, indented two columns, and a measured duration closes the body as a muted `Took 27ms` line at the body column. When the collapsed call can't draw, a heading built from the summary stands in: the tool's `label` (else `displayName`, else `name`), then the action, full subject, first counter, and metadata. Without a valid summary or content callbacks, the original bodies remain. Collapsed preview timing is the same plain muted line, never a tree branch.

Tool renderers provide a human heading via `renderToolHeader`, bounded collapsed content, and complete expanded content. They do not draw duplicate issue/outcome lines or expose operation IDs as display labels. Use `toolRunningLine` when pending work has no other content. The row's expansion affordance comes from `expandLabel`; a body that clips its own content uses `renderExpansionAffordance`, which names the configured key. Never hard-code the expansion shortcut.

## Shared vocabulary

Use Cosmic Core's duration, count, size, cost, timestamp, path, and text formatting helpers and Cosmic UI's `clipToWidth` and `managerActivity*` helpers. Their implementations own glyphs, tones, clipping, and spinner cadence. Preserve the distinction between a cancelled request and stopped running work; green denotes success. Attention (`?`, accent) marks work waiting on a person's or agent's decision and is not a warning, live (`waiting`) or settled; queued work is a muted `○` and paused work a muted held state (`‖`). An outcome that could not be confirmed uses `≈`, and a delivered message someone wrote uses `→` when sent and `←` when received (`CompactSummary.messageIcon`), in place of the success check or neutral dot. Warnings and errors are reserved for problems.

## Messages outside tool rows

Notifications, replies, and confirmations use short human-facing wording without internal IDs or agent procedures. `notifyAtHostBoundary` normalizes one-line messages and preserves deliberate multi-line reports; raw failures pass through `failureMessage`. Describe what failed and, when known, why. Successful actions use a short past-tense statement. Confirmations name the item by its display name.

## Managers and settings commands

Use the shared Cosmic UI manager navigation, action vocabulary, confirmation behavior, and settings command shell. Disruptive manager actions ask for the same key again and allow cancellation. `registerExtensionCommand` owns routing and completion; settings use `/<extension> settings` with help, status, scope, and assignment support. A setting has one label on every surface: its group and settings rows, lock reasons that name it, and health or status output. Preserve existing public commands and native `/mcp` grammar. Commands that open Activity show a notice when the Activity host is unavailable. The [UI integration guide](../../packages/pi-cosmic-ui/docs/extension-authors.md) describes these APIs without duplicating their implementation here.

## Retention and validation

Bound and sanitize evidence where it enters a package or persistence boundary. `createBoundedCompactIssuesSchema` provides bounded issue schemas. Redact before storage, mark incomplete evidence, and do not raise retention limits merely to make rendering pass. Change receipts in place without version bumps or legacy handling; saved receipts that no longer decode decline to generic presentation.

Use `pi-code-previews/testing` with actual registered definitions or public renderer-only callbacks. `createToolPresentationHarness` exercises call/result slots, widths, expansion, lifecycle, and invalidation without executing tools. Host-row helpers cover Pi's retained history, first-ready adoption, complete reconstruction, owner retirement, and fallback. Avoid importing another package's internal source for consumer assertions.

Behavioral coverage protects fallback, uncertainty, issue merging, source/recovery preservation, native images, renderer failures, and unchanged execution/result objects. Visual wording and layout are reviewed with `pnpm presentation:gallery`; add a scenario to the package's env-gated `tests/presentation-gallery.test.ts` when adding a visible state. The gitignored gallery is a review artifact, not an exact-text test oracle.

Each package's `ARCHITECTURE.md` identifies its visible tools and ownership. Supported external renderers have a separate [adapter maintenance guide](../../packages/pi-code-previews/docs/third-party-renderers.md); their domain behavior and execution remain outside workspace ownership.
