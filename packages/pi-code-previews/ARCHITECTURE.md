# Code Previews architecture

## Purpose

Provides syntax-highlighted previews, structured diffs, safer write/edit presentation, settings, and cooperative tool-shell APIs.

## Host surface

- Commands: preview health and settings (`settings/controller.ts`, `commands/health.ts`); both guard non-TUI hosts and fall back to plain notifications instead of opening custom UI.
- Events: `session_start` and `session_shutdown`.
- Tool surface: installed replacements for supported built-in tools and the public cooperative shell wrapper. The extension never changes Pi's active tool names.

## Source map

- `src/extension.ts` is the thin Pi package entrypoint.
- `src/application/lifecycle.ts` coordinates runtime replacement, settings startup, syntax initialization, and renderer installation. It uses the shared host-session capture, fail-closed trust, and best-effort notification boundaries. Startup calls the settings and syntax services directly; dependency-injected Effect factories are test seams, not another application service.
- `src/application/capability.ts` is the canonical named bridge used by synchronous callers. Its `activeCapability` is the sole authority for active checks, runtime execution, deferral, and scheduling. Inactive defer/schedule calls return no-op cancellers. Cleanup is unconditional and has no parallel lifecycle token or scheduler projection.
- `src/application/scheduler.ts` owns deferred and fixed-cadence renderer callbacks in a scoped `FiberSet`; synchronous disposers interrupt immediately, while session runtime disposal awaits every remaining scheduler fiber. Startup returns this scheduler through the runtime slot's activation value instead of publishing it through a temporary `MutableRef`.
- `src/layer.ts` is the sole application Layer composition root. Agent directory, environment, and Shiki adapters are private dependencies of the settings, syntax, write, and scheduler services. The final Layer retains the Node file-platform services so effects run through the session capability can use them.
- `src/config/store.ts` is the settings persistence **door** (Effect `CodePreviewSettingsService`, the public loader, and the Promise helpers the panel needs). The service contract is only `load`, `save`, and `flush`. Rooms: `schema`, `defaults`, `values`, `state`, `env`, `document-store`, internal `service.ts` (Context key retained), and `coordinator.ts`. The service keeps one complete save context in a private `Ref`; Layer construction does not publish settings. Each load or save captures a process-local monotonic admission before asynchronous work. The module-level coordinator serializes settings work across separately built Layers and publishes only admissions newer than the latest successful publication. Failed or interrupted newer work does not suppress an older success. `document-store.ts` always returns a complete save context containing only the baseline and loaded settings. Each atomic `modifyObject` derives known overrides from the locked latest document, applies only caller-edited fields, and preserves unknown root fields. `schema.ts` owns every persisted field decoder, including bundled Shiki themes; tolerant field recovery derives from that struct. `defaults.ts` contains the static settings and performance defaults. `env.ts` owns the single `CODE_PREVIEW_*` environment door: `CodePreviewEnvironmentService` decodes once, exposes only settings defaults, and publishes the synchronous performance/tools projection locally. Settings sources are current-only: nested `codePreview` objects in `$PI_CODING_AGENT_DIR/settings.json` and the trusted project's `.pi/settings.json` form the baseline, and the flat `$PI_CODING_AGENT_DIR/code-previews.json` stores package overrides (unknown root fields preserved). Invalid fields recover independently with bounded path-only diagnostics. Legacy HOME-derived locations, `codePreviewXxx`-prefixed keys, nested package files, and boolean/CSV value coercions are ignored, never migrated.
- `src/settings/` owns host commands (`controller.ts`) and the persistence-aware `/code-preview-settings` controller in `panel.ts`; `config/store.ts` owns abort-aware public loading. Signalled startup loads have independent cancellation ownership and never fall back to a one-shot runtime after abort. No-signal public loads share one admission and in-flight disk operation, then clone the settings object and tools array for each caller. The pre-session compatibility runner only builds and runs a short-lived Layer; the shared settings coordinator provides cross-runtime serialization and permits queued cancellation. A one-shot save rehydrates private state and saves under one coordinator permit without an intermediate publication. After a successful theme save, the panel catches a rejected Shiki initialization Promise locally. That failure cannot enter the persistence rollback or warning path. The host wraps its nested `SettingsList` tree with the pure `pi-cosmic-ui/manager/settings-adapter` Vim adapter. Pi/Jiti resolves that shared source subpath directly; no compiled package boundary or generated distribution exists. Pure menus, submenus, and summaries remain under `settings/ui/`. Settings modules import config directly; there is no settings re-export barrel.
- `src/syntax/` and `src/write/` are the other primary stateful features. The syntax service exposes only `initialize`; it owns Shiki replacement and finalization while `syntax/ingress.ts` owns the bounded synchronous renderer request bridge and its sole invalidation callback ledger. The write service exposes only `rememberBeforeWrite` and `withPathLock`. Its bounded projection has non-destructive renderer lookup. The Shiki render cache belongs to one highlighter object and theme pair, not a session-local number. Its module-level ANSI color-conversion cache is cleared on owner release under the same highlighter identity check. Replacement and finalization therefore discard both caches only when releasing the owning highlighter, so stale cleanup cannot clear a newer cache. `src/shared/projection-ownership.ts` gives syntax and write projections monotonic session ownership so a newer session wins overlap and stale cleanup cannot clear it.
- `src/diff/`, `src/paths/`, `src/tools/` (including grep/path-list/shell helpers), and `src/warnings/` contain deterministic preview policy and transformation logic.
- `src/tools/` owns tool names/policy, cooperative shell API (`cooperative-tools.ts`), the lower renderer adapter (`renderer-adapter.ts`), the canonical built-in tool emoji lookup (`presentation.ts`, exported for compound renderers), tool argument/result helpers (`data/`), and synchronous tool definition factories (`renderers/`). The public wrapper and every built-in factory use the same adapter. It creates one shell, copies the source definition once, preserves execution/result options, and calls supplied renderers unbound to match Pi 0.84. A path-list result creates one chunk renderer for the complete output, so collapsed head and tail chunks share the tree-mode decision and directory set across the hidden-lines marker.
- `src/boundary/` wraps Node and Shiki integration plus the one-shot settings runner. Shiki initialization uses `Effect.callback` cleanup for interruption; a highlighter that resolves after cancellation is disposed without resuming the fiber. Synchronous render timing imports `synchronousNow` from `pi-cosmic-core`, while session host capture, trust, and notifications use the shared core boundaries directly.
- `src/preview/` and feature render modules are synchronous UI (no top-level `ui/` folder).
- `src/shared/terminal-text.ts` owns the code-point SGR classifiers (`matchSgrSequence`, `replaceSgrSequences`) used instead of control-character regexes for ANSI parsing.
- Package tests live under `tests/`, mirroring `src/` paths, with `*.test.ts` suffix. `tests/support/effect-test.ts` provides the shared Effect-generator test registration (`effectTest`, `step`, `settle`, `eventLoopTurn`) for promise-shaped boundaries.

## State and resources

Settings, syntax, and before-write correlation are Effect-owned and publish bounded synchronous projections. Deferred and scheduled renderer callbacks are Effect-owned and reached synchronously through the active session capability. Settings state is one save context in a `Ref`; its `loaded` settings publish only after a coordinated load or the atomic rename commit. A stale save exits before `modifyObject`. Global `flush` waits behind settings work from any Layer. Save lock order is coordinator, JSON document lock, then the lock-free `afterCommit` Ref update and conditional publication. Renderer installation status is bounded plain state: pending, installed, disabled, conflict, or registration error. No raw registration error is retained. Before-write execution uses a scoped `RcMap` of per-path semaphores: each call owns one reference, unrelated paths remain independent, and zero idle TTL removes a lock after its final active or waiting user exits. Correlation entries remain visible for duplicate renders until bounded eviction or scope cleanup. Shiki is the documented synchronous-capability exception. Pure diff and rendering calculations remain synchronous.

## Lifecycle

```text
session_start -> guarded host capture -> application Layer -> settings load -> discover and build replacements
                                                          -> install each planned replacement
                                                          -> session capability -> scoped syntax initialization
write/tool render -> frozen projections + pure rendering
session_shutdown/replacement -> session capability cleared -> runtime resources disposed
```

Installation has a two-phase boundary. Discovery and option resolution build an ordered plan that stores every constructed definition before the first `registerTool` call; it does not retain installer closures. Pre-mutation failures fail startup through the lifecycle boundary. Each attempted name enters the lifecycle-owned tool set immediately before `registerTool`; only successful returns enter the installed set. This distinction handles Pi 0.84 mutating its extension registry before a refresh can throw. A visible nonbuiltin tool in the owned set remains retryable on a later start. Registration failures record a bounded status, later tools continue, and installed replacements keep the runtime live.
