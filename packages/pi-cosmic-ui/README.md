# pi-cosmic-ui

Composable, responsive UI elements for pi. Cosmic UI provides a custom footer that combines pi's location, session, token, context, model, thinking, and extension-status information with contributions from other extensions. Active extension statuses render according to each extension's declared placement, with generic defaults for extensions that declare none. While an agent is running, Pi's working row also shows elapsed time and estimated output speed (for example, `Working · 2m 14s · ~18.4 tok/s`). The estimate uses Pi's four-characters-per-token heuristic across streamed text, thinking, and tool-call arguments. Its generation clock pauses during tool execution, while the working elapsed time continues to show total agent wall time.

## Install

```bash
pi install npm:pi-cosmic-ui
```

For local development, load Cosmic UI by itself or together with Better OpenAI:

```bash
pi -e ./packages/pi-cosmic-ui
pi -e ./packages/pi-cosmic-ui -e ./packages/pi-better-openai
```

## Configure

Run `/cosmic-ui settings` for all footer settings, including OpenAI usage, xAI usage, and the fast indicator. Provider settings no longer have footer modes or usage-display switches.

- Usage is `automatic` on eligible models or `hidden`. Hidden usage stops automatic requests, but `/openai usage` and `/xai usage` still fetch on demand.
- Hiding the fast indicator does not disable fast mode.
- Disabling the custom footer restores Pi's default footer. Provider visibility preferences still apply to its status-line fallback.

Configuration is read from `~/.pi/agent/extensions/pi-cosmic-ui.json` and may be overridden per project in `.pi/extensions/pi-cosmic-ui.json`. The `hidden` list stores visibility preferences; for example, `["openai.usage"]` hides OpenAI usage.

```json
{
  "footer": {
    "enabled": true,
    "density": "auto",
    "order": [
      "model",
      "effort",
      "location",
      "openai.fast",
      "branch",
      "pullRequest",
      "git",
      "context",
      "session",
      "metrics",
      "openai.usage",
      "xai.usage",
      "extensions"
    ],
    "hidden": []
  }
}
```

Unknown configuration fields are preserved by the settings UI. Known fields are decoded independently, so an invalid value does not discard valid siblings.

Each active Pi session owns one scoped Effect runtime. Git and pull-request polling is single-flight, uses the current callback context, and is interrupted on session replacement, abort, or shutdown. Background Git probes disable optional locks so status refreshes do not contend with concurrent repository operations.

## Activity

`/activity`, `/subagents`, and `/tasks` open the same two-pane manager, with **Workflows → Subagents → Tasks** sections (plus **Attention** for standalone questions). The latter commands select matching standalone work first, or reveal a matching member inside a workflow; they do not filter other sections away. Producer managers remain fallbacks when Activity is unavailable. Ordinary `/activity` preserves the session selection and zoom when reopened.

A workflow appears as **workflow → phases → agents**. The workflow row shows its own state, elapsed time, and how many of its phases are done, naming stopped and skipped phases separately; a stopped workflow's own state word covers its stopped phases. Each phase shows a state glyph: not started, running, finished, stopped, or skipped, or a warning when any of its work failed. The current phase of a running workflow stays running between its agents. Phases without work that the workflow passed or never reached show as skipped, a phase whose work was all skipped shows as skipped, one whose work all stopped or was skipped shows as stopped, and a phase with failed work needs attention; only finished phases count as done. A settled phase shows how long its agents took. Queued agents show as queued until they start. Work cancelled before it started shows its producer's reason, such as being skipped or refused, beside its row, and work its producer marks `skipped` reads and counts as skipped rather than stopped. Agents a workflow declares before calling them show dim and static as planned, after the phase's real work, finished or not; they keep the same row when called and never count as running or queued work. A phase whose only members are planned stays not started while the workflow runs, even once the workflow has moved past it, because the script can still call them. Once the workflow ends, planned agents it never called show as not run. Beneath a live workflow row, the persistent view shows the workflow's narrator line, such as its latest log line, dim and clipped; the manager shows it in the workflow's detail. A workflow leaves the persistent view once it and all of its work finish, and remains in manager history. Work that names no known phase sits directly under its workflow, and work whose workflow is gone returns to its own section.

The persistent view normally uses up to eight rows, grows for workflow checklists, and is capped at half the terminal height so the conversation and editor stay visible. It reserves standalone capacity, then workflow rows and phase names, then narrator lines, then a live workflow's two most recent failed agents, each with a clipped reason, and a count of its other failures, before sharing member rows; planned rows take what is left. Each phase row counts its planned agents, and the workflow row counts those in phases it doesn't show, so the ones that don't fit are never silently dropped. When not every phase fits, phases whose work needs attention come first, then running ones, still in declared order. Overflow notices count omitted work, planned agents, phases, and workflows separately and keep attention counts visible; very narrow views combine attention into a total rather than imply none. Finished member detail leaves the persistent view, while phase rows and their attention counts remain; the failed agents and failure count a live workflow keeps leave once it ends. Section headings appear only in the full-screen manager, where they lead with what needs attention so a clipped heading keeps it, and manager collapse can reduce member detail but not the phase checklist. While a questionnaire, form, or sign-in dock is visible above the editor, the view shrinks to a three-row summary so the dock fits.

Rows show their `WORKFLOW`, `SUBAGENT`, `TASK`, or `QUESTION` type, the selected profile, state, elapsed time, and an explicitly awaited marker. Human input ("needs you"), parent waits ("waiting"), blocked work, and failures are counted separately. A short row keeps the start of its title: elapsed time gives way first, then progress, then phase counts, then the row's own state, while attention counts always stay. Finished history rows recede in the manager. Pane headings mark keyboard focus. Use shared arrow/Vim navigation and page keys: `h`/Left collapses or returns to the parent row; `l`/Right expands, then inspects; Enter inspects a phase summary or source details. `?` shows more help, `z` zooms, and `w` cycles only through human-input attention. Phase rows and sections show summaries only and have no actions.

Number keys invoke the displayed source's actions and `a` pages action lists longer than nine. Source shortcuts are `x` stop or skip, `i` interrupt, `u` resume, `m` reply/message, `e` rename, and `c` clear. When a row has only one of these, the footer shows its key directly, such as `x Stop workflow`; `?` lists every action key. Destructive actions ask for confirmation: pressing the same letter shortcut again, such as `x`, or Enter confirms, and Esc or `q` declines; a number key never confirms. A confirmed or pressed action targets the row's current revision when the same row and generation still offer an identical action (same id, label, confirmation, and handoff), so unrelated progress doesn't void the choice; otherwise the displayed revision is sent and the producer rejects it as stale. Actions close the manager first so the producer can show its own UI, unless the producer marks them `handoff: false`; those run while the manager stays open. Questionnaires still use Ask User's own renderer. `r` refreshes lazy details without moving the viewed log slice; `t` toggles technical source identity and revision metadata. `f` opts the selected source into follow refresh, off by default. Only explicit input and the host's source-update callback fetch details, never render, resize, or theme invalidation. Selection changes, follow-off, and close revoke pending delivery and cancel the host request; stale output remains marked until refreshed. Esc returns to the list, then closes; `q` closes immediately. Retention keeps at most 128 removable completed items per branch and 1,024 across the session, plus 100 finished roots; live rows and their ancestors are protected. Planned agents that never ran go first and aren't reported as hidden finished items, since their phase and workflow counts still include them.

Producers import `registerActivityProvider` and `ActivityItem` from `pi-cosmic-ui/activity`. Register once per producer session with `pi.events`, the exact `ctx.sessionManager.getSessionId()`, a stable provider ID, a synchronous `snapshot()` returning plain summaries, and `invoke(itemId, actionId, revision, signal)`. Call `publish()` after changes and `dispose()` during session teardown. `parent: { providerId, itemId }` is explicit ownership, never an inference from labels or start times. `registerRevisionedActivityProvider` wraps this for producers whose details and actions require the current session, the exact item revision, and an action that revision offers; it republishes on the supplied change sources and returns the disposer. Its action callback receives `invocationCurrent()` as its fourth argument: recheck it after user input or another await before changing source state. Host withdrawal or replacement permanently invalidates that invocation, even if availability later returns. Producer tests can use `fakeActivityHost` from `pi-cosmic-ui/activity/testing`, a Vitest-free in-memory host that answers discovery and acknowledges registration, and producer galleries can use `activityGalleryFrames` from the same subpath to render their items through the real widget and manager, with chosen items' details opened.

Every item includes a stable `id`, `kind`, `title`, `status`, and `revision`. Statuses distinguish pending, running, stopping, blocked, needs-input, done, failed, and cancelled. Every needs-input item must supply `inputTarget: "user" | "parent"`; other statuses cannot carry it. Blocked rows may supply `blockedReason: "parent-review" | "file-access-review" | "file-access" | "write-containment"`. Other statuses cannot carry a blocked reason. There is no legacy inference from kind, provider, or text. Invalid attention metadata withdraws the provider snapshot until a valid publication restores it. Optional `startedAt`, `endedAt`, and `updatedAt` are finite epoch milliseconds for elapsed/update information. Optional `summary`, static `detail`, and `{ id, label, confirmation?, handoff? }` actions must contain display-safe information, not credentials or raw provider errors. Destructive actions must supply a `confirmation` prompt that describes their scope, including affected descendants. Actions default to handoff: the manager closes before the producer runs them. Set `handoff: false` on actions that open no UI, such as stop or skip, so they run with the manager open. The host validates, sanitizes, detaches, and freezes summaries. Snapshots are limited to 512 items per provider and 16 actions per item. Details are limited to 16,384 characters. `ACTIVITY_LIMITS`, exported from `pi-cosmic-ui/activity`, lists every bound the protocol enforces, so producers can clip to it. Use optional `getDetail(itemId, revision, signal): Promise<string>` for logs or other lazy detail. It runs only when the user opens or refreshes details, or opts into follow and the selected source updates; previous detail remains marked stale otherwise. Revisions must change whenever the item or its available actions change. Keep them per item, for example a hash of the item's published fields, so one item's progress never makes another item's action stale.

A `kind: "workflow"` item may carry ordered `phases` (up to 32 `{ title, detail?, work?, planned? }`) and the current `phase` title. A phase's optional `work: { items, finished, stopped, failed?, skipped? }` is the producer's own count, including members it no longer publishes; when present, the phase state comes from it rather than from visible rows, so a phase whose finished rows were pruned stays done. `stopped`, `failed` and `skipped` count disjoint parts of the finished work, and a phase with failures needs attention instead of showing as done. Members are ordinary items whose `parent` is the workflow item and whose `phase` names one of its phases; publish queued work as pending items without `startedAt`. Publish declared work that hasn't been requested with `planned: true`: never a workflow, `pending` while it may still be requested, when it may offer actions such as skipping it, and `cancelled`, with no actions, once it never will be. Keep its `id` when it becomes real work so selection follows it. Give a planned item that will never run its owner's `endedAt`, so retention drops older ones first. A phase's optional `planned` count is the producer's own count of its planned members, including rows it doesn't publish, and phase rows show it instead of counting visible planned rows. A workflow's optional `unphasedPlanned` count does the same for planned members outside its published phases, such as those past the 32 shown. Workflow and section totals add up these counts, so they agree with the phase rows. A workflow's `summary` is its narrator line. Only workflow items may carry `phases` or `unphasedPlanned`, titles must be unique, a workflow's `phase` must name one of them, `work` counts need `finished` at most `items` and `stopped` plus `failed` and `skipped` at most `finished`, workflows cannot need input or block, planned items must follow the rules above, and only cancelled work that is neither planned, a workflow nor a question may carry `skipped: true`, for work skipped before it started; violations withdraw the snapshot. Workflow attention comes from its members.

`onAvailability(available)` and `isAvailable()` report acknowledged replacement ownership, not merely that Cosmic UI was discovered. Producers must keep their old panel until availability becomes true and restore it when availability becomes false. RPC and headless sessions never acknowledge the TUI replacement. The host checks its activation nonce, session registration, item revision, and action membership before dispatch. Replayed old registrations cannot enter a replacement host. Invalid or oversized snapshots withdraw acknowledgement, and the next valid publication can recover. Producers must honor the supplied cancellation signal and also check their current session generation, revision, ownership, and action policy immediately before operating.

## Screen sizing

Cosmic Pi's full-screen managers and pickers use a centered window at 90% of terminal width and height when the terminal is at least 125 columns by 30 rows. Smaller or shorter terminals keep full-size layouts. Resizing preserves the open screen and its selection. Questionnaires and owned forms use the same bounds but keep short content compact; long content can be paged without clipping inputs.

`pi-cosmic-ui/manager/viewport` provides the pure outer-size calculation. `pi-cosmic-ui/boundary/host-viewport` supplies a per-opening adapter with matching live overlay bounds and `getHeight`. Attach its terminal reader inside the custom UI factory before constructing components, and pass `overlayOptions` by identity without spreading it. Embedded children inherit their parent's allocated height rather than applying the percentage again. The owned-surface `screen` placement attaches it for you.

`pi-cosmic-ui/boundary/host-surface` owns one `ctx.ui.custom` opening in a `screen`, `dock`, `inline`, or plain `overlay` placement. It keeps the pinned-Pi close guard (hide the owned overlay, show an inert non-capturing overlay, call `done`, hide the guard), so closing never pops a newer overlay stacked above. It holds a finish until mount, gives late or stale factories an inert component, admits in the same frame as `custom`, and exposes an external close. Inline surfaces close the editor slot with a guarded `done` and no overlay guard. `openOwnedSurface` is the Effect door and `openOwnedSurfacePromise` the Promise door, whose callers map a `Failed` outcome themselves; `hasCustomSurface` is the fail-closed capability check. Callers keep their domain lifecycle: gates, bridges, tickers, subscriptions, and error wording. `pi-cosmic-ui/testing` exports `fakeCustomSurfaceHost`, a Vitest-free model of Pi's custom host (unchanged from 0.86 through the pinned 1.0) with explicit mounting and one-shot close faults.

`pi-cosmic-ui/boundary/host-settings-command` builds an extension's `settings` subcommand (`/<extension> settings`) from its option descriptors: completions, help with examples, `status`, optional scopes, diagnostics, validation messages, and the scripted `[scope] <id> <value>` apply. The extension supplies config and status accessors, the persistence call, an `afterApply` refresh, and its own picker, which opens through `host-surface` and uses the shell's apply, and adds the subcommand to the command `registerExtensionCommand` from `pi-cosmic-core` registers. Every workspace extension with settings uses it except MCP.

## Extension contributions

The public `pi-cosmic-ui/protocol` subpath exports the versioned `pi.events` channel names and contribution types. A producer first queries for a host and then upserts keyed text or status-placement contributions. Text contributions provide plain text plus a semantic tone, and may declare a line `label` (details entries with a label render as their own labeled line), a theme `color` token, and a `decorates` target (the contribution's text is prefixed onto the target entry, or rendered standalone when the target is absent). Status contributions declare footer placement (region, alignment, priority, order) for a host status entry published through `ctx.ui.setStatus`; the status text keeps flowing through the host, so it still renders without Cosmic UI. Producers must remove their contributions during `session_shutdown`.

Cosmic UI is the sole custom-footer owner among Cosmic extensions. It has no runtime dependency on providers. Its settings name the supported contribution IDs, while producers declare placement, labels, colors, and decorations. The v2 host query/state protocol reports footer ownership, settings readiness, and hidden IDs. Providers wait for settings readiness before automatic requests, honor visibility even when the custom footer is disabled, and use keyed Pi status entries when no custom footer is active. Host state changes include visibility updates, not just installation changes. There are no old-protocol aliases or footer-setting migrations.

The public `pi-cosmic-ui/manager` subpath provides pure shared chrome for full-screen extension managers: fixed-width activity frames, responsive grouped footer fitting, shared narrow/stacked/wide layout tiers, and a consistent status vocabulary (`◌` pending, animated Braille running, `✓` done, `✗` failed, `⊘` stopped/cancelled, `◒` stopping). `/subagents`, `/tasks`, and Code Mode use these primitives so their state animation and status presentation remain aligned; equal-cadence animations share one ref-counted host ticker instead of creating phase-shifted timers per card or overlay. The `pi-cosmic-ui/manager/keymap` subpath (with key-label helpers under `pi-cosmic-ui/manager/key-labels`, including `fullScreenKeybindingOptions`, which adapts Pi's keybindings into a manager's `matchesKeybinding` and `keybindingLabel` and falls back to default labels on a host without `getKeys`) provides their shared modeless Vim navigation policy (`j/k`, `h/l`, `Ctrl-u/d` half-page, `PgUp`/`PgDn` full-page, `gg/G`, `/`, `?` contextual help, and `q`) while preserving configured Pi selection bindings and normal text entry; hints never surface editor-style mode names, and configured key labels that collide with screen-reserved shortcuts are filtered from help lines. The `pi-cosmic-ui/manager/list-detail` subpath provides their pure shared list/detail primitives — index clamping, the motion reducer (Esc returns from detail to the list, then closes; `q` always closes), bottom-anchored detail windows (which can also open at their first lines) with a standardized position label, pane geometry, and row padding. The `pi-cosmic-ui/manager/list-detail-shell` subpath adds a small stateful `ListDetailShell` for generic selection clamping and reconciliation, pane, layout, detail-scroll, page-size, and keymap-chord state. It exports `listDetailFrame(theme)` plus pure framed row, fill, wide, stacked, and screen helpers. `framedFill` accepts raw lines and handles framing, clipping, and empty-row fill. Consuming managers keep Enter policy, actions, prompts, follow behavior, and rendering copy.
