# Building on pi-cosmic-ui

Shared UI pieces other Cosmic Pi extensions build on: footer contributions, full-screen manager primitives, owned surfaces, screen sizing, and the settings command shell. Activity producers should read [activity.md](activity.md). [ARCHITECTURE.md](../ARCHITECTURE.md) owns the internals of each piece; this file covers what callers use and must do.

## Footer contributions and managers

The public `pi-cosmic-ui/protocol` subpath exports the versioned `pi.events` channel names and contribution types. A producer first queries for a host and then upserts keyed text or status-placement contributions. Text contributions provide plain text plus a semantic tone, and may declare a line `label` (details entries with a label render as their own labeled line), a theme `color` token, and a `decorates` target (the contribution's text is prefixed onto the target entry, or rendered standalone when the target is absent). Status contributions declare footer placement (region, alignment, priority, order) for a host status entry published through `ctx.ui.setStatus`; the status text keeps flowing through the host, so it still renders without Cosmic UI. Producers must remove their contributions during `session_shutdown`.

Cosmic UI has no runtime dependency on providers. Its settings name the supported contribution IDs, while producers declare placement, labels, colors, and decorations. Providers use keyed Pi status entries when no custom footer is active. Host state changes include visibility updates, not just installation changes. There are no old-protocol aliases or footer-setting migrations. Footer ownership, discovery, settings readiness, and hidden IDs are described in [ARCHITECTURE.md](../ARCHITECTURE.md#footer-and-configuration).

The public `pi-cosmic-ui/manager` subpath provides pure shared chrome for full-screen extension managers: fixed-width activity frames, responsive grouped footer fitting, shared narrow/stacked/wide layout tiers, and a consistent status vocabulary (`◌` pending, animated Braille running, `✓` done, `✗` failed, `⊘` stopped/cancelled, `◒` stopping). `/subagents`, `/tasks`, and the Activity manager use these primitives so their state animation and status presentation remain aligned. The `pi-cosmic-ui/manager/keymap` subpath provides their shared modeless Vim navigation policy (`j/k`, `h/l`, `Ctrl-u/d` half-page, `PgUp`/`PgDn` full-page, `gg/G`, `/`, `?` contextual help, and `q`) while preserving configured Pi selection bindings and normal text entry; hints never surface editor-style mode names, and configured key labels that collide with screen-reserved shortcuts are filtered from help lines. Key-label helpers live under `pi-cosmic-ui/manager/key-labels`, including `fullScreenKeybindingOptions`, which falls back to default labels on a host without `getKeys`. The `pi-cosmic-ui/manager/list-detail` subpath provides pure shared list/detail primitives: index clamping, the motion reducer (Esc returns from detail to the list, then closes; `q` always closes), bottom-anchored detail windows (which can also open at their first lines) with a standardized position label, pane geometry, and row padding. The `pi-cosmic-ui/manager/list-detail-shell` subpath exports `ListDetailShell`, `listDetailFrame(theme)`, and pure framed row, fill, wide, stacked, and screen helpers; `framedFill` accepts raw lines and handles framing, clipping, and empty-row fill.

## Screen sizing, surfaces, and settings commands

Full-screen managers and pickers size their window through `pi-cosmic-ui/manager/viewport`; the sizing rule is in [ARCHITECTURE.md](../ARCHITECTURE.md#shared-presentation). Resizing preserves the open screen and its selection. Questionnaires use a `dock` placement instead: full width above the editor, capped at 60% of terminal rows, compact for short content, and pageable for long content without clipping inputs. The owned-surface `screen` placement attaches the live viewport for you. Otherwise, attach the terminal reader from `pi-cosmic-ui/boundary/host-viewport` inside the custom UI factory before constructing components, and pass its `overlayOptions` by identity.

`pi-cosmic-ui/boundary/host-surface` owns one `ctx.ui.custom` opening in a `screen`, `dock`, `inline`, or plain `overlay` placement. Overlay placements close through the pinned-Pi guard (hide the owned overlay, show an inert non-capturing overlay, call `done`, hide the guard), so closing never pops a newer overlay stacked above. `openOwnedSurface` is the Effect door and `openOwnedSurfacePromise` the Promise door; `openCommandSurface` opens a command's own view and rejects a failed opening; `hasCustomSurface` is the fail-closed capability check. Latching, admission, inline closing, caller responsibilities, and the `fakeCustomSurfaceHost` test double are described in [ARCHITECTURE.md](../ARCHITECTURE.md#shared-presentation).

`pi-cosmic-ui/boundary/host-settings-command` builds an extension's `/<extension> settings` subcommand from its option descriptors. The extension supplies config and status accessors, the persistence call, an optional `afterApply` refresh, and the rows the shell's picker shows; a custom list opens through `openSettingsList`. The subcommand's behavior and registration are described in [ARCHITECTURE.md](../ARCHITECTURE.md#shared-presentation).
