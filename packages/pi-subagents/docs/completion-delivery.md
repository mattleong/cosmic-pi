# Completion, projection, and delivery

Part of the [pi-subagents](../README.md) architecture documentation. See [ARCHITECTURE.md](../ARCHITECTURE.md) for the package overview, complete source map, and cross-cutting invariants.

## Assignment epochs, questions, and phases

Assignment epochs are prepared monotonically before task issue, advance only after at least one current live authenticated helper acknowledges them, and become unready on disconnect until a new peer handshakes. Helper calls capture the observed epoch, so delayed prior-assignment events retain their old epoch. Progress and warning/question calls normalize to existing `supervisor_contact` events; warnings update parent-visible projection/session history without injecting a standalone model message, while the latest child warning and latest system warning are preserved separately and folded together into the terminal outcome. Questions remain immediate generation-aware parent actions, and child instructions escalate risks that could invalidate current parent work into questions. The channel assigns report sequence and current captured epoch before emitting existing `BackendReport` data. Report `deliveryId` retries with identical text return the original sequence without a second event, while conflicting reuse fails. Only one question may be used per assignment and only one may block per run at a time; parent reply, MCP cancellation, socket loss, adapter cancellation, and scope close settle the exact owned correlation. Every definite question-death path emits a bounded epoch/request-correlated cancellation event so orchestration clears `waiting_for_parent` instead of retaining a dead question. The channel reserves queue capacity for that cancellation; ownership is not cleared unless the cancellation is queued. A parent reply timeout after transmission returns `reply_outcome_uncertain`, closes the exact question without retry, and retains a bounded system warning.

The standalone helper exposes only `supervisor_progress`, `supervisor_warning`, `supervisor_question`, and `supervisor_submit_report`. It dispatches up to 16 calls concurrently, so a blocked question does not block ping, progress, reports, cancellation, or unrelated responses; stdout and channel writes are serialized. It never silently retries an uncertain send. Parent death closes TCP and fails pending calls. Graceful scope release closes the listener and peers, ends the event queue, and removes only the bounded state owned by that run.

Every assignment has a monotonic never-reused epoch and a `preparing`/`issuing`/`running`/`reported` phase. Assignment-scoped events from older epochs, plus activity/tool/progress/warning/question events while idle `reported`, are ignored; handle-scoped lifecycle warnings remain visible in projection and session history but never trigger a parent model turn. A report received while `controls.start` is in flight is held in one bounded slot and committed only after start confirmation (or correlated `run_started` evidence following an outcome-uncertain result). Definite retained-start failure restores the prior view, settlement, report/warning fields, active tools, and assignment state under the matching attempt token while preserving bounded warning notices observed during the failed attempt. Outcome uncertainty keeps the new assignment and warning. Start confirmation never overwrites an already committed fast report.

## Retained runs and session shutdown

A `closeOnReport: false` run transitions from working to nonterminal `reported`, increments `reportGeneration`, retains its backend handle/PID, and counts as finished for the current `all_finished`/`any_finished` assignment. Guidance from `reported` uses the backend's assignment-start control on the same handle, clears the displayed prior report, and makes await target the next generation. Stop and session shutdown still close the scope. Service validation independently rejects retained writers and non-Herdr retained launches.

Session shutdown/replacement/tree navigation/reload closes all local children and exact session-owned Herdr topology, then tombstones safely releasable writer leases. Local Pi private run directories remain while a completed run is resumable; failed, stopped, evicted, and session-ended records reclaim them after process cleanup. A graceful shutdown is not crash recovery: parent death after `spawn-started` intentionally leaves a manual-recovery lock even after a surviving backend later exits. Leasing is owned above the six-driver registry, so every writer shares the same protocol without adapter-specific locking.

## Projection and delivery

UI and tool renderers consume immutable projections. All public tool calls use bounded user-facing action summaries; start calls keep tasks expanded-only and final start results render immutable launch receipts rather than live run snapshots. Receipt rows always retain profile plus actual selected/attempted route and model, or an explicit resolving/no-eligible-route state; outcome icons distinguish complete, mixed, and failed batches, fallback/failure details stay expanded-only, and a single `/subagents` hint hands successful starts to the live surface. Non-start/await results persist bounded semantic profile routes, run cards, and per-target failures instead of reparsing prose. Live cards expose run identity, profile/host/runtime/model route (using compact `model:effort ⚡` notation for fast models), write intent, retention, bounded timing/activity, humanized aggregate usage, state-aware recovery, and expanded provenance/capabilities. Usage cost is optional/unknown: only a backend-reported known cost renders (Pi RPC totals and Claude's `total_cost_usd` estimate are known; Codex and Herdr remain unknown), unknown or zero-information usage renders nothing — in cards and in the detailed status output, which omits its `Usage` field rather than printing `unknown` — sub-cent prices trim trailing zeros, and a fleet cost subtotal over runs with unknown costs is explicitly marked as a lower bound (`≥`). Compact card fallback preserves capability evidence, and renderers treat absent capabilities as unknown-neutral while an explicit lack of `resume` keeps cannot-resume guidance. `subagent_models` renders effective source, defaults, candidate eligibility, and the explicit launch-check boundary. Start/await card details are versioned, deeply frozen, bounded, include only the latest report generation, and preserve explicit truncation/omission evidence when reports cannot fit. Collapsed live results preview bounded first report lines; expanded live cards wrap diagnostics and render a preserved report and error independently, while no-report completion and recovered omitted output are explicit. Progressive batch starts remain input-ordered, render pending/started/failed receipt slots, count pending/failing launches, and animate only the launch header; settled start rows are immutable. Management banners count the true run total (`runCount`), and a result whose bounded card list omits runs adds an explicit cue to query specific run IDs with `subagent_status`. Send acknowledgements distinguish steering guidance from retained (`closeOnReport: false`) next assignments — retained targets are reported as having started their next assignment with `subagent_await` targeting the new report generation, and mixed sends render both. `reported` is rendered as an idle retained resource with explicit next-assignment guidance, rename, and stop controls rather than as a dead process. Interrupt-capable backends that do not advertise resume remain stoppable and present stop/replacement recovery instead of suggesting an unsupported resume. The fleet keeps message/resume/rename input and action errors inside its full-screen overlay, consumes stop confirmation modally, and uses capability-aware actions.

The service publishes every committed run mutation as a monotonic `SubscriptionRef` revision while still holding the shared run lock. Await captures the checked revision in that same locked transition, then subscribes for a strictly newer revision; replay closes the check-to-subscribe race, every wake rechecks authoritative run state, and interruption releases the stream subscription with the caller scope.

Each accepted report or terminal failure creates one internal unresolved outcome-generation record. Successful reports retain their final text; failures retain their bounded error; both snapshot a bounded fold of the latest child warning and latest system warning without adding warning ownership to completion claims. `completionClaims` maps each generation to one exclusive opaque owner token, never a refcount. Await atomically claims the current generation when already reported/completed/failed or the next generation while working; a second await fails with typed `completion_claim_conflict`. Competing status observes bounded metadata with report text/assistant transcript redacted and receives no receipt. A receipt carries the owner token, and consumption succeeds only while that exact token still owns the generation. Cancellation releases only its matching token and requeues notification; complete rendering consumes before the scope release. Failures and successful reports share the coalesced terminal-outcome notifier, which serializes delivery ownership against claim acquisition and acknowledges `(runId, generation)` exactly once. A failure after retained report generation N allocates N+1, preventing dedupe collisions; public `reportGeneration` still counts accepted reports only.

Resolved generation records are removed, while the immutable public projection retains only the latest bounded report, error, and warning for human UI. A retained run admits at most 64 unresolved generations; every next-assignment path, including retained send and resume, fails with typed `report_delivery_backlog` beyond that bound. Total run history never exceeds 50 records: start admission first evicts the oldest terminal record with no unresolved/claimed outcome, process, or cleanup ownership, and otherwise fails with typed `history_outbox_capacity`. Eviction is a two-phase reclaim-before-admit transaction: one eligible candidate is exclusively claimed under the lock without deletion by a single `evictionClaim` that simultaneously reserves the prospective process admission (and writer cwd digest, when present) before any destructive reclamation, its private run state is reclaimed outside the lock while it stays registered (resume rejects a claimed candidate), and a final locked phase revalidates eligibility and performs the delete+insert atomically while excluding its own reservation, creating the new record's scopes only after successful reclamation. Definite reclaim success is required before phase C, whose only outcome is admission — a second reclamation phase is impossible by construction. Reclaim failure or timeout clears only the claim (and with it the reserved admission), keeps the candidate registered, quarantines it against unsafe resume because partial deletion cannot be disproved, and admits nothing. Thus total report/outbox memory is bounded by 50 × 64 plus the already bounded notification/event queues. Questions alone use the independent retryable action slot; ordinary warnings stay in projection/session history and are folded into an eventual terminal outcome instead of being sent through `pi.sendMessage`.

## Module responsibilities

- `src/run/assignment.ts`, `report-lifecycle.ts`, `settlement.ts`, and `resume.ts` own assignment epochs, report commit, terminal settlement, and retained generation rollover.
- `src/run/completion.ts`, `completion-observations.ts`, and `notification-delivery.ts` own outcome records, exclusive claims, receipt consumption, and the retrying delivery outbox.
- `src/run/projection.ts`, `state.ts`, `session-events.ts`, and `warnings.ts` own bounded immutable views and diagnostic/session-history projection.
- `src/tools/details.ts`, `details-decode.ts`, `output.ts`, and `render*.ts` own versioned persisted cards and bounded model-visible output.
- `src/ui/` and `src/settings/ui/` consume immutable projections and never own Effect resources.

Backend-specific completion evidence is documented in [Local backends](local-backends.md) and [Herdr ownership](herdr-ownership.md).
