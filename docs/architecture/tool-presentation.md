# Shared tool presentation

This is the normative contract for workspace-owned visible tools. `pi-code-previews` owns presentation policy and composition. Each tool package owns domain classification and its unique content. Rendering must not change tool execution, permissions, result content, retained artifacts, or native images.

## Registration and policy

Load trusted preview settings before wrapping and registering owned definitions with `withCodePreviewShell`. Wrapping captures collapsed style and background mode until reload. Never wrap another extension's execution definition. Extensions importing the shell declare `pi-code-previews` as a runtime dependency. Renderer-only integrations use `withCodePreviewRenderers({ name, label? }, renderers, options)` without execution or schemas.

Code Previews requires Pi 1.0.1 or later and is tested with 1.0.2. It registers one stable public `pi.registerToolRenderer` resolver during factory loading, never another resolver per session. `next()` supplies only public `renderShell`, `renderCall`, and `renderResult` callbacks, not an execution definition. Exact builtin source metadata admits core/native renderers; unsupported foreign or unknown ownership falls through. Explicit third-party adapters live in `pi-code-previews/src/third-party/`, with one static registry entry and separate exact public package/source/name admission per adapter; they never widen builtin/native admission or register execution. Core/codemode preview selection changes presentation only, and codemode need not be active at startup. Native factories, schemas, execution, approvals, tool selection/exposure, and results remain with Pi. No native factory composition/interception, private definition lookup, host monkey-patching, manager replacement, or forced takeover is allowed.

Write is the sole execution-registration exception: its genuine before-write snapshot hook captures evidence under Pi's native mutation queue, admits only the builtin or proven prior package owner, preserves activation through `defaultActive`, and tracks attempted versus successful installation for mutate-then-refresh recovery. Questionnaire/task/subagent/image tools remain normally registered executable definitions owned by their respective packages.

Cold replay facades keep a fixed `self` shell and downstream content before trusted startup; rows resolved after readiness use ordinary renderers in Pi's own shell. At first readiness they adopt only their originating owner's captured appearance and reconstruct retained call/result content. Replacement/shutdown revoke that owner's scheduler; old rows never borrow replacement settings or animation authority. `selfShell: true` keeps renderer-only framing in all styles/backgrounds, including a combined native-like background for preview/on.

Use `CompactSummary` for semantic action, target, counts, metadata, outcome, issues, and an optional call tree. A settled summary must explicitly classify its domain outcome or a neutral `returned` delivery outcome. A successful transport or a false Pi error flag does not prove operation success. Cancellation, uncertainty, delivery failure, and cleanup blockers remain distinct outcomes or issues. `resolveCompactSummary` reconciles Pi's error flag: an error the summary did not classify becomes an error outcome explained by `failureMessage` over the error text. A summary that classifies its own outcome as an error may leave the explanation to a child row's error issue. `planCompactPresentation` adds the generic fallback for missing or malformed summaries. Neither parses diagnostics or classifies domains.

Status icons are ✓ success, ⚠ warning, ✗ error, ⊘ cancelled, and ? for an outcome that cannot be confirmed. Native Code Mode opts completed dispatches into a neutral checkmark through `CompactChild.returnedCheckmark`, without changing their `returned` status or asserting operation success. Other neutral returns and notifications retain a bullet, including standalone MCP's top-level `returned` outcome; green checks remain semantic success. Child rows do not synthesize textual outcome metadata; explicit producer counters and metadata remain unchanged. A parent's outcome is its own: children never change it. A program that handles its own failed calls is a warning with failed child rows. When one visible call stopped its program, that call's row says so and the program adds no second line.

Collapsed views use one semantic heading and at most one routine detail. Counters precede metadata, then enabled measured timing, normally only once a call has taken at least one second (`TIMING_VISIBLE_MS`). Native Code Mode opts its parent shell and child summaries into `showShortTiming` to display measured subsecond durations, including a recorded zero; `showTiming` still controls placement beside routine detail, not eligibility. The call's own issues follow the heading, one line each. A call tree shows at most five children, preferring active and problem calls; each child row shows its primary issue in place of its counter, moving it to an indented line beneath the row when it does not fit, and the omission row counts hidden failures. Omission and hidden-failure counts wrap on overflow instead of losing digits or failure evidence; branch decoration yields before splitting a failure fact that fits unadorned. Counters are alternatives in priority order; the first that fits is shown. Missing, malformed, or incomplete summaries get a heading from the arguments and either the error's first line or a "details on expand" hint, never a full card.

Native Code Mode separates bounded call evidence from semantic outcome eligibility. Inspect only the latest 256 `details.calls` slots, validate records independently, and validate saved-output paths separately. Retain valid neighbors, including under unknown outer headers. Omitted or rejected records cannot support completed success; use uncertain status, one coverage warning, and “N calls listed” for validated metadata records rather than inferred dispatch totals. Expanded Calls retains bounded receipts and coverage diagnostics; never search older slots or substitute inaccessible persisted `nestedCalls`. Settled `running` records are unconfirmed, not ongoing animation or inferred cancellation.

Native Code Mode may add **MCP discovery** or **tool discovery** from bounded parsed program source. These are intent hints, never discovery execution receipts; expansion explains that distinction. Recognize only direct unshadowed discovery helpers, and require explicit static MCP targets or namespace filters for MCP specificity. Inert text, unused function bodies, aliases, dynamic callees, unsupported source and exhausted budgets fall through. Do not infer from guest output, count helper sites, synthesize children, or instrument execution. A complete empty native ledger suppresses its zero counter only for conservatively discovery-only source; mixed programs retain observed dispatch counts in both styles, with incomplete/unavailable-ledger warnings unchanged. Unknown outer headers still decline semantic completion.

Native MCP children inside Code Mode use readable call/resource actions and targets from registered aliases or observed argument scalars only. Ambiguous aliases and full-length hash-suffixed names that could hide a truncated separator retain their original names; hash suffixes are never removed or expanded into guessed remote identifiers. Expanded call evidence retains the registered name and sanitized abbreviated arguments, not fabricated nested output. No MCP definition, connection, authentication, exposure, or activation is changed. Standalone native MCP presentation is included in Code Previews, independent of the builtin/codemode preview-tools list, with no startup toggle. Registered tool/resource definitions require exact builtin MCP metadata. Missing historical aliases are admitted conservatively only when a unique independently builtin-owned `/mcp` manager is proven; aliases and argument evidence never become guessed remote identities. Pi retains manager lifecycle, authentication, connections, configuration, execution, activation, exposure, permissions, results and images. Code Previews never composes or intercepts `createMcpExtension`, registers `/mcp`, or alters user MCP configuration. Previously installed standalone `pi-mcp-previews` must be removed manually from every scope and Pi reloaded; see the [migration guide](../migrations/native-mcp-codemode.md).

Native preview source is bounded by eight wrapped screen rows, with full source on expansion and the same bound under theme fallback. Settled output/error hints use the shared expansion affordance. Empty streaming Output sections are omitted. The default-false `animateProgress` content opt-in reuses the registering owner's scheduler across both styles and expansion states, independently of timing; disabled timing creates no timestamps. Retired or declined scheduler admission never borrows a replacement owner's scheduler. Native parent/child timing uses measured values only and obeys the existing timing setting. Parent elapsed time is observed from execution start and frozen at settlement, not summed from concurrent children; children retain their individual native `durationMs`. Pending or replayed parents without an observed start and children without valid measurements remain untimed.

## Issues

`CompactIssue` is `{ severity, code, message, detail? }`. Severity is `error`, `warning`, or `info`. `message` is one short human-facing sentence, identical collapsed and expanded; it never contains agent procedures, tool-call syntax, retry advice, or internal operation IDs. `detail` holds the agent-facing recovery or diagnostic text and appears dimmed beneath its message only when expanded. `info` issues, such as routine pagination or saved-output locations, appear only when expanded. Native Code Mode and MCP output clipping is informational when bounded native metadata names a nonblank saved-output path; missing or unusable recovery and save failures remain warnings. For a settled non-error standalone MCP call, preview style replaces only a recognized, owned saved-output envelope with a neutral Output expansion affordance. Extra text blocks, unrecognized/provider warnings, missing or malformed recovery, contradictory save-failure text, progress and errors retain their original preview behavior. Complete raw envelopes and recovery paths remain expanded. This is recovery evidence, not proof the agent has read enough or the artifact remains available. Unrelated errors, incomplete call ledgers, and aggregate-listing uncertainty remain visible; rendering never reads spill files. Equal `code`, `severity`, and `message` merge, keeping every distinct detail line.

Producers write their own messages in one style:

- Start with the subject, then what happened, then the specific fact: `auth-review is paused`, `read: unexpected field "file"`, `Timed out after 100 ms (line 1)`.
- Prefer content to category. Quote a worker's warning or question rather than saying one exists, unless the text opens with an instruction to the agent.
- Never prefix a label the message repeats (`Unknown tool: Unknown tool …`). No `Error:`, `Uncaught:`, or `[Kind]` prefixes, internal type names, tool-call syntax, IDs, or trailing period. State a location once, as `(line N)`.
- Choose severity by what the reader must do. Routine states, such as a stop the status already shows or changes awaiting normal review, are metadata or `info`, not warnings.
- A status that says only that something failed, such as an exit code, may add the one output line that says why, redacted and clipped short, or else what a conventional exit code or signal means. Never add more than one cause.
- Aim for about 70 characters. The renderer wraps a longer message rather than cutting it off, so producers shorten their own quoted text.

When no classification exists, use `failureMessage(text, fallback)` for failures or `firstLineMessage(text, fallback)` for other text. Both take the first nonblank line, escape control characters, drop error-class prefixes and wrappers, drop trailing sentences that instruct the reader, and clip to one bounded row. `failureMessage` first names common service and network failures (rate limits, authentication, server errors, connection loss, context overflow) from that line alone. `isAgentGuidance(text)` tells producers when quoted text opens with an instruction. Full raw text stays in the agent-facing result and the expanded view. `compactSubject` replaces opaque targets only in compact headings.

Every issue renders through `renderCompactIssues(issues, theme, width, expanded, indent)`: one line per issue with its own glyph and color, wrapped without clipping. Nested and asynchronous consumers use the same function under their own heading.

## Expanded composition

`expandedContent.renderCall` and `expandedContent.renderResult` use the original callback signatures. They return unique content only, without a second heading or issue list. Supply an empty `Container` when a slot intentionally has no unique content. An omitted callback retains the original slot; it does not discard it.

For valid summaries, compact expansion composes, in order, the shared heading, the call's issues with their details, unique call content, and unique result content within the selected frame. Without content callbacks the original call and result slots remain, with the issues between them. Malformed or absent summaries use original renderers. Nothing is subtracted to avoid repetition: label raw output, such as `expandedSection(theme, "Error", …)`, and let it repeat facts the issue lines state. Recovery text a producer appends for the agent may follow under its own label, such as Code Mode's "Agent notes", but is never removed. Expanded sections nest under the heading with labels at two columns and bodies at four. Full program source, commands, proposed edits, and other unique call content must remain accessible, including after a failure.

Original and content-only renderers have independent call/result `lastComponent` caches. Call construction precedes result construction. Shared state, live panels, mouse routing, invalidation, and session-owned animation keep their existing lifecycle. A construction or drawing failure restores raw-result fallback for that slot and never replays the failing renderer. Pi owns native images and transcript separators. Supported external adapters preserve opaque downstream expanded components and append complete arguments and all raw output/recovery text, including on generic fallback, because provider renderers may clip their own expanded views. They do not subtract or reinterpret opaque rendered content.

Expanded content must preserve exact input: arguments the heading cannot show exactly are listed in full, never collapsed or clipped.

## Preview style

Preview style is the default. It keeps each tool's own call and result renderers for their bodies, and the shell draws the same issue lines compact style shows, from the same summary, so both styles report the same problems in the same words. The issues sit between the call body and the result body. A tool whose call body holds content under its heading, such as a diff or a proposed file, places them itself with `previewIssuesSlot(context)` directly under the heading. Before a result exists the lines come from the arguments alone, so risky commands and possible secrets are visible while a call awaits approval. A cancelled call without issues shows `⊘ Cancelled`. A failing host theme falls back to the plain messages.

Renderers therefore draw no issue, warning, error, or outcome lines of their own, and no status line that restates an issue ("Completed with a problem", "Retained read failed"). Pi's row background already shows success, failure, and pending. A tool renderer draws:

- A heading from `renderToolHeader({ title, subtitle })`: the tool's human name and a human subject. No internal IDs (run, task, request, or result IDs) and no raw snake_case action tokens.
- A body: a bounded preview collapsed, with routine counts in muted text, and the full content once expanded. Agent-facing procedures, raw envelopes, and diagnostics appear only when expanded, under a label such as "Raw result" or "Agent notes".
- `toolRunningLine(theme, frame)` ("Running…") while it runs and has nothing else to show.
- Expansion affordances through `renderExpansionAffordance(label, expanded, theme)`, whose hint comes from the configured keys (`toolExpandHint()`, "ctrl+o to expand"). Never hard-code a key.

## Shared vocabulary

Formatting comes from `pi-cosmic-core`: `formatDuration` for how long something took, `formatElapsed` for live clocks, `formatRelativeAge`, `countLabel`, `formatBytes`, `formatCost`, `formatTimestamp`, `formatDisplayPath`, and `clipText`. Terminal-width clipping uses `clipToWidth` from `pi-cosmic-ui/manager`, which marks cuts with "…"; lint rejects direct `truncateToWidth` imports, whose default is "...". States use the one table in `pi-cosmic-ui/manager`: `managerActivityGlyph`, `managerActivityColor`, and `managerActivityLabel`. Live work is accent, so green only means success; waiting and paused work is a warning; the words are "starting", "running", "waiting", "paused", "stopping", "finished", "failed", and "stopped". Requests and questionnaires that end early are "cancelled" (always this spelling); running work that someone ends is "stopped". Spinners advance every `SPINNER_FRAME_MS`.

## Messages outside tool rows

Notifications, command replies, and confirmations follow the issue style: one plain line, no error-class prefix, internal IDs, tool-call syntax, or agent procedures. `notifyAtHostBoundary` tidies one-line messages (spacing, control characters, a final period) and leaves multi-line reports, such as help and status, as written. Raw failure text passes through `failureMessage` first. The shared phrasings are:

- A start failure: "X couldn't start" (warning).
- An unavailable feature: "X isn't available in this session" (warning).
- A failed action the user asked for: "Couldn't <do something>: <reason>" (error), or without a reason when there is none.
- No interactive terminal: "Open Pi in an interactive terminal to …" (warning).
- Bad arguments: "Usage: …" (warning).
- Success: a short past-tense statement (info).
- Confirmations name items by their display name, never by ID.

## Managers and settings commands

Full-screen managers share one key vocabulary: `j/k` or arrows move, `h/l` or ←/→ change pane, Enter inspects, `?` shows more, and Esc or `q` closes. Actions use the same letter everywhere: `x` stops, `i` interrupts, `u` resumes, `m` sends a message, `e` renames, `c` clears finished items, `f` toggles follow, `t` shows technical details, `a` opens more actions, `r` refreshes, and `n`/`p` page. Destructive or disruptive actions (`x`, `i`, `c`) ask for the same key again to confirm, with Esc to cancel, and the confirmation names the item.

Each extension has one slash command named for it, with subcommands that autocomplete: `/openai usage`, `/subagents profiles`, `/tasks settings`. `registerExtensionCommand` in `pi-cosmic-core` owns routing, completion, the overview a bare command shows when the extension has no main view, and the usage warning for an unknown subcommand; a subcommand that needs a session can be added when the session starts. There are no aliases for earlier names. Settings are always the `settings` subcommand: bare `/<extension> settings` opens the settings list in a terminal and shows help elsewhere; `help` lists ids, usage, and examples; `status` shows effective values; `[scope] <id> <value>` changes one setting. Workspace settings come from `settingsSubcommand` in `pi-cosmic-ui/boundary/host-settings-command`. Native `/mcp` retains Pi's server-management grammar. MCP presentation has no separate command or startup settings. `/activity` and `/ask-user` stay standalone because each is already a single view, and `/ultracode` (pi-subagents) stays standalone because it is named after its setting and takes a task, as in Claude Code. With Cosmic UI active, `/activity`, `/subagents`, and `/tasks` share the Workflows/Subagents/Tasks manager and retain source-specific actions; the latter two select their corresponding initial focus. Without an available Activity host, the feature commands retain their package-owned managers.

## Retention and validation

`createBoundedCompactIssuesSchema({ maxTextLength, maxEntries })` bounds issues that cross a package or persistence boundary. Sanitize and bound retained text at each boundary; clip display text or mark evidence incomplete rather than silently dropping attention. Do not increase existing retention limits to make rendering pass. Strip arbitrary failure bodies, redact sensitive content, and bound retained evidence before storage. Versioned receipts that change shape bump their version; older versions decline to the generic row rather than being reinterpreted.

The source-only `pi-code-previews/testing` export provides `createToolPresentationHarness`. It accepts actual executable definitions or renderer-only callbacks with separate call/result slots, supports lifecycle overrides, rendering at chosen widths, invalidation, and `cycle()` over configurable expansion states with opt-in invalidation. It defaults to core's `plainTheme`, never invokes execute, and has no Vitest dependency. The same export provides `renderContextFixture` (pending defaults), `applyPresentationSettings`/`withPresentationSettings` (overrides on a snapshot of current settings, kept through rendering and restored even on a throw), `captureRegistrations` (tools, message renderers, `toolRenderers`, and `resolveToolRenderers(name, base?)`), and `animationSchedulerProbe` with `probeAnimationOwnership` for the registering owner's scheduler. Consumer tests should reach presentation behavior through this export rather than `pi-code-previews/src/**`; each package keeps its own presentation assertions. `issueMessageStyleProblems(message, { forbidden, maxLength })` checks a message against the style rules above; each producer runs its messages through it rather than asserting exact copy. `galleryFrames` and `writeGallerySection` render registered calls as plain text for review: each package's `tests/presentation-gallery.test.ts` runs only under `PRESENTATION_GALLERY`, and `pnpm presentation:gallery` joins them into `presentation-gallery.txt`. Galleries assert nothing about wording. Conformance tests cover compact toggles, preview fallback, widths/backgrounds, uncertainty, issue merging, construction/drawing failures, source preservation, and unchanged execution/result objects.
