Sending code from Neovim to pi — the expected workflow

User-perspective storyboard for pi.nvim + pi-nvim-bridge. Status: planning. Companion specs: pi-nvim-bridge.md · pi-nvim-plugin.md.

The one-breath model: pi writes a file saying where it listens; nvim reads it, connects, and pastes your selection into pi's input; you decide in pi what to do with it.

0One-time setup

Install the extension once, add the plugin to your lazy spec, bind two keys. No config required.

shell
$ pi install npm:pi-nvim-bridge
✓ installed pi-nvim-bridge
lazy spec
{
  "mattleong/pi.nvim",
  keys = {
    { "<leader>ps", mode = { "n", "x" } },
    { "<leader>pr", mode = { "n", "x" } },
  },
  opts = {},
}

From now on, every pi you launch advertises itself in a private discovery file (<agentDir>/nvim-bridge-v1/<pid>.json, 0600) and cleans it up on exit. You never touch these.

Nothing is submitted for you. Press Enter in pi to send it as a prompt — or, if the agent is mid-turn, pi's own steer / follow-up handling applies, exactly as if you had typed it. An unsaved buffer adds an (unsaved changes) badge to the reference line.

4Several repos — routing is automatic

A pi per repo, one nvim with buffers from both. The buffer's path decides: whichever pi's cwd contains the file gets the snippet. No prompt, ever.

<leader>ps  → pi: src/app.ts:10-18   (cosmic-pi session)

buffer: ~/dev/CosmicNvim/lua/init.lua

5Several pis on one repo — pick once, pinned

Two pi sessions in the same checkout: the first send asks which one, labeled by pi's session name. The choice is pinned for that project — every later send is silent. No pane-position guessing.

nvim — first send only
Send to which pi session?
1. refactor-parser  · ~/dev/cosmic-pi
2. fix-flaky-tests  · ~/dev/cosmic-pi
Type number and <Enter> or click: 1
→ pi: src/parser.ts:88-95

6Worktree buffer, pi elsewhere — fallback, not a dead end

Editing in a worktree while pi runs in another checkout means no cwd matches. Instead of an error, you get the picker over all live sessions — because sending across checkouts is usually intentional. Pinned afterward like any other choice.

7When it can't deliver, it says so

Every failure is a one-line notify in nvim; pi's UI is never touched by failures. Stale state heals itself — a dead session's refused connection drops the pin and triggers one re-scan.

You didnvim says
Sent with no pi runningpi.nvim: no pi session running
Sent after pi restartedreconnects via re-scan; or pi.nvim: pi session unreachable — is it still running?
Updated one side onlypi.nvim: protocol mismatch — update pi.nvim or pi-nvim-bridge
Targeted a headless pipi.nvim: target pi session has no interactive UI
Selected > 512 KBselection too large — send a reference instead (:PiRef)
Wondered why it's broken:checkhealth pi — discovery dir, live candidates, protocol version

8What never happens

  • Your prompt is never submitted for you — staging only; queue/steer decisions stay in pi.
  • A send never interrupts a running turn — it can't; it only edits the input.
  • pi's UI shows no notifications from the bridge — the paste itself is the feedback; failures surface only in nvim.
  • The target is never guessed from window layout — ambiguity is asked about once, then pinned; works identically under Herdr, tmux, or bare terminals.
  • Nothing listens beyond loopback, and every request carries a per-process token readable only by your user.
  • nvim never deletes or edits pi's discovery files — pi owns their lifecycle.
