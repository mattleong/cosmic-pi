# Shared tool presentation

This is the normative contract for workspace-owned visible tools. `pi-code-previews` owns presentation policy and composition. Each tool package owns domain classification and its unique content. Rendering must not change tool execution, permissions, result content, retained artifacts, or native images.

## Registration and policy

Load trusted preview settings before wrapping and registering owned definitions. Wrapping captures collapsed style and background mode until reload. Never wrap another extension's tools. Extensions importing the shell declare `pi-code-previews` as a runtime dependency.

Use `CompactSummary` for semantic action, target, counts, metadata, outcome, issues, and an optional call tree. A settled summary must explicitly classify its domain outcome. A successful transport or a false Pi error flag does not prove operation success. Cancellation, uncertainty, delivery failure, and cleanup blockers remain distinct outcomes or issues. `resolveCompactSummary` reconciles Pi's error flag: an error the summary did not classify becomes an error outcome explained by the first line of the error text. `planCompactPresentation` adds the generic fallback for missing or malformed summaries. Neither parses diagnostics or classifies domains.

Status icons are ✓ success, ⚠ warning, ✗ error, ⊘ cancelled, and ? for an outcome that cannot be confirmed. A parent's outcome is its own: children never change it. A program that handles its own failed calls is a warning with failed child rows.

Collapsed views use one semantic heading and at most one routine detail. Counters precede metadata, then enabled measured timing. The call's own issues follow the heading, one line each. A call tree shows at most five children, preferring active and problem calls; each child row shows its primary issue in place of its counter, moving it to an indented line beneath the row when it does not fit, and the omission row counts hidden failures. Counters are alternatives in priority order; the first that fits is shown. Missing, malformed, or incomplete summaries get a heading from the arguments and either the error's first line or a "details on expand" hint, never a full card.

## Issues

`CompactIssue` is `{ severity, code, message, detail? }`. Severity is `error`, `warning`, or `info`. `message` is one short human-facing sentence, identical collapsed and expanded; it never contains agent procedures, tool-call syntax, retry advice, or internal operation IDs. `detail` holds the agent-facing recovery or diagnostic text and appears dimmed beneath its message only when expanded. `info` issues, such as routine pagination or saved-output locations, appear only when expanded. Equal `code`, `severity`, and `message` merge, keeping every distinct detail line.

Producers write their own messages. When no classification exists, use `firstLineMessage(text, fallback)`: the first nonblank line of the error, with control characters escaped, clipped to one row. Full raw text stays in the agent-facing result and the expanded view. `compactSubject` replaces opaque targets only in compact headings.

Every issue renders through `renderCompactIssues(issues, theme, width, expanded, indent)`: one line per issue with its own glyph and color, wrapped without clipping. Nested and asynchronous consumers use the same function under their own heading.

## Expanded composition

`expandedContent.renderCall` and `expandedContent.renderResult` use the original callback signatures. They return unique content only, without a second heading or issue list. Supply an empty `Container` when a slot intentionally has no unique content. An omitted callback retains the original slot; it does not discard it.

For valid summaries, compact expansion composes, in order, the shared heading, the call's issues with their details, unique call content, and unique result content within the selected frame. Without content callbacks the original call and result slots remain, with the issues between them. Preview style and malformed or absent summaries use original renderers. Nothing is subtracted to avoid repetition: label raw output, such as `expandedSection(theme, "Error", …)`, and let it repeat facts the issue lines state. Expanded sections nest under the heading with labels at two columns and bodies at four. Full program source, commands, proposed edits, and other unique call content must remain accessible, including after a failure.

Original and content-only renderers have independent call/result `lastComponent` caches. Call construction precedes result construction. Shared state, live panels, mouse routing, invalidation, and session-owned animation keep their existing lifecycle. A construction or drawing failure restores raw-result fallback for that slot and never replays the failing renderer. Pi owns native images and transcript separators.

In preview style, builtin tools render the same issue lines directly under their heading. Before a result exists, argument-based warnings such as risky commands and possible secrets appear there, so they are visible while a call awaits approval. Their former inline warning headers and truncation footers are gone. Expanded content must preserve exact input: arguments the heading cannot show exactly are listed in full, never collapsed or clipped.

## Retention and validation

`createBoundedCompactIssuesSchema({ maxTextLength, maxEntries })` bounds issues that cross a package or persistence boundary. Sanitize and bound retained text at each boundary; clip display text or mark evidence incomplete rather than silently dropping attention. Do not increase existing retention limits to make rendering pass. Strip arbitrary failure bodies, redact sensitive content, and bound retained evidence before storage. Versioned receipts that change shape bump their version; older versions decline to the generic row rather than being reinterpreted.

The source-only `pi-code-previews/testing` export provides `createToolPresentationHarness`. It invokes real registered render callbacks with separate call/result slots, supports lifecycle overrides, rendering at chosen widths, invalidation, and `cycle()` over configurable expansion states with opt-in invalidation. It defaults to core's `plainTheme`, never invokes execute, and has no Vitest dependency. The same export provides `renderContextFixture` (pending defaults), `applyPresentationSettings`/`withPresentationSettings` (overrides on a snapshot of current settings, kept through rendering and restored even on a throw), `captureRegistrations` (tools and message renderers), and `animationSchedulerProbe` with `probeAnimationOwnership` for the registering owner's scheduler. Consumer tests should reach presentation behavior through this export rather than `pi-code-previews/src/**`; each package keeps its own presentation assertions. Conformance tests cover compact toggles, preview fallback, widths/backgrounds, uncertainty, issue merging, construction/drawing failures, source preservation, and unchanged execution/result objects.

The private coordinator proxy (the delegated-Pi bridge's `SupervisorProxy` RPC) is not a visible Pi tool row. Code Mode's seven direct builtin adapters and Windows-only PowerShell execute headlessly; their bounded nested receipts use Code Mode's shared presentation, not a second registered shell.

Better xAI, Directory Models, Herdr BTW, Cosmic UI, and Cosmic Core register no visible tool renderer to migrate. Their commands, settings, footer, and manager interfaces remain outside this tool contract. Third-party tools are outside workspace ownership.
